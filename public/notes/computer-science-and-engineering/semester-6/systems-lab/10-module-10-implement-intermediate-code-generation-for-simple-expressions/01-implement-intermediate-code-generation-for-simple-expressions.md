# Systems Lab: Module 10 - Intermediate Code Generation for Simple Expressions

## 1. Introduction to Intermediate Code Generation (ICG)

Intermediate Code Generation (ICG) is a crucial phase in a compiler, situated between syntax analysis (parsing) and code optimization. Its primary purpose is to transform the source code into a representation that is closer to machine code but still independent of the target architecture. This intermediate representation (IR) simplifies the subsequent stages of compilation, particularly optimization and target code generation.

**Key Concepts:**

*   **Compiler:** A program that translates source code written in one programming language into another language, typically machine code or a lower-level language.
*   **Source Code:** The human-readable code written by a programmer.
*   **Target Code:** The code generated by the compiler that can be executed by the target machine.
*   **Intermediate Representation (IR):** A machine-independent representation of the source program that facilitates optimization and target code generation.

**Why ICG is Important:**

*   **Simplifies Optimization:** Many optimization techniques are easier to implement on an IR than directly on the source code or target code.
*   **Enhances Portability:** By decoupling the front-end (parsing and semantic analysis) from the back-end (optimization and code generation), compilers can be more easily retargeted to different machine architectures.
*   **Improves Readability and Debugging:** ICG can make the program's structure more explicit, aiding in debugging.

## 2. Types of Intermediate Representations

There are several common forms of intermediate representations. For simple expressions, we will focus on the most relevant ones.

### 2.1. Abstract Syntax Trees (ASTs)

An AST is a tree representation of the abstract syntactic structure of the source code. It omits irrelevant details like punctuation, keywords, and operands at the same level of precedence. Nodes in the AST represent operations or values.

**Characteristics:**

*   Hierarchical structure.
*   Nodes represent operators, operands, or control flow constructs.
*   Edges represent the relationships between these elements.

**Example:** For the expression `a = b + c * d`

```
      =
     / \
    a   +
       / \
      b   *
         / \
        c   d
```

**Advantages:**

*   Naturally represents the hierarchical structure of expressions.
*   Easy to traverse and manipulate for optimization.

**Disadvantages:**

*   Can be verbose for linear sequences of operations.

### 2.2. Three-Address Code (TAC)

Three-address code is a form of IR where each instruction has at most three operands (two source operands and one destination operand). It's a linear sequence of instructions.

**Characteristics:**

*   Each instruction typically performs a single operation.
*   Uses temporary variables to store intermediate results.
*   Common forms include:
    *   **Assignment:** `result = operand1 operator operand2` (e.g., `t1 = b + c`)
    *   **Copy:** `result = operand1` (e.g., `a = t2`)
    *   **Unconditional jump:** `goto label`
    *   **Conditional jump:** `if condition goto label`
    *   **Function calls:** `result = func(arg1, arg2)`

**Example:** For the expression `a = b + c * d`

1.  `t1 = c * d`
2.  `t2 = b + t1`
3.  `a = t2`

**Advantages:**

*   Linear and easy to generate.
*   Well-suited for many optimization techniques (e.g., common subexpression elimination, dead code elimination).
*   Explicitly shows the flow of computation and the use of temporary variables.

**Disadvantages:**

*   Can be less intuitive for complex nested structures compared to ASTs.

### 2.3. Postfix Notation (Reverse Polish Notation - RPN)

Postfix notation is a way of writing arithmetic expressions where the operator follows its operands. It's often used in stack-based evaluation.

**Characteristics:**

*   No parentheses are needed.
*   Evaluation is straightforward using a stack.

**Example:** For the expression `a = b + c * d`

Assuming `b + c * d` is evaluated first: `b c d * +`
Then assigned to `a`: `a b c d * + =`

**Advantages:**

*   Simple to evaluate using a stack.
*   Can be a direct output from a recursive descent parser.

**Disadvantages:**

*   Less readable for humans than infix notation.
*   Less suitable for direct optimization compared to TAC.

## 3. Generating Intermediate Code for Simple Expressions

Simple expressions typically involve arithmetic operators (`+`, `-`, `*`, `/`), assignment (`=`), and operands (variables or constants). We'll focus on generating Three-Address Code (TAC) and briefly discuss AST generation.

### 3.1. Generating ASTs for Expressions

The generation of ASTs is closely tied to the parsing phase. A recursive descent parser can naturally build an AST as it processes the input.

**Example: Parsing `x = y + z * 2`**

A parser would recognize the structure:
*   An assignment statement (`=`).
*   The left-hand side (`x`).
*   The right-hand side, which is an expression.
    *   The expression is an addition (`+`).
    *   The left operand of addition is a variable (`y`).
    *   The right operand of addition is a multiplication (`*`).
        *   The left operand of multiplication is a variable (`z`).
        *   The right operand of multiplication is a constant (`2`).

This structure directly maps to the AST shown earlier.

### 3.2. Generating Three-Address Code (TAC) for Expressions

Generating TAC from an AST or directly during parsing is a common approach. We'll use a recursive approach based on the structure of the expression.

**Key Idea:** For each operation, generate a TAC instruction and store the result in a temporary variable. This temporary variable becomes an operand for subsequent operations.

**Rules for Generating TAC:**

1.  **Leaf Nodes (Operands):** If a node is an operand (variable or constant), its value is directly available.
2.  **Binary Operation Nodes:** For a node representing `operand1 op operand2`:
    *   Recursively generate TAC for `operand1`. Let its result be `t_left`.
    *   Recursively generate TAC for `operand2`. Let its result be `t_right`.
    *   Generate a new temporary variable, say `t_result`.
    *   Create a TAC instruction: `t_result = t_left op t_right`.
    *   Return `t_result`.
3.  **Assignment Nodes:** For an assignment `variable = expression`:
    *   Recursively generate TAC for `expression`. Let its result be `t_expr`.
    *   Generate a TAC instruction: `variable = t_expr`.

**Managing Temporary Variables:**

A global counter is typically used to generate unique temporary variable names (e.g., `t1`, `t2`, `t3`, ...).

**Example 1: `a = b + c * d`**

Let's assume parsing produces an AST. We can traverse this AST to generate TAC.

*   **Expression:** `b + c * d`
    *   **Sub-expression:** `c * d`
        *   **Operand:** `c` -> `t1 = c` (implicitly, or can be treated as is)
        *   **Operand:** `d` -> `t2 = d` (implicitly)
        *   **Operation:** `*` -> `t3 = t1 * t2` (or directly `t3 = c * d`)
    *   **Operand:** `b` -> `t4 = b` (implicitly)
    *   **Operation:** `+` -> `t5 = t4 + t3` (or `t5 = b + t3`)
*   **Assignment:** `a = ...`
    *   **Result of expression:** `t5`
    *   **TAC:** `a = t5`

**Consolidated TAC:**

Assuming we don't explicitly generate temporaries for single operands and use them directly where possible:

1.  `t1 = c * d`
2.  `t2 = b + t1`
3.  `a = t2`

**Example 2: `x = (y + z) * (w - v)`**

Let's generate TAC directly, considering operator precedence and parentheses.

1.  `t1 = y + z`  (Parentheses force this first)
2.  `t2 = w - v`  (Parentheses force this first)
3.  `t3 = t1 * t2` (Multiplication has higher precedence than potential implied addition/subtraction at higher levels)
4.  `x = t3`

**Example 3: `a = b / c + d - e`**

Standard operator precedence: `/` and `*` before `+` and `-`. Operations of the same precedence are evaluated left-to-right.

1.  `t1 = b / c`
2.  `t2 = t1 + d`
3.  `t3 = t2 - e`
4.  `a = t3`

**Implementation Considerations:**

*   **Recursive Descent Parsing:** A parser can be augmented to generate TAC. For an expression grammar like:
    ```
    expression -> term { ('+' | '-') term }
    term -> factor { ('*' | '/') factor }
    factor -> '(' expression ')' | identifier | number
    ```
    When reducing an `expression` with `+` or `-`, you'd generate the corresponding TAC instruction. Similar logic applies to `term` and `factor`.

*   **Semantic Actions:** In parser generators (like Yacc/Bison), semantic actions associated with grammar rules can be used to emit TAC.

## 5. Practice Questions and Exercises

**Question 1:**
Consider the following expression: `result = 5 + x * (y - 2)`
Generate the Three-Address Code for this expression.

**Answer 1:**
Assuming `x`, `y` are variables and `5`, `2` are constants.

1.  `t1 = y - 2`
2.  `t2 = x * t1`
3.  `t3 = 5 + t2`
4.  `result = t3`

**Question 2:**
What is the primary advantage of using Three-Address Code over direct machine code generation for compiler optimization?

**Answer 2:**
Three-Address Code provides a structured, machine-independent representation that makes it easier to identify and perform various optimization transformations (like common subexpression elimination, constant folding, dead code elimination) compared to working directly with complex machine code or abstract syntax trees. It explicitly represents intermediate results, making these transformations more apparent.

**Question 3:**
How would an Abstract Syntax Tree (AST) represent the expression `a = b + c`? Draw the AST.

**Answer 3:**
The AST would have the assignment operator (`=`) as the root. Its left child would be the variable `a`, and its right child would be the addition operator (`+`). The addition operator's children would be the variables `b` and `c`.

```
      =
     / \
    a   +
       / \
      b   c
```

**Question 4:**
Generate the Three-Address Code for: `a = b * c + d / e - f`

**Answer 4:**
Following standard operator precedence (`*`, `/` before `+`, `-`) and left-to-right evaluation for same precedence:

1.  `t1 = b * c`
2.  `t2 = d / e`
3.  `t3 = t1 + t2`
4.  `t4 = t3 - f`
5.  `a = t4`

## 6. Important Points to Remember

*   **Intermediate Code Generation (ICG)** is a bridge between parsing and code optimization/generation.
*   Common IRs include **Abstract Syntax Trees (ASTs)** and **Three-Address Code (TAC)**.
*   **TAC** is characterized by instructions with at most three operands (two sources, one destination).
*   **Temporary variables** are essential for storing intermediate results in TAC.
*   Operator **precedence** and **associativity** (and parentheses) dictate the order of operations and thus the sequence of TAC instructions.
*   Generating TAC often involves **recursive traversal** of the expression's structure (either implicitly during parsing or explicitly from an AST).
*   The goal is to produce a clear, linear, and optimizable representation of the computation.
