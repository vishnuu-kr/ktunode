# MICROCONTROLLERS: Module 2 - Interrupt Handling

## Introduction

These notes cover interrupt handling in STM32 microcontrollers, a crucial aspect of real-time embedded programming. We will explore different types of interrupts, the interrupt vector table, interrupt priorities, and how to configure and use interrupts effectively.

## Learning Outcomes

By the end of this topic, you should be able to:

*   Understand the concept of interrupts and their importance in embedded systems.
*   Identify different types of interrupts available in STM32 microcontrollers (external, timer, peripheral).
*   Explain the interrupt vector table and its role in interrupt handling.
*   Configure and enable interrupts using the Nested Vector Interrupt Controller (NVIC).
*   Understand and implement interrupt priorities and preemption.
*   Write interrupt service routines (ISRs) and handle interrupt flags correctly.
*   Program and debug interrupt-driven applications.

## 1. Interrupt Concepts and Importance

*   **Definition:** An interrupt is a hardware-triggered event that suspends the normal execution of a program and transfers control to a dedicated piece of code called an **Interrupt Service Routine (ISR)** or interrupt handler.  After the ISR finishes, the processor returns to the point where it was interrupted.

*   **Importance:**
    *   **Real-Time Responsiveness:** Allows the microcontroller to respond to time-critical events immediately without constantly polling.  For example, reacting to a button press, a sensor reading exceeding a threshold, or a timer expiry.
    *   **Efficient Resource Utilization:** Frees the CPU to perform other tasks while waiting for external events, leading to better efficiency compared to polling.  Reduces CPU load.
    *   **Event-Driven Architecture:** Simplifies program design by structuring code around events rather than constantly checking for conditions.
    *   **Handling Asynchronous Events:** Enables the system to react to events that occur at unpredictable times.

*   **Polling vs. Interrupts:**

    | Feature          | Polling                                         | Interrupts                                   |
    |-----------------|---------------------------------------------------|-----------------------------------------------|
    | CPU Usage       | High - Constantly checking for events.         | Low - Only active when an event occurs.     |
    | Responsiveness  | Can be slow, dependent on polling frequency.    | Fast - Near instantaneous response to events. |
    | Code Complexity | Simpler for basic tasks.                        | More complex initially due to configuration. |
    | Suitability     | Simple, non-critical tasks.                     | Real-time applications, asynchronous events.   |

## 2. Types of Interrupts in STM32 Microcontrollers

STM32 microcontrollers offer a variety of interrupt sources, broadly categorized as:

*   **External Interrupts (EXTI):** Triggered by changes on GPIO pins.  These are the most common for responding to external signals like button presses, sensor readings, etc.
    *   Configurable for rising edge, falling edge, or both.
    *   Each GPIO pin can be configured as an EXTI source.
    *   Multiple GPIO pins can share the same EXTI line.
*   **Timer Interrupts:** Generated by timers when they reach a certain count or compare value. Useful for creating periodic tasks, PWM generation, or measuring time intervals.
    *   Different types of timer interrupts: update interrupt, capture/compare interrupt, etc.
    *   Each timer peripheral has its own interrupt vector.
*   **Peripheral Interrupts:** Generated by other peripherals like UART, SPI, I2C, ADC, etc., when they complete a specific task or encounter an error.  For example:
    *   UART: Interrupt when data is received or transmitted.
    *   SPI/I2C: Interrupt when a data transfer is complete.
    *   ADC: Interrupt when a conversion is complete.
*   **System Interrupts:** Generated by the CPU itself for exceptions like memory faults, division by zero, or supervisor calls (SVC). Often related to system errors or OS operation.

## 3. Interrupt Vector Table

*   **Definition:** A table stored in memory that maps interrupt numbers (vectors) to the addresses of the corresponding ISRs.  When an interrupt occurs, the CPU uses the interrupt number to look up the address of the ISR in the vector table and jumps to that address.

*   **Location:**  The interrupt vector table is typically located at the beginning of flash memory.  The exact address is usually specified in the linker script.

*   **Structure:** Each entry in the table contains the address of the ISR for a specific interrupt.

*   **Importance:** Essential for the CPU to know where to jump when an interrupt occurs. Without a properly configured interrupt vector table, the system will crash or behave unpredictably.

*   **Example (Simplified):**

    | Vector Number | Address          | Description             |
    |----------------|-------------------|--------------------------|
    | 0             | `0x08000000`       | Stack Pointer Initialization |
    | 1             | `0x08000004`       | Reset Handler            |
    | 2             | `0x08000008`       | NMI Handler              |
    | 3             | `0x0800000C`       | HardFault Handler        |
    | ...           | ...              | ...                      |
    | 6             | `0x08000018`       | SVC Handler              |
    | ...           | ...              | ...                      |
    | 39            | `0x0800009C`       | EXTI0_IRQHandler        |  (External interrupt line 0)
    | ...           | ...              | ...                      |

*   **Note:**  The vector table is often defined in the startup assembly file (e.g., `startup_stm32f407xx.s`).  The compiler automatically places the ISR function names in the correct locations in the table during the linking process, *provided the ISR functions are correctly named*.

## 4. Nested Vector Interrupt Controller (NVIC)

*   **Role:** The NVIC is a crucial component of the ARM Cortex-M processor. It manages interrupt priorities and enables/disables interrupts. It's responsible for:
    *   **Enabling/Disabling Interrupts:** Allows software to selectively enable or disable specific interrupts.
    *   **Priority Management:** Assigns priority levels to different interrupts, allowing higher-priority interrupts to preempt lower-priority ones.
    *   **Interrupt Masking:** Temporarily disabling interrupts globally (useful for critical sections of code).

*   **Key Registers:**
    *   **ISER (Interrupt Set-Enable Registers):** Used to enable individual interrupts.  Setting a bit in this register enables the corresponding interrupt.
    *   **ICER (Interrupt Clear-Enable Registers):** Used to disable individual interrupts.  Setting a bit in this register disables the corresponding interrupt.
    *   **IPR (Interrupt Priority Registers):** Used to assign priority levels to each interrupt.  Each interrupt has a dedicated byte (or more, depending on the processor) in the IPR, allowing for multiple priority levels.

*   **Configuration Steps:**

    1.  **Enable the Interrupt Clock:**  Enable the clock for the peripheral associated with the interrupt (e.g., enable GPIO clock for EXTI interrupts).  This is usually done in the Reset and Clock Control (RCC) peripheral.
    2.  **Configure the Peripheral (if needed):**  Configure the specific peripheral generating the interrupt (e.g., configure GPIO pin as an input for EXTI).
    3.  **Configure the EXTI (if applicable):** For external interrupts, configure the EXTI line to detect rising/falling edges, enable the EXTI interrupt, and select the corresponding GPIO port.
    4.  **Set Interrupt Priority:** Use `NVIC_SetPriority()` to assign a priority level to the interrupt.  Higher values represent *lower* priority on some architectures. Check your specific microcontroller's documentation!
    5.  **Enable the Interrupt in the NVIC:** Use `NVIC_EnableIRQ()` to enable the interrupt in the NVIC.

*   **Example (HAL library):**

    ```c
    // Example for enabling EXTI0 interrupt (connected to GPIO PA0)

    // 1. Enable GPIO clock (RCC already configured elsewhere)

    // 2. Configure GPIO PA0 as input (already configured elsewhere)

    // 3. Configure EXTI0
    SYSCFG->EXTICR[0] &= ~SYSCFG_EXTICR1_EXTI0;  // Clear existing configuration
    SYSCFG->EXTICR[0] |= SYSCFG_EXTICR1_EXTI0_PA; // Select PA0 as EXTI0 source

    EXTI->IMR |= EXTI_IMR_MR0;     // Unmask EXTI0 line (enable interrupt requests)
    EXTI->FTSR |= EXTI_FTSR_TR0;   // Trigger on falling edge

    // 4. Set Interrupt Priority (lower value = higher priority)
    NVIC_SetPriority(EXTI0_IRQn, 0);

    // 5. Enable EXTI0 Interrupt in NVIC
    NVIC_EnableIRQ(EXTI0_IRQn);
    ```

## 5. Interrupt Priorities and Preemption

*   **Interrupt Priorities:**  Assigning priority levels allows the NVIC to determine which interrupt to handle when multiple interrupts occur simultaneously.  A higher-priority interrupt can interrupt (preempt) a lower-priority interrupt that is currently being handled.

*   **Preemption:** The ability of a higher-priority interrupt to interrupt a lower-priority interrupt handler.

*   **Subpriority (Grouping):** STM32 microcontrollers allow you to divide the interrupt priority register into two parts:
    *   **Preemption Priority:** Determines if an interrupt can preempt another interrupt.
    *   **Subpriority:** Determines the order in which interrupts of the same preemption priority are handled. If multiple interrupts with the same preemption priority occur, the one with the lower subpriority value is handled first.

*   **NVIC_SetPriorityGrouping():** This function configures the number of bits used for preemption priority and subpriority. The valid values are defined as follows:
    * `NVIC_PRIORITYGROUP_0`: 0 bits for preemption priority, 4 bits for subpriority (16 subpriority levels)
    * `NVIC_PRIORITYGROUP_1`: 1 bits for preemption priority, 3 bits for subpriority (2 preemption levels, 8 subpriority levels)
    * `NVIC_PRIORITYGROUP_2`: 2 bits for preemption priority, 2 bits for subpriority (4 preemption levels, 4 subpriority levels)
    * `NVIC_PRIORITYGROUP_3`: 3 bits for preemption priority, 1 bits for subpriority (8 preemption levels, 2 subpriority levels)
    * `NVIC_PRIORITYGROUP_4`: 4 bits for preemption priority, 0 bits for subpriority (16 preemption levels, 1 subpriority level)

*   **Important Considerations:**
    *   Careful priority assignment is critical for system stability.  Give higher priority to time-critical tasks (e.g., motor control, sensor data acquisition).
    *   Avoid assigning the same priority to multiple interrupts unless they are non-critical and their order of execution doesn't matter.
    *   Use `NVIC_SystemReset()` to reset the system after changing priority grouping.

## 6. Interrupt Service Routines (ISRs)

*   **Definition:** A special function that is executed when an interrupt occurs.

*   **Naming Convention:** ISRs must have specific names, as defined in the STM32's startup file or interrupt vector table.  For example, `EXTI0_IRQHandler` for the EXTI0 interrupt.  Incorrect naming will result in the ISR not being called.

*   **Key Responsibilities:**
    1.  **Identify the Interrupt Source:**  Determine which specific event triggered the interrupt (e.g., which EXTI line, which UART flag). This is done by checking the interrupt flags in the peripheral's status registers.
    2.  **Clear the Interrupt Flag:**  This is *essential* to prevent the ISR from being called repeatedly.  Failing to clear the flag will result in the ISR being entered again immediately after it returns, leading to a system lockup.
    3.  **Perform the Necessary Action:**  Execute the code required to handle the event (e.g., read sensor data, send data over UART, toggle an LED).
    4.  **Exit the ISR:**  The ISR must return to the interrupted code. The compiler takes care of this automatically.

*   **Example (EXTI0_IRQHandler):**

    ```c
    void EXTI0_IRQHandler(void) {
        if (EXTI->PR & EXTI_PR_PR0) { // Check if EXTI0 interrupt occurred
            EXTI->PR |= EXTI_PR_PR0; // Clear the pending request flag for EXTI0
            // Perform the necessary action (e.g., toggle an LED)
            HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_12); // Example for toggling PD12 LED
        }
    }
    ```

*   **Important Guidelines:**

    *   **Keep ISRs Short and Fast:**  ISRs should execute quickly to minimize the time during which interrupts are disabled. Avoid performing lengthy calculations or blocking operations in ISRs.
    *   **Avoid Floating-Point Operations:**  Floating-point operations can be slow and may introduce non-deterministic timing.  Use integer arithmetic whenever possible.
    *   **Use Volatile Variables:**  If an ISR modifies a variable that is also accessed in the main program, declare the variable as `volatile`. This tells the compiler that the variable's value can change unexpectedly and prevents it from optimizing away reads or writes.  Example:  `volatile uint32_t count;`
    *   **Disable Interrupts Sparingly:**  Disable interrupts only for the shortest possible time when necessary to protect critical sections of code.
    *   **Re-enable Interrupts:** If interrupts are disabled within an ISR, be sure to re-enable them before exiting the ISR, *if appropriate*.  However, generally avoid disabling interrupts within an ISR unless absolutely necessary.

## 7. Programming and Debugging Interrupt-Driven Applications

*   **Debugging Challenges:** Debugging interrupt-driven applications can be more complex than debugging sequential code due to the asynchronous nature of interrupts.

*   **Debugging Techniques:**
    *   **Use a Debugger:**  A debugger allows you to step through code, set breakpoints, and examine variables.  It's essential for understanding the flow of execution and identifying problems in ISRs.
    *   **Logic Analyzer:**  A logic analyzer can be used to capture digital signals, including interrupt signals, allowing you to verify the timing and frequency of interrupts.
    *   **Printf Debugging (with caution):**  Use `printf` statements (or similar debugging functions) to output information about the state of the system. *However*, be aware that `printf` is a relatively slow operation and can affect the timing of interrupts. Use with care, and consider using a circular buffer and background UART transmission to minimize impact.
    *   **Scope and Pin Toggle Method:** Toggle a GPIO pin at the start and end of your ISR. Using an oscilloscope will allow you to determine the execution time of the ISR and verify that the interrupt is triggered correctly.
    *   **CMSIS-DAP/J-Link Debugger:** Modern debuggers allow you to view the NVIC state and active interrupts.

*   **Common Pitfalls:**
    *   **Forgetting to Clear Interrupt Flags:**  This is the most common cause of infinite ISR loops and system lockups.
    *   **Incorrect Interrupt Priority Assignment:** Can lead to unexpected preemption and incorrect behavior.
    *   **Stack Overflow:**  ISRs consume stack space.  If the ISR is too large or if there are too many nested interrupts, a stack overflow can occur, leading to a crash.
    *   **Race Conditions:**  When an ISR modifies a variable that is also accessed in the main program, a race condition can occur if the ISR interrupts the main program at an inopportune time. Use volatile variables and consider disabling interrupts briefly to protect critical sections of code.
    *   **Interrupt Latency:** The time it takes for the system to respond to an interrupt. Factors such as interrupt priority, nested interrupts, and long ISRs can increase interrupt latency.
