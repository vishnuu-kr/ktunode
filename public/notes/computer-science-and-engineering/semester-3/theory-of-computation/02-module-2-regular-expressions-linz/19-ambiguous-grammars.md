## THEORY OF COMPUTATION: Module 2 - Regular Expressions (Linz) - Ambiguous Grammars

These notes cover the concept of ambiguous grammars as presented in Linz's "An Introduction to Formal Languages and Automata" in the context of regular expressions (although ambiguity more generally applies to context-free grammars as well).

**Learning Outcomes:**

*   Define what constitutes an ambiguous grammar.
*   Identify ambiguous grammars.
*   Explain the problems caused by ambiguous grammars.
*   Understand how ambiguity relates to derivations and parse trees.
*   Be aware of methods (though not necessarily perform) for resolving ambiguity in some cases.

### 1. Definition of Ambiguous Grammar

*   **Definition:** A grammar G is said to be *ambiguous* if there exists at least one string `w` in L(G) (the language generated by G) that has two or more *different* parse trees, or equivalently, two or more *different* leftmost (or rightmost) derivations.

    *   **Key Idea:** The ambiguity arises from the *process* of generation, not the string itself.  Multiple ways to build the same string demonstrate the grammar's ambiguity.

*   **Unambiguous Grammar:**  A grammar that is not ambiguous is considered *unambiguous*.

*   **Important Note:** Ambiguity is a property of the *grammar*, not the language.  It is possible for a language to have both ambiguous and unambiguous grammars that generate it. In other words, ambiguity is tied to the *rules* of production in the grammar, not the set of strings the grammar is capable of producing.

### 2. Parse Trees and Derivations

*   **Parse Tree (Derivation Tree):** A graphical representation of a derivation. It illustrates how a string can be derived from the start symbol using the production rules of the grammar.

    *   **Root:** The root of the tree is the start symbol.
    *   **Internal Nodes:** Internal nodes are non-terminal symbols.
    *   **Leaves:** Leaves are terminal symbols (or the empty string, ε).
    *   **Construction:** A production rule `A -> X1 X2 ... Xn` means that node `A` has children `X1`, `X2`, ..., `Xn`.  The order matters.

*   **Leftmost Derivation:** A derivation where the *leftmost* non-terminal symbol is replaced in each step.

*   **Rightmost Derivation:** A derivation where the *rightmost* non-terminal symbol is replaced in each step.

*   **Ambiguity & Parse Trees/Derivations:**  A grammar is ambiguous if there exists a string `w` that has:

    *   Two or more different parse trees.
    *   Two or more different leftmost derivations.
    *   Two or more different rightmost derivations.

    *   **Important Relationship:**  Having different parse trees is equivalent to having different leftmost derivations, and also equivalent to having different rightmost derivations. You only need to find two different derivations *of one type* to prove ambiguity.

### 3. Identifying Ambiguous Grammars

*   **General Approach:** There is no algorithm to determine if an arbitrary context-free grammar is ambiguous. This is an undecidable problem.

*   **Common Patterns:**  Look for these common scenarios that often indicate ambiguity:

    *   **Multiple Production Rules for the Same Non-Terminal:**  If a non-terminal can be derived in several different ways, it's a potential source of ambiguity.
    *   **Lack of Precedence or Associativity:**  Especially in grammars involving arithmetic expressions, the absence of explicit precedence or associativity rules (e.g., for operators like +, -, *, /) often leads to ambiguity.
    *   **Chains of Productions:**  Long sequences of productions can sometimes hide multiple possible derivations.

*   **Proof by Example:**  To *prove* a grammar is ambiguous, you must provide a concrete example:

    1.  Choose a string `w` generated by the grammar.
    2.  Show two different parse trees for `w`. *OR*
    3.  Show two different leftmost derivations for `w`. *OR*
    4.  Show two different rightmost derivations for `w`.

### 4. Problems Caused by Ambiguous Grammars

*   **Semantic Uncertainty:**  The most significant problem.  Different parse trees represent different interpretations (semantics) of the same string.  This is especially problematic in programming language compilers:

    *   **Example: Arithmetic Expressions:**  Consider `1 + 2 * 3`.

        *   One parse tree might interpret this as `(1 + 2) * 3 = 9`.
        *   Another parse tree might interpret this as `1 + (2 * 3) = 7`.

        *   Without unambiguous rules of precedence, the compiler doesn't know which operation to perform first.

*   **Compiler/Parser Issues:** Ambiguous grammars can lead to unpredictable behavior in parsers.  The parser may choose one derivation arbitrarily, leading to incorrect code generation or unexpected results.

*   **Mathematical Inconsistencies:** In formal language theory and logic, ambiguities can invalidate proofs and undermine the consistency of systems.

### 5. Examples of Ambiguous Grammars

**Example 1: Simple Arithmetic Expression Grammar**

*   `E -> E + E | E * E | id`  (where `id` represents an identifier or number)

    *   **String:** `id + id * id`
    *   **Ambiguity:** This grammar doesn't specify operator precedence.

    *   **Leftmost Derivation 1:**
        `E  => E + E => id + E => id + E * E => id + id * E => id + id * id`

    *   **Leftmost Derivation 2:**
        `E => E * E => E + E * E => id + E * E => id + id * E => id + id * id`

    *   These derivations correspond to different parse trees and, hence, different evaluations.

**Example 2: Dangling Else**

*   `S -> if E then S | if E then S else S | a`  (where `S` is a statement, `E` is an expression, and `a` is some other statement)

    *   **String:** `if E1 then if E2 then a else a`
    *   **Ambiguity:** Which `if` does the `else` belong to?

    *   **Parse Tree 1:** The `else` belongs to the first `if`.
    *   **Parse Tree 2:** The `else` belongs to the second `if`.

**Example 3:**

* `S -> aSb | ab`

    * **String:** `aabb`
    * **Leftmost Derivation 1:**  `S => aSb => aaSbb => aabb`
    * **Leftmost Derivation 2:**  `S => ab => aaSb => aabb`  (Note, this one is a little tricky, but it exists.)

### 6. Resolving Ambiguity (Overview)

*   **Rewriting the Grammar:** The most common approach.  Design a new, unambiguous grammar that generates the same language.  This often involves:

    *   **Introducing Precedence:**  Create separate non-terminals for different precedence levels.
    *   **Enforcing Associativity:**  Use left- or right-recursive productions to dictate how operators of the same precedence are grouped.
    *   **Adding Extra Non-Terminals:**  Can force certain derivation patterns.

*   **Dangling Else Solution (Example):**

    ```
    S -> MS | US
    MS -> if E then MS else MS | a
    US -> if E then S | if E then MS else US
    ```

    *   `MS`: "Matched Statement" (an `if` statement where the `else` part matches the `if`)
    *   `US`: "Unmatched Statement" (an `if` statement with a potentially unmatched `else`)

    *   This grammar forces the `else` to match the *nearest* unmatched `if`.

*   **Parser Techniques (Beyond Scope):** Some parsers can handle ambiguous grammars with disambiguation rules (e.g., Yacc/Bison). These rules specify how to resolve conflicts when multiple parse trees are possible.  However, it's generally preferable to use an unambiguous grammar if possible.

*   **Important Note:**  Not all ambiguous grammars can be transformed into unambiguous ones. Some languages are *inherently ambiguous* (meaning that *every* grammar for that language is ambiguous). However, such languages are rarely used in programming.

### 7. Practice Questions/Exercises

**Question 1:** Is the following grammar ambiguous? Explain your answer.

```
S -> AB
A -> aA | a
B -> bB | b
```

**Answer 1:** No, the grammar is *not* ambiguous.  There is only one way to derive any string in the language `a+b+`. A leftmost (or rightmost) derivation will always yield a unique parse tree for a given string. For instance, the string `aab` will have the following leftmost derivation:

`S => AB => aAB => aaAB => aab`

and this is the only possible leftmost derivation.

**Question 2:**  Is the following grammar ambiguous? Prove your answer.

```
S -> aSbS | bSaS | ε
```

**Answer 2:** Yes, the grammar is ambiguous.

*   **String:** `abab`

*   **Leftmost Derivation 1:** `S => aSbS => abS => abaSbS => ababS => ababε => abab`

*   **Leftmost Derivation 2:** `S => bSaS => baS => baaSbS => baabS => baabε => baab`

Since the string `abab` is not accepted by that grammar, let's instead look at another valid string which does exist, let's consider "ababa"

*   **Leftmost Derivation 1:** `S => aSbS => abS => abaSbS => ababaS => ababaε => ababa`

*   **Leftmost Derivation 2:** `S => aSbS => aSbaS`... but from here there is no way to reach `ababa`, so let's pick a different string, `ababab` and try to show how it has two derivations.

*   **Leftmost Derivation 1:**  `S => aSbS => abS => abaSbS => ababS => ababaSbS => abababS => abababε => ababab`

*   **Leftmost Derivation 2:**  `S => aSbS => a (bSaS) bS` => from here it is clear that these are two different leftmost derivations.

**Question 3:** Identify the ambiguity in the following grammar and suggest how to remove it (conceptually, without writing the full grammar).

```
E -> E - E | n
```

(where `n` represents a number)

**Answer 3:** The ambiguity lies in the associativity of the `-` operator. This grammar allows for both left-associative and right-associative interpretations.

*   **To remove the ambiguity:** Enforce left-associativity (as is standard for subtraction) by using left recursion: `E -> E - n | n`.  This ensures that `a - b - c` is interpreted as `(a - b) - c`.

**Question 4:**  Explain why ambiguous grammars can be problematic for compilers.

**Answer 4:**  Ambiguous grammars lead to multiple possible interpretations of the same source code.  The compiler may choose an incorrect parse tree, resulting in code that doesn't behave as intended, incorrect optimization, or compilation errors.  Without a single, well-defined meaning, the compiler cannot reliably translate the source code into executable instructions. The compiler needs to have one and only one way to understand the input in order to generate executable code.

### 8. Important Points to Remember

*   Ambiguity is a property of the *grammar*, not the language.
*   To prove ambiguity, you must find *one* string with two different parse trees (or derivations).
*   Ambiguous grammars can lead to semantic uncertainty and compiler/parser issues.
*   Removing ambiguity often involves rewriting the grammar to enforce precedence and associativity.
*   Some languages are inherently ambiguous, but this is rare in programming.
