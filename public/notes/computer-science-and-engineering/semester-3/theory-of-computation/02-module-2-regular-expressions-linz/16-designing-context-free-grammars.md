## THEORY OF COMPUTATION - Module 2: Regular Expressions (Linz) - Designing Context-Free Grammars

**Topic:** Designing Context-Free Grammars (CFGs)

**Description:** This module focuses on designing context-free grammars, which are more powerful than regular expressions in describing formal languages. We will learn how to construct CFGs for various language types.

**Learning Outcomes:**

*   Understand the definition of a Context-Free Grammar (CFG).
*   Be able to design CFGs for languages specified in English or mathematical notation.
*   Recognize ambiguous grammars and understand how ambiguity affects parsing.
*   Learn techniques to simplify CFGs.
*   Understand the relationship between CFGs and Pushdown Automata (PDAs).

---

### 1. Introduction to Context-Free Grammars (CFGs)

*   **Definition:** A Context-Free Grammar (CFG) is a formal grammar that defines a set of strings (a language). It consists of four components:

    *   **V:** A finite set of variables (or non-terminals).  Represented by uppercase letters (e.g., `S`, `A`, `B`).
    *   **T:** A finite set of terminals. Represented by lowercase letters, digits, or special symbols (e.g., `a`, `b`, `0`, `1`). `V` and `T` are disjoint (they have no elements in common).
    *   **P:** A finite set of productions (or rules).  Each production is of the form `A -> α`, where `A` is a variable and `α` is a string of variables and terminals.  `α` can also be the empty string, denoted by `ε`.
    *   **S:** The start variable (or start symbol). A variable in `V` that initiates the derivation of strings in the language.

*   **Formal Notation:**  A CFG is often represented as G = (V, T, P, S).

*   **Derivation:**  The process of generating a string from the start variable using the production rules.

    *   **Direct Derivation (=>):**  `αAβ => αγβ` if `A -> γ` is a production in `P`. This means `γ` replaces `A` in the string `αAβ`.
    *   **Derives (=>*):**  The reflexive, transitive closure of `=>`.  This means that `α =>* β` if `α = β` or if there exists a sequence of derivations `α => γ1 => γ2 => ... => β`.  In simpler terms, `α` can be transformed into `β` by applying zero or more production rules.

*   **Language Generated by a CFG (L(G)):** The set of all strings consisting only of terminals that can be derived from the start variable.
    `L(G) = {w | w ∈ T* and S =>* w}`

**Example 1:**

Let's define a CFG that generates the language of palindromes over the alphabet {a, b}.

`G = (V, T, P, S)` where:

*   `V = {S}`
*   `T = {a, b}`
*   `P = {S -> aSa, S -> bSb, S -> a, S -> b, S -> ε}`
*   `S` is the start variable.

To generate the palindrome "abba":

`S => aSa => abSba => abbba` (using `S -> aSa`, `S -> bSb`, `S -> ε` and then the last two in reverse)
`S => abba` (direct derivation)

**Example 2:**

CFG for the language `L = {a^n b^n | n >= 0}`

`G = (V, T, P, S)` where:

*   `V = {S}`
*   `T = {a, b}`
*   `P = {S -> aSb, S -> ε}`
*   `S` is the start variable.

To generate the string "aabb":

`S => aSb => aaSbb => aaεbb => aabb`

### 2. Designing CFGs

Designing CFGs requires practice and understanding of the language structure. Here are some general guidelines and examples:

*   **Identify the Recursive Structure:**  Many context-free languages have a recursive structure. Look for patterns where the same element or structure is repeated within itself.

*   **Break Down the Language:**  Divide the language into smaller, manageable parts.  Create variables to represent these parts and then define the productions for each variable.

*   **Handle Base Cases:**  Define productions for the simplest strings in the language (the base cases of the recursion).  Often, this involves productions that derive directly to terminals or to the empty string (ε).

*   **Start Variable:** The start variable (S) should represent the entire language.

**Example 3:  Designing a CFG for balanced parentheses.**

The language consists of strings containing properly nested parentheses: `(), (()), (()()), ...`

`G = (V, T, P, S)` where:

*   `V = {S}`
*   `T = {(, )}`
*   `P = {S -> (S), S -> SS, S -> ε}`
*   `S` is the start variable.

Explanation:

*   `S -> (S)`:  Handles the nesting of parentheses.  An opening parenthesis, followed by a balanced string, followed by a closing parenthesis.
*   `S -> SS`: Handles the concatenation of two balanced strings.
*   `S -> ε`: Handles the empty string, which is also considered balanced.

**Example 4: Designing a CFG for the language `L = {a^m b^n | m > n >= 0}`**

This language has more 'a's than 'b's. We can break it down into:

*   A portion with an equal number of 'a's and 'b's (`a^n b^n`)
*   A remaining portion of 'a's (`a^(m-n)`) where `m-n > 0`

`G = (V, T, P, S)` where:

*   `V = {S, A}`
*   `T = {a, b}`
*   `P = {S -> aS | aA, A -> aA | ε}`
*   `S` is the start variable.

Explanation:

*   `S -> aS`: Generates an 'a' followed by the equal number of a's and b's
*   `S -> aA`: Generates an 'a' and then the excess a's
*   `A -> aA`: Adds extra a's
*   `A -> ε`: Terminates the extra a's

**Example 5:  Designing a CFG for the language of arithmetic expressions with `+`, `-`, `*`, `/`, and numbers.**

This requires handling operator precedence and associativity. A simplified version is:

`G = (V, T, P, E, T, F)` where:

*   `V = {E, T, F}` (Expression, Term, Factor)
*   `T = {id, +, -, *, /, (, )}` (id = identifier, representing a number)
*   `P = {
        E -> E + T | E - T | T,
        T -> T * F | T / F | F,
        F -> ( E ) | id
    }`
*   `E` is the start variable.

Explanation:

*   We use different variables to represent different levels of precedence.
*   `E` (Expression) handles addition and subtraction (lowest precedence).
*   `T` (Term) handles multiplication and division (medium precedence).
*   `F` (Factor) handles the highest precedence - expressions in parentheses and identifiers.
*   The recursive productions (e.g., `E -> E + T`) handle operator associativity (left associativity in this case).

### 3. Ambiguity in CFGs

*   **Definition:** A CFG is ambiguous if there exists a string in its language that has two or more distinct parse trees (or, equivalently, two or more distinct leftmost or rightmost derivations).

*   **Parse Tree:** A tree representation of the derivation of a string from the start variable. The root is the start variable, internal nodes are variables, and leaf nodes are terminals.

*   **Impact of Ambiguity:** Ambiguity can cause problems in parsing and language processing.  It can lead to multiple interpretations of a program or sentence, making it difficult to determine the intended meaning.

**Example 6: Ambiguous Grammar**

Consider the grammar:

`G = (V, T, P, S)` where:

*   `V = {S}`
*   `T = {a, b}`
*   `P = {S -> SS, S -> a, S -> b}`
*   `S` is the start variable.

The string "aba" has two possible parse trees:

1.  `S => SS => aS => aba`
2.  `S => SS => Sb => aSb => aba`

*   **Detecting Ambiguity:**  There is no general algorithm to determine if a CFG is ambiguous.  You often need to reason about the grammar structure and try to construct multiple parse trees for the same string.  Tools like parser generators might provide warnings about potential ambiguity.

*   **Resolving Ambiguity:** Ambiguity can sometimes be removed by rewriting the grammar. This is often done by explicitly defining precedence and associativity rules.  This is crucial in compiler design. For the above ambiguous grammar example, we cannot simply rewrite the grammar to be unambiguous, because it generates the set of all strings consisting of *a* and *b*.

**Example 7:  Ambiguous Grammar - Dangling Else**

A classic example of ambiguity in programming languages is the "dangling else" problem:

```
stmt -> if expr then stmt
stmt -> if expr then stmt else stmt
stmt -> other
```

The string `if E1 then if E2 then S1 else S2`  can be parsed in two ways:

1.  `if E1 then {if E2 then S1 else S2}` (else associated with the outer if)
2.  `if E1 then {if E2 then S1} else S2` (else associated with the inner if)

To resolve this, programming languages typically associate the `else` with the *nearest* unmatched `if`.  This can be achieved by rewriting the grammar to make the association explicit.

### 4. Simplification of CFGs (Optional but Helpful)

Simplifying CFGs can make them easier to understand and work with.  Common simplification techniques include:

*   **Eliminating Useless Symbols:**  A symbol (variable or terminal) is useless if it cannot appear in any derivation of a string of terminals.

    *   *Unreachable symbols:* symbols that cannot be derived from the start variable.
    *   *Unproductive symbols:* symbols that cannot derive any terminal strings.

*   **Eliminating Unit Productions:** A unit production is of the form `A -> B`, where A and B are variables. These can often be replaced by the productions of `B`.

*   **Eliminating ε-Productions:** Productions of the form `A -> ε`.  These can be more complex to eliminate, as they might require adding new productions to compensate.

**Important Note:** Simplification should preserve the language generated by the grammar.

---

### 5. Relationship between CFGs and Pushdown Automata (PDAs)

*   **Equivalence:** Context-Free Grammars (CFGs) and Pushdown Automata (PDAs) are equivalent formalisms.  That is:

    *   For every CFG, there exists a PDA that recognizes the same language.
    *   For every PDA, there exists a CFG that generates the same language.

*   **PDA Implementation:** A PDA uses a stack to remember information about the structure of the language as it processes the input.  The stack is used to simulate the derivation process of the CFG.

*   **Conversion:** There are algorithms to convert CFGs to PDAs and vice versa.  The conversion from CFG to PDA is relatively straightforward and intuitive.

### Practice Questions/Exercises:

1.  **Design a CFG for the language `L = {0^n 1^m | n >= m >= 0}`**
2.  **Design a CFG for the language of all strings over {a, b} that contain at least one 'a'.**
3.  **Design a CFG for the language of all strings of balanced brackets of two types: `()` and `[]`.**
4.  **Determine if the following grammar is ambiguous. If so, provide a string that demonstrates the ambiguity.**

    ```
    S -> AB
    A -> aA | ε
    B -> bB | ε
    ```

### Answers:

1.  **`L = {0^n 1^m | n >= m >= 0}`**

    `G = (V, T, P, S)` where:

    *   `V = {S, A}`
    *   `T = {0, 1}`
    *   `P = {S -> 0S | 0A, A -> 0A1 | ε}`
    *   `S` is the start variable.

2.  **All strings over {a, b} that contain at least one 'a'.**

    `G = (V, T, P, S)` where:

    *   `V = {S, A, B}`
    *   `T = {a, b}`
    *   `P = {S -> ASA, A -> a, A -> b, B ->b, B -> a}`
    *   `S` is the start variable.
    *Another Solution*
     `G = (V, T, P, S)` where:

    *   `V = {S, A}`
    *   `T = {a, b}`
    *   `P = {S -> ASB, S-> BSA, B ->a, A -> b}`
    *   `S` is the start variable.

    *Alternative Solution*:

    `G = (V, T, P, S)` where:

    *   `V = {S}`
    *   `T = {a, b}`
    *   `P = {S -> aA | bS | a, A -> aA | bA | a | b}`
    *   `S` is the start variable.  (Or, more concisely, `P = {S -> aA | a, A -> aA | bA | b}`. Note the removal of `bS`.

3.  **Balanced brackets of two types: `()` and `[]`**

    `G = (V, T, P, S)` where:

    *   `V = {S}`
    *   `T = { (, ), [, ] }`
    *   `P = {S -> (S), S -> [S], S -> SS, S -> ε}`
    *   `S` is the start variable.

4.  **Ambiguity Check:**

    The grammar is ambiguous.  The string `ε` (the empty string) has two derivations:

    *   `S => AB => εB => εε => ε`
    *   `S => AB => Aε => εε => ε`

    While these produce the same string, they involve different derivation sequences, thus demonstrating ambiguity.  Note that this grammar actually generates `L = {a^n b^m | n, m >= 0}`, and a less ambiguous grammar for the same language is `S -> aS | Sb | ε`.

**Important Points to Remember:**

*   CFGs are more powerful than regular expressions.
*   Designing CFGs requires understanding the recursive structure of the language.
*   Ambiguity can cause problems in parsing.  Strive to design unambiguous grammars where possible (especially for programming languages).
*   CFGs and PDAs are equivalent.
*   Simplifying CFGs can make them easier to work with.
*   Practice, practice, practice!  The more you design CFGs, the better you'll become at it.
