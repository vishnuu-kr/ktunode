# Digital Forensics: Module 2 - Windows Forensics: Event Logs

## 1. Introduction to Windows Event Logs

### Key Concepts & Definitions

*   **Event Log:** A record of events occurring on a Windows operating system. These events can range from system startup and shutdown to application errors, security breaches, and user activity.
*   **Event Viewer:** A graphical tool in Windows that allows users to view, filter, and manage event logs.
*   **Event ID:** A unique numerical identifier assigned to each type of event. This helps in categorizing and identifying specific events.
*   **Source:** The application or component that generated the event (e.g., "Security," "System," "Application").
*   **Level:** The severity of the event (e.g., Information, Warning, Error, Critical, Success Audit, Failure Audit).
*   **User:** The user account associated with the event.
*   **Computer:** The name of the computer where the event occurred.
*   **Date and Time:** The timestamp of when the event occurred.
*   **Event Data:** Additional details about the event, which can include specific information relevant to the event type.

### Purpose of Event Logs in Digital Forensics

*   **Reconstructing Activity:** Event logs provide a chronological record of system and user actions, crucial for understanding what happened during an incident.
*   **Identifying Malicious Activity:** Security logs, in particular, can reveal attempted or successful unauthorized access, malware execution, and system modifications.
*   **Troubleshooting and Diagnosis:** Event logs help identify the root cause of system failures, application errors, and performance issues.
*   **Compliance and Auditing:** Many regulations require organizations to maintain audit trails of system activity, which event logs facilitate.
*   **Evidence Preservation:** Understanding how to properly collect and preserve event logs is vital to ensure their integrity as digital evidence.

### Types of Windows Event Logs

Windows operating systems typically have several standard event logs. The most important for forensic analysis are:

*   **Application Log:**
    *   **Description:** Records events logged by Windows applications. This includes errors, warnings, and information messages generated by software installed on the system.
    *   **Forensic Relevance:** Can reveal application crashes, failed installations, malware attempting to compromise specific applications, or application-specific activities.
    *   **Example Event IDs:**
        *   `1000`: Application Error (e.g., an application crashed)
        *   `1102`: The audit log was cleared (can be suspicious if done by an attacker)

*   **Security Log:**
    *   **Description:** Records security-related events, such as login attempts (successful and failed), resource access, privilege use, and system policy changes. This log requires auditing to be enabled for specific events.
    *   **Forensic Relevance:** Essential for detecting unauthorized access, brute-force attacks, privilege escalation, policy violations, and data exfiltration attempts.
    *   **Example Event IDs:**
        *   `4624`: An account was successfully logged on (useful for tracking user activity).
        *   `4625`: An account failed to log on (indicates potential brute-force attacks).
        *   `4648`: A logon was attempted using explicit credentials (e.g., "Run as different user").
        *   `4720`: A user account was created.
        *   `4726`: A user account was deleted.
        *   `5140`: A network share object was accessed.

*   **System Log:**
    *   **Description:** Records events logged by Windows system components. This includes driver failures, hardware malfunctions, operating system errors, and system startup/shutdown events.
    *   **Forensic Relevance:** Can help identify hardware failures, operating system instability, unexpected system reboots, and potential malware impacting system services.
    *   **Example Event IDs:**
        *   `6005`: The event log service was started (indicates system startup).
        *   `6006`: The event log service was stopped (indicates system shutdown).
        *   `7036`: The service entered the running state.
        *   `7045`: A service was installed in the system.

*   **Setup Log (Less Common in modern Windows for direct user access):**
    *   **Description:** Records events related to the installation of the operating system and some Windows updates.
    *   **Forensic Relevance:** Can provide information about when the system was initially set up or when significant updates occurred, which might be relevant for establishing a timeline.

*   **Forwarded Events Log:**
    *   **Description:** This log is used when an administrator configures computers to forward events to a central collector.
    *   **Forensic Relevance:** Crucial if the investigation involves multiple systems and a centralized logging infrastructure.

### Newer Event Log Architectures (Windows Vista and later)

*   **Windows Event Collector (WEC):** A service that collects events from various sources.
*   **Event Log Channels:** Event logs are organized into channels rather than just the classic logs. These channels can be more granular and are often XML-based.
    *   **Microsoft-Windows-Security-Auditing:** Replaces the traditional Security log.
    *   **Microsoft-Windows-System:** Replaces the traditional System log.
    *   **Microsoft-Windows-Application-Experience:** Records application compatibility information.
    *   **Microsoft-Windows-TaskScheduler:** Logs Task Scheduler events.
    *   **Microsoft-Windows-PowerShell:** Records PowerShell activity, which is highly valuable for detecting advanced attacks.

## 2. Accessing and Navigating Event Logs

### Using Event Viewer (GUI)

*   **Opening Event Viewer:**
    *   Search for "Event Viewer" in the Start Menu.
    *   Run `eventvwr.msc`.

*   **Navigating the Tree:**
    *   Expand "Windows Logs" to access the Application, Security, System, Setup, and Forwarded Events logs.
    *   Expand "Applications and Services Logs" for more specific logs (e.g., Microsoft, Security, System).

*   **Viewing Events:**
    *   Click on a specific log to display its events in the central pane.
    *   Each event is displayed with columns for Date and Time, Source, Event ID, Level, User, and Computer.

*   **Filtering Events:**
    *   **Why filter?** Event logs can contain thousands or millions of events, making manual review impractical. Filtering helps narrow down the search to relevant events.
    *   **How to filter:**
        1.  Right-click on the desired log.
        2.  Select "Filter Current Log..."
        3.  **Filter by:**
            *   **Logged:** Date/time range.
            *   **Event IDs:** Specify specific Event IDs (e.g., `4624, 4625`).
            *   **Level:** Select desired severity levels.
            *   **User:** Filter by specific user accounts.
            *   **Keywords:** Filter by specific keywords (e.g., "failed," "error," "created").
            *   **Task Category:** Filter by specific categories of events (e.g., "Logon/Logoff," "System Events").

*   **Finding Specific Events:**
    *   Use the "Find" feature (Ctrl+F) within a log to search for keywords or Event IDs.

### Using Command-Line Tools

*   **`wevtutil`:** A powerful command-line utility for managing event logs.
    *   **Viewing logs:** `wevtutil qe <LogName>` (e.g., `wevtutil qe System`)
    *   **Filtering logs (using XPath queries):** This is more advanced but essential for automation and precise searching.
        *   `wevtutil qe System /q:"*[System[(EventID=6005)]]" /f:text` (Queries for Event ID 6005 in the System log)
        *   `wevtutil qe Security /q:"*[System[EventRecordID>=1000 and EventRecordID<=2000]]" /f:text` (Queries for Event IDs between 1000 and 2000 in the Security log)
    *   **Exporting logs:** `wevtutil epl <LogName> <FilePath.evtx>` (e.g., `wevtutil epl System C:\Logs\System.evtx`)
    *   **Clearing logs:** `wevtutil cl <LogName>` (USE WITH CAUTION! This is destructive and should only be done if you know what you are doing and have already backed up the logs).

*   **`Get-WinEvent` (PowerShell):** A more modern and flexible cmdlet for querying event logs.
    *   **Viewing logs:** `Get-WinEvent -LogName System`
    *   **Filtering logs:**
        *   `Get-WinEvent -LogName Security | Where-Object {$_.Id -eq 4624}` (Get successful logons)
        *   `Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625}` (Get failed logons using a hash table for efficient filtering)
        *   `Get-WinEvent -FilterXml '<QueryList><Query Id="0" Path="Security"><Select Path="Microsoft-Windows-Security-Auditing/Audit Failure">*[System[(EventID=4625)]]</Select></Query></QueryList>'` (Using XPath via XML)
    *   **Exporting logs:** `Get-WinEvent -LogName System | Export-Csv -Path C:\Logs\System.csv -NoTypeInformation`

## 3. Forensic Considerations for Event Logs

### Log Clearing and Tampering

*   **Importance:** Attackers often try to clear or modify event logs to hide their tracks.
*   **Detection:**
    *   **Event ID 1102:** "The audit log was cleared." This is a critical event to monitor. If found, it strongly suggests an attempt to cover up activity.
    *   **System Log for Log Service Stop:** Look for unexpected stops of the "Eventlog" service (`Event ID 7036` with a stop state).
    *   **Log File Integrity:** Compare the current log files with known good copies or use hashing techniques to detect modifications (though direct modification of `.evtx` files is difficult without specific tools).
    *   **Disabled Auditing:** An attacker might disable auditing for certain events to prevent them from being logged.
*   **Best Practices:**
    *   **Regular Backups:** Regularly back up event logs to a separate, secure location.
    *   **Centralized Logging:** Forward logs to a secure, centralized logging server (e.g., SIEM) that is not directly accessible by the compromised system.
    *   **Read-Only Access:** Ensure that forensic investigators have read-only access to the original log files to prevent accidental modification.

### Log Size and Overflow

*   **How it works:** Event logs have a configurable maximum size. When the log reaches its maximum and is set to "Overwrite events as needed" or "Overwrite events if they are older than X days," older events are discarded to make space for new ones.
*   **Forensic Impact:** If a log file overflows, crucial historical data might be lost.
*   **Mitigation:**
    *   **Increase Log Size:** Configure log files with larger maximum sizes, especially on critical servers.
    *   **Set to "Do not overwrite events (clear log manually)":** This prevents automatic data loss but requires manual intervention to clear logs. For forensics, it's often better to use "Overwrite events as needed" and ensure timely collection.
    *   **Regular Collection:** Collect logs frequently to prevent them from filling up and overwriting important data.

### Enabling Auditing

*   **Default Auditing:** Not all events are audited by default. To gain valuable forensic insights, specific auditing policies must be enabled.
*   **Local Security Policy:**
    1.  Run `secpol.msc`.
    2.  Navigate to `Security Settings` -> `Advanced Audit Policy Configuration` -> `Audit Policies`.
    3.  **Key Policies to Consider Enabling:**
        *   **Account Logon:** Audit Logon Events (Success, Failure)
        *   **Account Management:** Audit User Account Management (Success, Failure)
        *   **Logon/Logoff:** Audit Logon Events (Success, Failure), Audit Logoff (Success)
        *   **Object Access:** Audit File System, Audit Registry (if critical data is being protected)
        *   **Policy Change:** Audit Audit Policy Change (Success, Failure)
        *   **System:** Audit System Events (Success, Failure)
        *   **Privilege Use:** Audit Sensitive Privilege Use (Success, Failure)
*   **Group Policy:** For domain environments, audit policies are best managed through Group Policy.
*   **Forensic Importance:** Without proper auditing, the Security log will have limited value for detecting many types of malicious activity.

### Timeline Analysis

*   **Crucial Element:** Establishing a precise timeline of events is fundamental to forensic investigations.
*   **Using Event Logs for Timeline:**
    *   **System Startup/Shutdown:** Event IDs `6005` and `6006` in the System log.
    *   **Logons/Logoffs:** Event IDs `4624` (successful logon), `4634` (logoff), `4647` (user initiated logoff) in the Security log.
    *   **Process Creation/Termination:** Event ID `4688` (Process Creation) requires auditing to be enabled. This is extremely valuable for tracking program execution.
    *   **File Access:** Event ID `4663` (Attempted to access an object) requires specific object access auditing to be enabled for files and folders.
    *   **Registry Changes:** Similar to file access, specific registry key auditing can capture modifications.
*   **Time Synchronization:** Ensure that system clocks are synchronized across all relevant machines. Network Time Protocol (NTP) is crucial for this. If time is not synchronized, correlating events across multiple systems becomes very difficult.
*   **Time Zones:** Be mindful of time zones when analyzing logs, especially if dealing with distributed systems or remote access.

### Understanding Event Data

*   **Details are Key:** The "Details" tab in Event Viewer provides rich information about the event.
*   **Common Data Fields:**
    *   **Logon Type:** (e.g., Interactive, RemoteInteractive, Network, Batch, Service) helps differentiate how a user logged in.
    *   **Subject:** The account and process that initiated the action.
    *   **Target:** The account or object that was acted upon.
    *   **Process Information:** Details about the process that generated the event (e.g., Process ID, Image Path).
    *   **Network Information:** Source and destination IP addresses and ports for network-related events.

## 4. Advanced Topics and Best Practices

### PowerShell Logging

*   **PowerShell's Role:** PowerShell is a powerful scripting language widely used for system administration and, unfortunately, by attackers for malicious purposes.
*   **Key PowerShell Logging Features:**
    *   **Module Logging:** Logs cmdlets, module names, and parameter values. (Event ID `4103` in `Microsoft-Windows-PowerShell/ModuleLog`)
    *   **Script Block Logging:** Logs the actual content of scripts executed by PowerShell. This is extremely valuable for detecting malicious scripts. (Event ID `4104` in `Microsoft-Windows-PowerShell/ScriptBlockLog`)
    *   **Transcription Logging:** Records the entire input and output of PowerShell sessions to text files.
*   **Enabling:** These settings can be configured via Group Policy (`Computer Configuration` -> `Policies` -> `Administrative Templates` -> `Windows Components` -> `Windows PowerShell`).
*   **Forensic Value:** Enables the forensic investigator to see exactly what commands were executed, making it a powerful tool against fileless malware and advanced persistent threats (APTs).

### Sysmon

*   **What is Sysmon?** A free Windows system service and device driver that monitors and logs system activity to the Windows event log. It provides much more granular detail than native Windows logging.
*   **Key Sysmon Events:**
    *   **Event ID 1: Process Creation:** Logs the parent process, command line, hash of the executable, and more.
    *   **Event ID 3: Network Connection:** Logs source/destination IP, port, process that made the connection.
    *   **Event ID 4: Sysmon Service State Change:** Logs changes to the Sysmon service itself.
    *   **Event ID 7: Image Load:** Logs DLLs loaded by processes.
    *   **Event ID 11: File Creation:** Logs when new files are created.
    *   **Event ID 12, 13, 14: Registry Events:** Logs registry key/value creation, deletion, and modification.
    *   **Event ID 15: FileStream Create:** Logs when a file is created with specific file stream metadata.
    *   **Event ID 17, 18: Pipe Create/Connect:** Logs named pipe activity, often used for inter-process communication or lateral movement.
    *   **Event ID 19, 20, 21: WMI Activity:** Logs WMI event filter creation, consumer creation, and event consumer binding, common for persistence and lateral movement.
*   **Configuration:** Sysmon is configured using an XML file. Creating an effective configuration requires careful planning and tuning. Microsoft provides example configuration files.
*   **Forensic Value:** Sysmon is an invaluable tool for detecting advanced threats, understanding malware behavior, and reconstructing complex attack chains.

### Log Management and Retention Policies

*   **Importance:** Establishing clear policies for how long logs are retained and how they are managed is crucial for both operational efficiency and legal/compliance requirements.
*   **Key Aspects:**
    *   **Retention Period:** How long logs should be kept (e.g., 90 days, 1 year). This depends on legal, regulatory, and business needs.
    *   **Storage Location:** Where logs are stored (e.g., local, network share, SIEM).
    *   **Security:** Ensuring logs are stored securely and protected from unauthorized access or modification.
    *   **Archiving:** Developing a process for archiving older logs if they need to be retained longer than active logs.
    *   **Disposal:** Securely disposing of logs that have passed their retention period.

### Tools for Event Log Analysis

*   **Event Viewer (Built-in):** Good for initial browsing and simple filtering.
*   **`wevtutil` (Built-in):** Essential for scripting and exporting.
*   **PowerShell (`Get-WinEvent`):** Powerful for complex queries and automation.
*   **Third-Party SIEM/Log Management Tools:** Splunk, ELK Stack (Elasticsearch, Logstash, Kibana), QRadar, etc. These are essential for managing and analyzing large volumes of logs from multiple sources in real-time.
*   **Forensic Suites:** EnCase, FTK, Autopsy, X-Ways Forensics often have built-in capabilities to parse and analyze Windows event logs from disk images.
*   **Specialized Log Parsers:** Tools like LogParser from Microsoft can parse various log formats, including event logs, using SQL-like queries.

**Question 6: Practical Exercise (Conceptual)**
Imagine you are investigating a potential insider threat. You suspect an employee has been accessing sensitive files they shouldn't. Describe the steps you would take using Event Viewer to investigate this, including the logs you would check and the filters you might apply.

**Conceptual Answer:**
1.  **Identify the User:** First, I would need to know the username of the employee in question.
2.  **Check Security Log:** The primary log to examine would be the **Security Log**.
3.  **Enable Auditing (if necessary):** If auditing for object access (specifically file access) wasn't enabled, the Security log might be insufficient. In a real investigation, I'd check if auditing for "File System" access was previously enabled under "Advanced Audit Policy Configuration."
4.  **Filtering:**
    *   **Event IDs:** I would filter the Security log for specific event IDs related to file access:
        *   `4663`: An attempt was made to access an object (This is the most critical for file access, but requires object access auditing to be configured for specific files/folders).
        *   `5140`: A network share object was accessed (if the files were on a network share).
    *   **User:** I would filter the results to only show events generated by the suspect employee's username.
    *   **Timeframe:** I would filter by the suspected timeframe of the activity.
5.  **Examine Event Data:** For each relevant event, I would look at the "Details" tab to identify:
    *   The specific file or object that was accessed.
    *   The type of access (e.g., Read, Write, Delete).
    *   The process that performed the action.
6.  **Cross-reference with other logs:** If the suspected activity involved executing programs or system modifications, I would also check the **System Log** (for unexpected reboots or service issues) and the **Application Log** (for application-specific errors or behavior). If PowerShell was involved, I'd look for events in the PowerShell logs (if enabled).

**Question 7: Practical Exercise (PowerShell)**
Write a PowerShell command to find all failed logon attempts (Event ID 4625) in the Security log that occurred in the last 24 hours.

**Answer:**
```powershell
Get-WinEvent -LogName Security -FilterHashtable @{
    LogName = 'Security'
    ID      = 4625
    StartTime = (Get-Date).AddDays(-1)
} | Format-Table TimeCreated, @{Name="User";Expression={$_.Properties[1].Value}}, @{Name="LogonType";Expression={$_.Properties[8].Value}}, @{Name="Status";Expression={$_.Properties[17].Value}}
```

*Explanation of the PowerShell command:*
*   `Get-WinEvent -LogName Security`: Retrieves events from the Security log.
*   `-FilterHashtable`: Uses a hashtable for efficient filtering.
*   `LogName = 'Security'`: Specifies the Security log.
*   `ID = 4625`: Filters for failed logon events.
*   `StartTime = (Get-Date).AddDays(-1)`: Sets the start time to 24 hours ago.
*   `| Format-Table ...`: Formats the output to display relevant columns like Time Created, User, Logon Type, and Status. The properties array indices (`[1]`, `[8]`, `[17]`) correspond to specific data fields within the Event Record for Event ID 4625.

## 6. Important Points to Remember

*   **Auditing is Key:** Default auditing settings are often insufficient for forensic investigations. Proactive configuration of audit policies is crucial.
*   **Timestamps Matter:** Ensure time synchronization and understand time zones when analyzing logs across multiple systems.
*   **Log Clearing is Suspicious:** Event ID `1102` is a major red flag indicating potential tampering.
*   **Log Size Limits:** Be aware of log size limitations and the "overwrite" settings, as they can lead to data loss.
*   **Centralized Logging:** For robust security and forensics, forward logs to a secure, central location.
*   **PowerShell and Sysmon:** Leverage PowerShell logging and Sysmon for deeper visibility into system activity and advanced threat detection.
*   **Tools:** Understand and utilize both built-in Windows tools (Event Viewer, `wevtutil`, PowerShell) and specialized forensic tools.
*   **Integrity:** Always ensure the integrity of log files is maintained during collection and analysis. Work on copies when possible.
*   **Context is Everything:** Individual events are important, but understanding their context within a larger timeline and sequence of events is vital for a successful investigation.
