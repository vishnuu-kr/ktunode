# Digital Forensics: Module 1 - Introduction to Digital Forensics

## Topic: EXT3 File System

This topic provides an introduction to the EXT3 file system, a widely used journaling file system in Linux-based operating systems, and its relevance within the field of digital forensics.

---

Upon completion of this topic, you should be able to:

*   **LO2:** Identify key data structures and their forensic significance within EXT3.
*   **LO3:** Explain the concept of journaling in EXT3 and its impact on forensic investigations.
*   **LO4:** Recognize the forensic challenges and considerations specific to the EXT3 file system.

### **1. Introduction to File Systems**

*   **Definition:** A file system is a method and data structure that an operating system uses to control how data is stored and retrieved. It manages files, directories, and their metadata.
*   **Importance in Digital Forensics:** File systems are crucial because they organize all the data on a storage device. Understanding the file system allows investigators to locate, interpret, and recover evidence.

---

### **2. The EXT3 File System**

*   **Overview:**
    *   EXT3 (Fourth Extended Filesystem) is a journaling file system commonly used in Linux.
    *   It was an evolution of EXT2, introducing journaling to improve reliability and reduce recovery time after system crashes.
    *   It supports file sizes up to 2 TB and volume sizes up to 16 TB.
*   **Key Features:**
    *   **Journaling:** The most significant addition over EXT2.
    *   **Extents (Optional):** Improves performance for large files by allocating contiguous blocks.
    *   **H-tree Indexing:** Optimizes directory lookups.

---

### **3. Basic Structure and Organization (LO1)**

*   **Superblock:**
    *   **Definition:** The first block on the filesystem that contains critical metadata about the filesystem's structure and integrity.
    *   **Forensic Significance:** Contains information like the total number of inodes, blocks, block size, and pointers to important data structures. Multiple copies of the superblock are typically found at specific offsets for redundancy.
    *   **Example:** A corrupted superblock can make the entire filesystem inaccessible. Investigators often look for backup superblocks.
*   **Inode Table (Inode Bitmap and Inodes):**
    *   **Definition:** A table containing "inodes" (index nodes), which are data structures that store metadata about each file or directory. Each inode has a unique number.
    *   **Inode Bitmap:** A bit array where each bit corresponds to an inode. A '1' indicates the inode is in use, and a '0' indicates it's free.
    *   **Inode Structure:** Contains:
        *   File type (regular file, directory, symbolic link, etc.)
        *   Permissions
        *   Owner and group IDs
        *   File size
        *   Timestamps (atime, mtime, ctime, dtime)
        *   **Pointers to Data Blocks:** The most crucial part for data retrieval.
    *   **Forensic Significance:** Inodes are the gateway to a file's data. The `dtime` (deletion time) field in an inode can indicate if a file has been deleted. Even if data blocks are overwritten, the inode might still exist, offering clues.
*   **Data Block Groups:**
    *   **Definition:** EXT3 divides the disk into block groups, each containing its own superblock, group descriptor table, block bitmap, inode bitmap, inode table, and data blocks.
    *   **Forensic Significance:** This segmentation helps with performance and recovery. When examining a disk image, investigators need to understand how data is distributed across these groups.
*   **Directory Entries:**
    *   **Definition:** Directories in EXT3 are essentially special files that map human-readable filenames to inode numbers.
    *   **Structure:** Each directory entry contains:
        *   Inode number
        *   Record length (the total size of the directory entry)
        *   Name length
        *   File type
        *   Filename
    *   **Forensic Significance:** Crucial for navigating the filesystem and reconstructing the directory structure. When a file is deleted, its directory entry is typically marked as unused, but the entry itself might remain until overwritten.

### **5. Journaling in EXT3 (LO3)**

*   **Concept:**
    *   Before making changes to the main file system structures (metadata like inode updates, directory changes), EXT3 writes a description of these changes to a dedicated journal area.
    *   Once the journal entry is safely written, the changes are applied to the actual filesystem.
    *   If a system crash occurs mid-operation, upon reboot, the system checks the journal. If pending operations are found, they are either committed or rolled back to restore filesystem consistency.
*   **Journaling Modes:**
    *   **`data=journal` (Default):** Both file data and metadata are written to the journal. Provides the highest level of data integrity but can be slower.
    *   **`data=ordered`:** Only metadata is journaled. File data is written to the main filesystem *before* its metadata is journaled. This ensures data blocks written correspond to valid metadata.
    *   **`data=writeback`:** Only metadata is journaled. File data can be written to the main filesystem *after* its metadata is journaled. Fastest but offers no guarantee that file data written corresponds to the journaled metadata, potentially leading to data corruption if not handled carefully.
*   **Forensic Significance:**
    *   **Reconstructing Events:** The journal provides a chronological record of metadata changes, allowing investigators to reconstruct file creation, modification, and deletion events.
    *   **Recovering Deleted Files:** Even if a file's inode and data blocks are marked as free, the journal might contain entries related to the file's creation or modification, providing valuable clues.
    *   **Filesystem State:** The journal can help determine the state of the filesystem before and after a crash or specific operation.
    *   **Challenges:** The journal can be large and complex to parse. Different journaling modes can affect the information available.

### **6. Forensic Challenges and Considerations (LO4)**

*   **File Deletion:**
    *   When a file is deleted in EXT3, its directory entry is typically marked as unused, and its inode is deallocated.
    *   Crucially, the actual data blocks are *not* immediately erased. They are marked as free and can be overwritten by new data.
    *   **Forensic Implication:** Recovering deleted files relies on finding the inode and its associated data blocks before they are overwritten.
*   **Fragmentation:**
    *   Files can become fragmented, meaning their data blocks are not stored contiguously on the disk.
    *   **Forensic Implication:** Analyzing fragmented files requires piecing together data blocks from potentially scattered locations, making recovery more complex.
*   **Journal Corruption/Overwriting:**
    *   While journaling enhances reliability, the journal itself can be subject to corruption or overwriting, especially in `writeback` mode or with aggressive journaling activity.
    *   **Forensic Implication:** A damaged journal can hinder the reconstruction of events.
*   **Timestamps:**
    *   **`atime` (access time):** Updated when a file is read. Can be disabled for performance.
    *   **`mtime` (modification time):** Updated when the file's content is modified.
    *   **`ctime` (change time):** Updated when the file's metadata (permissions, ownership, etc.) or content is changed.
    *   **`dtime` (deletion time):** Set when a file is deleted. Crucial for identifying deleted files, but it's only set when the inode is deallocated.
    *   **Forensic Implication:** Timestamps are vital for establishing timelines and reconstructing events. However, `atime` updates can be disabled, and `ctime` can be modified programmatically, requiring careful interpretation. The presence of a `dtime` value is a strong indicator of deletion.
*   **Tool Dependency:**
    *   Forensic analysis of EXT3 often relies on specialized tools (e.g., `extundelete`, `scalpel`, Sleuth Kit's `fls` and `icat`) that understand its structure.
    *   **Forensic Implication:** Investigators must be proficient with these tools and understand their limitations.

### **7. Techniques for Recovery and Analysis (LO5)**

*   **Disk Imaging:**
    *   **Process:** Create a bit-by-bit copy (image) of the original storage media.
    *   **Importance:** Preserves the integrity of the original evidence and allows for multiple analyses without risking damage to the source.
*   **Mounting Read-Only:**
    *   **Process:** Mount the filesystem image in a read-only mode to prevent any accidental modifications.
    *   **Importance:** Adheres to the principle of preserving evidence integrity.
*   **File Carving:**
    *   **Definition:** The process of recovering files based on their headers, footers, and internal structure, regardless of filesystem metadata.
    *   **Tools:** `scalpel`, `foremost`.
    *   **Use Case:** Effective for recovering files where filesystem metadata is lost or damaged, or for files that were deleted and their data blocks are still intact.
*   **Inode Table Analysis:**
    *   **Process:** Examining the inode table to identify allocated and deallocated inodes. Look for inodes with a `dtime` value.
    *   **Tools:** Sleuth Kit (`fls`, `istat`).
    *   **Use Case:** Identifying potential deleted files by their metadata.
*   **Data Block Recovery:**
    *   **Process:** If an inode with a `dtime` is found, use the inode's data block pointers to recover the file's content.
    *   **Tools:** Sleuth Kit (`icat`), `extundelete`.
    *   **Use Case:** Recovering the actual content of deleted files.
*   **Journal Analysis:**
    *   **Process:** Parsing the journal to reconstruct the sequence of metadata operations.
    *   **Tools:** Specialized journal parsing tools.
    *   **Use Case:** Understanding the timeline of events and potentially recovering data that wasn't fully committed to the main filesystem.

*   **A.** The data blocks are immediately erased.
*   **B.** The data blocks are marked as free and can be overwritten.
*   **C.** The data blocks are moved to a "recycle bin" directory.
*   **D.** The data blocks are encrypted.

*   **A.** To improve file read speeds.
*   **B.** To record metadata changes before they are applied to the main filesystem, ensuring consistency.
*   **C.** To compress files automatically.
*   **D.** To manage user permissions.

**Question 5 (Practical Exercise):** Imagine you are analyzing an EXT3 disk image. You find an inode with a `dtime` value of `1678886400` (Unix timestamp for March 15, 2023, 12:00:00 PM UTC). What does this tell you about the file associated with this inode? How would you proceed to recover its content?

---

### **Answers to Practice Questions**

**Answer 1:** **B.** Introduction of journaling. Journaling significantly improves reliability and helps in recovering from system crashes, which is a crucial aspect for forensic investigations to maintain data integrity.

**Answer 2:** **C.** Inode. The inode is the central data structure storing all metadata about a file, including the critical pointers to its data blocks.

**Answer 3:** **B.** The data blocks are marked as free and can be overwritten. The actual data is not erased until new data overwrites it.

**Answer 4:** **B.** To record metadata changes before they are applied to the main filesystem, ensuring consistency. This process allows for quick recovery of filesystem integrity after an unexpected shutdown.

**Answer 5 (Practical Exercise):**
*   **What it tells you:** The `dtime` value indicates that the file was deleted on or around March 15, 2023, at 12:00:00 PM UTC. The inode itself has been deallocated, meaning the filesystem considers the file gone.
*   **How to proceed:**
    1.  **Identify the inode number:** This would be found by analyzing the directory entry that pointed to this inode.
    2.  **Examine the inode:** Retrieve the inode's data block pointers.
    3.  **Recover Data Blocks:** Use forensic tools (like Sleuth Kit's `icat` or `extundelete`) to read the data from the blocks pointed to by the inode.
    4.  **Reconstruct the file:** Piece together the recovered data blocks in the correct order to reconstruct the deleted file's content.
    5.  **Consider Journal:** Check the EXT3 journal for any entries related to this inode or file that might provide additional context or confirm the deletion event.

### **Important Points to Remember**

*   **Journaling is key:** Understand its modes (`data=journal`, `data=ordered`, `data=writeback`) and how they affect forensics.
*   **Inodes are critical:** They are the gateway to file metadata and data. The `dtime` field is vital for identifying deleted files.
*   **Data blocks are not erased immediately:** This is the fundamental principle behind deleted file recovery.
*   **Timestamps are useful but not infallible:** Be aware of how `atime`, `mtime`, and `ctime` are updated and that they can sometimes be manipulated.
*   **Specialized tools are essential:** Proficiency with tools like The Sleuth Kit is highly recommended for EXT3 analysis.
*   **Preserve evidence integrity:** Always work on a forensic image and mount it read-only.
