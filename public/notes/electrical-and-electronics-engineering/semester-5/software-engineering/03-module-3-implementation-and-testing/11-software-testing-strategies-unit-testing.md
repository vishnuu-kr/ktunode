# Software Engineering: Module 3 - Implementation and Testing

## Unit Testing

### 1. Introduction to Unit Testing

Unit testing is the first level of software testing. It focuses on verifying the smallest testable parts of an application, called units. A unit is typically a function, method, procedure, or a class. The goal is to isolate each unit and test it to ensure it behaves as expected, independent of other parts of the system.

*   **Purpose:** To validate that each unit of the software performs as designed.
*   **Key Principle:** Isolation. Unit tests should not depend on external systems like databases, networks, or file systems.
*   **Who Performs:** Typically performed by developers as they write code.

#### 1.1. Importance of Unit Testing

*   **Early Defect Detection:** Identifies bugs early in the development lifecycle, making them cheaper and easier to fix.
*   **Code Quality Improvement:** Encourages developers to write modular, maintainable, and well-structured code.
*   **Facilitates Refactoring:** Provides a safety net when refactoring or modifying existing code, ensuring that changes haven't broken existing functionality.
*   **Documentation:** Unit tests can serve as a form of executable documentation, demonstrating how a particular unit is intended to be used.
*   **Faster Feedback Loop:** Developers receive immediate feedback on the correctness of their code.

*(Pressman, 8th Ed., Chapter 14: Component Testing; Sommerville, 10th Ed., Chapter 18: Managing and controlling software development)*

#### 1.2. Unit Testing vs. Other Testing Levels

| Testing Level     | Focus                                     | Performed By      | Goal                                                  |
| :---------------- | :---------------------------------------- | :---------------- | :---------------------------------------------------- |
| **Unit Testing**  | Smallest testable parts (functions, methods, classes) | Developers        | Verify individual components work correctly in isolation. |
| Integration Testing | Interaction between units                 | Developers/Testers | Verify interfaces and interactions between modules.     |
| System Testing    | Entire integrated system                  | Independent Testers | Verify the system meets specified requirements.        |
| Acceptance Testing| User satisfaction and business needs      | End-users/Clients | Verify the system is acceptable to the user.          |

*(Sommerville, 10th Ed., Chapter 18: Managing and controlling software development)*

### 2. Key Concepts in Unit Testing

#### 2.1. Test Fixture

A test fixture is a fixed state of a set of objects used as input for tests. It's a collection of items that are initialized before a test runs and cleaned up after it finishes. This ensures that tests are run in a consistent environment.

*   **Setup:** The code that prepares the environment for the test.
*   **Teardown:** The code that cleans up the environment after the test.

**Example:**
In a banking application, a test fixture for a `BankAccount` class might involve creating a `BankAccount` object with an initial balance of $100. The setup would create this object, and the teardown might involve deleting it or resetting its state.

#### 2.2. Test Case

A test case is a set of conditions or variables under which a tester will determine whether a system under test satisfies requirements or works correctly. Each test case includes:
*   **Test Procedure:** Steps to execute.
*   **Input Data:** Data used for execution.
*   **Expected Result:** The anticipated outcome.

**Example:**
For the `BankAccount.deposit(amount)` method:
*   **Test Case 1 (Valid Deposit):**
    *   **Input:** `amount = 50`
    *   **Expected Result:** Balance increases by 50.
*   **Test Case 2 (Zero Deposit):**
    *   **Input:** `amount = 0`
    *   **Expected Result:** Balance remains unchanged.
*   **Test Case 3 (Negative Deposit):**
    *   **Input:** `amount = -20`
    *   **Expected Result:** An exception is thrown (e.g., `IllegalArgumentException`).

#### 2.3. Test Driver

A test driver is a piece of software that calls a unit of work (the code under test) and potentially passes it test data. It's responsible for executing the test cases.

*   **Purpose:** To invoke the unit being tested and to collect/report results.
*   **In Unit Testing:** Often generated by unit testing frameworks.

#### 2.4. Test Stub

A test stub is a dummy piece of code that simulates the behavior of a called module. When testing a unit that depends on other units, stubs are used to provide controlled responses from those dependencies.

*   **Purpose:** To satisfy the dependencies of the unit under test.
*   **Simulates:** The behavior of a lower-level component.

**Example:**
If testing a `PaymentProcessor` class that relies on a `BankService` to authorize payments, a stub for `BankService` could be created to always return `true` for authorization, regardless of the actual bank's state.

#### 2.5. Test Harness

A test harness is a collection of software and test data that facilitates testing a software component by checking that certain functions behave as expected. It includes the test driver, stubs, and other necessary utilities.

*   **Purpose:** To provide a controlled environment for executing unit tests and reporting results.
*   **Includes:** Test drivers, stubs, test execution, and result reporting.

*(Pressman, 8th Ed., Chapter 14: Component Testing)*

### 3. Unit Testing Frameworks

Unit testing frameworks provide a structured way to write and run unit tests. They offer tools for creating test cases, managing fixtures, running tests, and reporting results.

#### 3.1. Common Unit Testing Frameworks

*   **Java:** JUnit, TestNG
*   **Python:** unittest, pytest
*   **C#:** NUnit, MSTest
*   **JavaScript:** Jest, Mocha, Jasmine
*   **C++:** Google Test, CppUnit

#### 3.2. Principles of Using Frameworks

*   **Test Organization:** Frameworks help organize tests into classes and methods.
*   **Assertions:** Provide methods (e.g., `assertEquals`, `assertTrue`, `assertNotNull`) to check if the actual output matches the expected output.
*   **Test Runner:** Executes all defined tests and reports the outcomes (pass/fail).
*   **Setup/Teardown Methods:** Allow defining methods that run before and after each test or test class.

#### 3.3. Example with JUnit (Java)

**Code to be tested (Unit):**

```java
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }

    public int subtract(int a, int b) {
        return a - b;
    }

    public int divide(int a, int b) {
        if (b == 0) {
            throw new IllegalArgumentException("Division by zero is not allowed.");
        }
        return a / b;
    }
}
```

**Unit Test using JUnit:**

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

public class CalculatorTest {

    // Test fixture setup (implicit in this simple case)
    // In more complex scenarios, @BeforeEach would be used

    @Test
    void testAddPositiveNumbers() {
        Calculator calculator = new Calculator();
        int result = calculator.add(5, 3);
        assertEquals(8, result, "5 + 3 should be 8");
    }

    @Test
    void testAddNegativeNumbers() {
        Calculator calculator = new Calculator();
        int result = calculator.subtract(-5, -3);
        assertEquals(-2, result, "-5 - (-3) should be -2");
    }

    @Test
    void testDivideByZero() {
        Calculator calculator = new Calculator();
        // Using assertThrows to check for exceptions
        assertThrows(IllegalArgumentException.class, () -> {
            calculator.divide(10, 0);
        }, "Division by zero should throw IllegalArgumentException");
    }

    @Test
    void testDivideValidNumbers() {
        Calculator calculator = new Calculator();
        int result = calculator.divide(10, 2);
        assertEquals(5, result, "10 / 2 should be 5");
    }

    // Teardown (implicit in this simple case)
    // In more complex scenarios, @AfterEach would be used
}
```

*   `@Test`: Annotation marking a method as a test case.
*   `assertEquals(expected, actual, message)`: Assertion method to check if two values are equal.
*   `assertThrows(exceptionType, executable)`: Assertion method to check if a specific exception is thrown.

*(Pressman, 8th Ed., Chapter 14: Component Testing)*

### 4. Unit Testing Strategies and Techniques

#### 4.1. Black-Box Unit Testing

Treats the unit as a black box, focusing on inputs and outputs without knowledge of the internal code structure.

*   **Techniques:**
    *   **Equivalence Partitioning:** Dividing input data into partitions from which test cases can be derived.
    *   **Boundary Value Analysis (BVA):** Testing at the boundaries of input partitions, as errors often occur at these edges.
    *   **Error Guessing:** Using experience to predict where errors might occur.

**Example (BVA for `divide` method):**
Consider the input `b` for division. If `b` can be any integer:
*   Boundary values: `0`, `1`, `-1`, `Integer.MAX_VALUE`, `Integer.MIN_VALUE`.
*   Tests would focus on `b=0` (already covered), `b=1`, `b=-1`, and potentially values near `Integer.MAX_VALUE` and `Integer.MIN_VALUE` to check for overflow.

#### 4.2. White-Box Unit Testing

Examines the internal logic of the code to design test cases. It requires knowledge of the source code.

*   **Techniques:**
    *   **Statement Coverage:** Every statement in the code is executed at least once.
    *   **Branch Coverage (Decision Coverage):** Every branch (true and false outcomes of conditional statements) is executed at least once.
    *   **Path Coverage:** Every possible path through the code is executed at least once. (Often infeasible for complex code).
    *   **Condition Coverage:** Each boolean sub-expression within a condition is evaluated to both true and false.
    *   **Multiple Condition Coverage:** All possible combinations of boolean sub-expressions are tested.

**Example (Statement Coverage for `divide` method):**
To achieve statement coverage for the `divide` method:
1.  Call `divide(10, 2)`: This executes `return a / b;`.
2.  Call `divide(10, 0)`: This executes `if (b == 0)` (true) and `throw new IllegalArgumentException(...)`.

**Example (Branch Coverage for `divide` method):**
To achieve branch coverage:
1.  Call `divide(10, 2)`: `if (b == 0)` is false. This covers the "false" branch. The `return a / b;` statement is also covered.
2.  Call `divide(10, 0)`: `if (b == 0)` is true. This covers the "true" branch and the exception.

#### 4.3. Test-Driven Development (TDD)

A development practice where tests are written *before* the code that implements them. The cycle is:
1.  **Red:** Write a failing unit test for a new feature.
2.  **Green:** Write the minimum amount of code necessary to make the test pass.
3.  **Refactor:** Improve the code while ensuring all tests still pass.

*   **Benefits:** Encourages modular design, reduces defects, provides clear requirements, acts as living documentation.
*   **Alignment:** Closely tied to Agile methodologies (CO2).

*(Poppendieck & Poppendieck, Implementing Lean Software Development; Anderson, Agile Management for Software Engineering)*

#### 4.4. Mocking and Stubbing

When a unit depends on other components that are complex, unavailable, or unstable, these dependencies can be replaced with **mocks** or **stubs**.

*   **Stubs:** Provide predefined responses to method calls. They are simpler and focus on returning specific values.
*   **Mocks:** More sophisticated. They not only return predefined responses but also verify that specific methods were called on them with expected arguments and in a specific order. They verify the *interaction* between the unit under test and its dependencies.

**Example (Mocking `BankService` for `PaymentProcessor`):**

```java
// Assuming PaymentProcessor uses a BankService dependency

public class PaymentProcessor {
    private BankService bankService;

    public PaymentProcessor(BankService bankService) {
        this.bankService = bankService;
    }

    public boolean processPayment(double amount) {
        if (bankService.authorizePayment(amount)) {
            // Perform actual payment processing
            return true;
        }
        return false;
    }
}

// Mocking framework like Mockito (Java)

// In the test:
@Test
void testProcessPayment_successfulAuthorization() {
    BankService mockBankService = Mockito.mock(BankService.class);
    PaymentProcessor processor = new PaymentProcessor(mockBankService);

    // Stubbing: When authorizePayment is called with 100.0, return true
    Mockito.when(mockBankService.authorizePayment(100.0)).thenReturn(true);

    assertTrue(processor.processPayment(100.0));

    // Verifying interaction: Ensure authorizePayment was called exactly once with 100.0
    Mockito.verify(mockBankService, Mockito.times(1)).authorizePayment(100.0);
}

@Test
void testProcessPayment_failedAuthorization() {
    BankService mockBankService = Mockito.mock(BankService.class);
    PaymentProcessor processor = new PaymentProcessor(mockBankService);

    // Stubbing: When authorizePayment is called with 50.0, return false
    Mockito.when(mockBankService.authorizePayment(50.0)).thenReturn(false);

    assertFalse(processor.processPayment(50.0));

    // Verifying interaction
    Mockito.verify(mockBankService, Mockito.times(1)).authorizePayment(50.0);
}
```

*(Pressman, 8th Ed., Chapter 14: Component Testing)*

### 5. Writing Effective Unit Tests

*   **Readability:** Tests should be clear and easy to understand. Use descriptive names for test methods.
*   **Maintainability:** Tests should be easy to update as the code changes. Avoid overly complex test logic.
*   **Repeatability:** Tests should produce the same results every time they are run. Avoid dependencies on external factors like time or random numbers.
*   **Independence:** Each test should be independent of others. The order of execution should not matter.
*   **Speed:** Unit tests should run quickly to provide fast feedback.
*   **Focus:** Each test should focus on testing one specific aspect or behavior of the unit.

### Answers

**Answer 1:** c) To validate the smallest testable parts of an application in isolation.

**Answer 2:** b) Dependency on external systems. (Good unit tests should be isolated.)

**Answer 3:** b) 1, 3, 2 (Red, Green, Refactor)

**Answer 4:** b) Test stub (or a mock object, which also serves this purpose and more)

**Answer 5:**

**Statement Coverage:** Every executable statement in the source code is executed at least once.
**Branch Coverage (Decision Coverage):** For every decision point (e.g., `if`, `while`, `for` statements), all possible outcomes (branches) are executed at least once.

**Code Snippet:**

```java
public int checkValue(int x) {
    int result = 0;
    if (x > 10) {
        result = x * 2; // Statement A
    } else {
        result = x + 5; // Statement B
    }
    return result; // Statement C
}
```

**Achieving Statement Coverage:**
*   Call `checkValue(15)`: Executes Statement A and Statement C.
*   Call `checkValue(5)`: Executes Statement B and Statement C.
    *   Now all statements (A, B, C) have been executed.

**Achieving Branch Coverage:**
*   Call `checkValue(15)`: This executes the `if (x > 10)` condition as `true`, covering the `result = x * 2;` branch (Statement A) and Statement C.
*   Call `checkValue(5)`: This executes the `if (x > 10)` condition as `false`, covering the `result = x + 5;` branch (Statement B) and Statement C.
    *   Now both the `true` and `false` branches of the `if` statement have been covered, along with all statements.

### Important Points to Remember

*   **Isolation is Key:** Unit tests must be independent of other units and external systems.
*   **Developers Own Unit Tests:** They are the primary responsibility of the development team.
*   **Early Feedback:** Unit tests provide the quickest feedback loop for developers.
*   **TDD:** A powerful methodology that integrates testing into the development process from the start.
*   **Frameworks:** Leverage unit testing frameworks to streamline test creation and execution.
*   **Mocks/Stubs:** Essential for managing dependencies in unit testing.
*   **Coverage:** Aim for high coverage (statement, branch) but understand that 100% path coverage is often impractical. Focus on testing critical logic and edge cases.
