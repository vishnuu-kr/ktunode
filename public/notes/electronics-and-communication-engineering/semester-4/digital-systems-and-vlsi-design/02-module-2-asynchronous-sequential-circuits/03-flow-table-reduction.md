# Digital Systems and VLSI Design - Module 2: Asynchronous Sequential Circuits

## Topic: Flow Table Reduction

---

### 1. Introduction to Flow Tables

*   **Definition:** A flow table is a tabular representation of an asynchronous sequential circuit's behavior. It describes the circuit's state transitions in response to inputs.
*   **Purpose:** Flow tables are essential for designing and analyzing asynchronous sequential circuits. They provide a systematic way to understand the circuit's logic.
*   **Components of a Flow Table:**
    *   **States (rows):** Represent the internal memory states of the circuit.
    *   **Inputs (columns):** Represent the possible combinations of external inputs.
    *   **Next State:** The state the circuit will transition to from a current state given a specific input.
    *   **Output:** The output generated by the circuit in a given state and with a given input.

*   **Types of Flow Tables:**
    *   **Primitive Flow Table:** Contains only stable states in each row, with next state entries indicating transitions to other stable states.
    *   **Reduced Flow Table:** Derived from a primitive flow table by merging equivalent states.

---

### 2. Concept of State Equivalence

*   **Definition:** Two states, $S_a$ and $S_b$, of a sequential circuit are equivalent if, for every possible input sequence, the output sequence and the next state reached from $S_a$ are the same as those reached from $S_b$.
*   **Importance:** State equivalence allows us to reduce the number of states in a flow table without altering the circuit's functionality. This leads to simpler and more efficient circuit designs.

---

### 3. Flow Table Reduction Techniques

The primary goal of flow table reduction is to minimize the number of states in the table by merging equivalent states. This process is crucial for designing efficient asynchronous sequential circuits, as per **CO2**.

#### 3.1. Merging Equivalent States

This is the core technique for flow table reduction. It involves identifying and merging states that behave identically.

**Steps:**

1.  **Identify Equivalent States:**
    *   **Condition for Equivalence:** Two states, $S_i$ and $S_j$, are equivalent if:
        *   They produce the same output for all inputs.
        *   For every input, the next state reached from $S_i$ is equivalent to the next state reached from $S_j$.
    *   **Systematic Merging:**
        *   **Initial Grouping:** Start by grouping states that are identical in terms of output for all inputs.
        *   **Iterative Refinement:** Repeatedly compare states within groups and across groups. If two states are found to be equivalent, they can be merged into a single new state. This process continues until no more states can be merged.

2.  **Construct the Reduced Flow Table:**
    *   Once equivalent states are identified and merged, create a new flow table where each row represents a merged state (or a group of equivalent states).
    *   The next state entries in the reduced table are determined by mapping the original next states to their corresponding merged states.

#### 3.2. Example of Flow Table Reduction

Let's consider a primitive flow table for an asynchronous sequential circuit.

**Primitive Flow Table:**

| Present State | Input 00 | Input 01 | Input 10 | Input 11 | Output (y1, y2) |
| :------------ | :------- | :------- | :------- | :------- | :-------------- |
| **a**         | a, 00    | b, 00    | a, 00    | a, 00    | 00              |
| **b**         | a, 00    | b, 10    | c, 00    | b, 00    | 00              |
| **c**         | c, 00    | b, 10    | d, 00    | c, 00    | 00              |
| **d**         | a, 00    | b, 00    | d, 10    | d, 00    | 00              |

**Analysis for Equivalence:**

*   **Output Check:** All states have the same output (00) for all input combinations. This means we only need to check the next state equivalence.

*   **Pairwise Equivalence (Implication Table Method - though not explicitly required by the prompt, it's a systematic way to visualize):**

    Let's try to merge states by inspection first.

    *   **Compare 'a' and 'c':**
        *   Input 00: a -> a, c -> c. Are 'a' and 'c' equivalent? Unknown yet.
        *   Input 01: a -> b, c -> b. If 'b' is equivalent to itself (always true), then this is fine.
        *   Input 10: a -> a, c -> d. Are 'a' and 'd' equivalent? Unknown yet.
        *   Input 11: a -> a, c -> c. Are 'a' and 'c' equivalent? Unknown yet.
        *   Since 'a' goes to 'a' and 'c' goes to 'd' for input 10, they can only be equivalent if 'a' is equivalent to 'd'.

    *   **Compare 'a' and 'd':**
        *   Input 00: a -> a, d -> a. Equivalent.
        *   Input 01: a -> b, d -> b. Equivalent.
        *   Input 10: a -> a, d -> d. Are 'a' and 'd' equivalent? Unknown yet.
        *   Input 11: a -> a, d -> d. Are 'a' and 'd' equivalent? Unknown yet.
        *   From input 10, 'a' goes to 'a' and 'd' goes to 'd'. This implies that if 'a' is equivalent to 'd', then 'a' must be equivalent to itself (trivial) and 'd' must be equivalent to itself (trivial).

    *   **Let's assume 'a' and 'd' are equivalent.** We'll call this new merged state **A**.
        *   'a' -> 'a' (maps to A)
        *   'd' -> 'd' (maps to A)
        *   'a' -> 'b' (maps to B if 'b' is a new state)
        *   'd' -> 'b' (maps to B)
        *   'a' -> 'a' (maps to A)
        *   'd' -> 'd' (maps to A)

    *   **Now consider 'b'.** Let's see if it's equivalent to 'A'.
        *   Compare 'b' and 'A' (representing 'a' and 'd'):
            *   Input 00: b -> a (maps to A), A -> a (maps to A). Equivalent.
            *   Input 01: b -> b (maps to B), A -> b (maps to B). Equivalent.
            *   Input 10: b -> c (maps to C if 'c' is a new state), A -> a (maps to A). For 'b' and 'A' to be equivalent, 'c' must be equivalent to 'A'.
            *   Input 11: b -> b (maps to B), A -> d (maps to A). For 'b' and 'A' to be equivalent, 'b' must be equivalent to 'A'. This is a contradiction, so 'b' is not equivalent to 'A'.

    *   **Consider 'c'.** Let's see if it's equivalent to 'A'.
        *   Compare 'c' and 'A' (representing 'a' and 'd'):
            *   Input 00: c -> c (maps to C), A -> a (maps to A). For 'c' and 'A' to be equivalent, 'c' must be equivalent to 'A'.
            *   Input 01: c -> b (maps to B), A -> b (maps to B). Equivalent.
            *   Input 10: c -> d (maps to A), A -> a (maps to A). Equivalent.
            *   Input 11: c -> c (maps to C), A -> d (maps to A). For 'c' and 'A' to be equivalent, 'c' must be equivalent to 'A'.
        *   If 'c' were equivalent to 'A', then for input 00, 'c' goes to 'c' and 'A' goes to 'A', requiring 'c' to be equivalent to 'A'. This seems self-referential and problematic.

    *   **Let's re-evaluate the equivalence 'a' and 'd'.**
        *   From 'a', input 10 goes to 'a'.
        *   From 'd', input 10 goes to 'd'.
        *   For 'a' and 'd' to be equivalent, their next states for all inputs must be equivalent.
        *   Consider input 10: If 'a' and 'd' are equivalent, then 'a' must be equivalent to 'd'.

    *   **Let's try to group 'a' and 'b' and 'd' first.**
        *   'a' and 'b': input 10, a->a, b->c. Not equivalent.
        *   'a' and 'd': input 10, a->a, d->d. Potential equivalence if 'a' ~ 'd'.
        *   'b' and 'd': input 10, b->c, d->d. Potential equivalence if 'c' ~ 'd'.

    *   **Let's try to group 'a' and 'c'.**
        *   Input 10: a -> a, c -> d. Needs 'a' ~ 'd'.
        *   Input 01: a -> b, c -> b. Needs 'b' ~ 'b'.

    *   **Let's try to group 'b' and 'c'.**
        *   Input 00: b -> a, c -> c. Needs 'a' ~ 'c'.
        *   Input 01: b -> b, c -> b. Needs 'b' ~ 'b'.
        *   Input 10: b -> c, c -> d. Needs 'c' ~ 'd'.
        *   Input 11: b -> b, c -> c. Needs 'b' ~ 'c'.

    *   **Let's try to group 'c' and 'd'.**
        *   Input 00: c -> c, d -> a. Needs 'c' ~ 'a'.
        *   Input 01: c -> b, d -> b. Needs 'b' ~ 'b'.
        *   Input 10: c -> d, d -> d. Needs 'd' ~ 'd'.
        *   Input 11: c -> c, d -> d. Needs 'c' ~ 'd'.

    **The most common approach is to use the implication table.**

    **Implication Table:**
    Create a table with states on both axes. Mark cells $(S_i, S_j)$ if $S_i$ and $S_j$ are not equivalent.
    States are in columns/rows. We mark an 'X' in cell $(i, j)$ if state $i$ and state $j$ are *not* equivalent.

    |       | a     | b     | c     | d     |
    | :---- | :---- | :---- | :---- | :---- |
    | **a** |       |       |       |       |
    | **b** |       |       |       |       |
    | **c** |       |       |       |       |
    | **d** |       |       |       |       |

    1.  **Row-by-row initial check:** If two states have different outputs for any input, they are not equivalent. In our case, all outputs are the same.

    2.  **Check for non-equivalent next states:**
        *   Consider pair (a, b):
            *   Input 00: a -> a, b -> a. OK (a~a)
            *   Input 01: a -> b, b -> b. OK (b~b)
            *   Input 10: a -> a, b -> c. If (a,c) is not equivalent, then (a,b) is not equivalent.
            *   Input 11: a -> a, b -> b. OK (a~b)
        *   Consider pair (a, c):
            *   Input 00: a -> a, c -> c. If (a,c) is not equivalent, then (a,c) is not equivalent.
            *   Input 01: a -> b, c -> b. OK (b~b)
            *   Input 10: a -> a, c -> d. If (a,d) is not equivalent, then (a,c) is not equivalent.
            *   Input 11: a -> a, c -> c. If (a,c) is not equivalent, then (a,c) is not equivalent.
        *   Consider pair (a, d):
            *   Input 00: a -> a, d -> a. OK (a~a)
            *   Input 01: a -> b, d -> b. OK (b~b)
            *   Input 10: a -> a, d -> d. If (a,d) is not equivalent, then (a,d) is not equivalent.
            *   Input 11: a -> a, d -> d. If (a,d) is not equivalent, then (a,d) is not equivalent.
        *   Consider pair (b, c):
            *   Input 00: b -> a, c -> c. If (a,c) is not equivalent, then (b,c) is not equivalent.
            *   Input 01: b -> b, c -> b. OK (b~b)
            *   Input 10: b -> c, c -> d. If (c,d) is not equivalent, then (b,c) is not equivalent.
            *   Input 11: b -> b, c -> c. If (b,c) is not equivalent, then (b,c) is not equivalent.
        *   Consider pair (b, d):
            *   Input 00: b -> a, d -> a. OK (a~a)
            *   Input 01: b -> b, d -> b. OK (b~b)
            *   Input 10: b -> c, d -> d. If (c,d) is not equivalent, then (b,d) is not equivalent.
            *   Input 11: b -> b, d -> d. If (b,d) is not equivalent, then (b,d) is not equivalent.
        *   Consider pair (c, d):
            *   Input 00: c -> c, d -> a. If (c,a) is not equivalent, then (c,d) is not equivalent.
            *   Input 01: c -> b, d -> b. OK (b~b)
            *   Input 10: c -> d, d -> d. If (d,d) is not equivalent, then (c,d) is not equivalent.
            *   Input 11: c -> c, d -> d. If (c,d) is not equivalent, then (c,d) is not equivalent.

    *   **Crucial Observation:** Notice the self-implications. For example, for pair (a,d) and input 10, we have a -> a and d -> d. If 'a' and 'd' were equivalent, then 'a' must be equivalent to 'a' (which is true) and 'd' must be equivalent to 'd' (which is true). This doesn't immediately rule them out. However, let's look at (a, c) and input 10: a -> a, c -> d. If 'a' and 'c' are equivalent, then their next states must be equivalent, meaning 'a' must be equivalent to 'd'.

    *   Let's assume (a,d) are equivalent. Let this merged state be **A**.
        *   Now we check if 'c' is equivalent to 'A' (i.e., 'a' and 'd').
            *   Compare (c, a): Input 10: c -> d. For (c,a) to be equivalent, c -> d means d must be equivalent to the next state from 'c' for input 10, which is 'd'. This implies 'd' ~ 'd'.
            *   Compare (c, d): Input 00: c -> c. For (c,d) to be equivalent, c -> c means c must be equivalent to the next state from 'd' for input 00, which is 'a'. This implies 'c' ~ 'a'.

    *   This is becoming circular. Let's step back and reconsider.
    *   **Key Insight:** If state $S_i$ transitions to $S_k$ and state $S_j$ transitions to $S_l$ for some input, then for $S_i$ and $S_j$ to be equivalent, it must be true that $S_k$ and $S_l$ are equivalent.

    *   Let's analyze the conditions that *must* hold for states to be equivalent.
        *   **Equivalent States:**
            *   `a` and `d`:
                *   Input 10: `a`->`a`, `d`->`d`. Requires `a` ~ `d`.
                *   Input 11: `a`->`a`, `d`->`d`. Requires `a` ~ `d`.
                *   If `a` ~ `d`, then `a` and `d` can be merged into state **X**.
            *   `b` and `c`:
                *   Input 00: `b`->`a`, `c`->`c`. Requires `a` ~ `c`.
                *   Input 10: `b`->`c`, `c`->`d`. Requires `c` ~ `d`.
                *   Input 11: `b`->`b`, `c`->`c`. Requires `b` ~ `c`.
                *   If `b` ~ `c`, then `b` and `c` can be merged into state **Y**.

        *   **Conditions for merging:**
            *   For `a` and `d` to be equivalent, `a` must be equivalent to `d`. Let's call this group {a, d}.
            *   For `b` and `c` to be equivalent, `a` must be equivalent to `c` (from b->a, c->c) and `c` must be equivalent to `d` (from b->c, c->d).
            *   If {a, d} is a group, then the condition `a` ~ `c` and `c` ~ `d` means `c` must be equivalent to the group {a, d}.

        *   **Let's test the hypothesis: {a, d} are equivalent. {b} is unique. {c} is unique.**
            *   Check `a` vs `d`: Input 10: `a`->`a`, `d`->`d`. Since `a` is equivalent to itself and `d` to itself, this is okay. This suggests `a` and `d` *can* be equivalent. Let's group them as **A**.
            *   Now, check if `c` is equivalent to `A` (i.e., `a` or `d`).
                *   `c` vs `a`: Input 10: `c`->`d`. For `c` to be equivalent to `a`, `d` must be equivalent to `d` (which is true).
                *   `c` vs `d`: Input 00: `c`->`c`. For `c` to be equivalent to `d`, `c` must be equivalent to `a` (which is not yet proven).
            *   This means `c` is *not* equivalent to `a` or `d`. So `c` remains a separate state.

        *   **What about `b`?** Is `b` equivalent to `a` or `d`?
            *   `b` vs `a`: Input 10: `b`->`c`. For `b` to be equivalent to `a`, `c` must be equivalent to `a`. We know `c` is not equivalent to `a`. So `b` is not equivalent to `a`.
            *   `b` vs `d`: Similar logic, `b` is not equivalent to `d`.

        *   **What about `b` and `c`?**
            *   `b` vs `c`:
                *   Input 00: `b`->`a`, `c`->`c`. Requires `a` ~ `c`. As established, `a` is not equivalent to `c`. So `b` is not equivalent to `c`.

    **Conclusion from this analysis:** It appears that no states are equivalent in this particular flow table. This can happen. A primitive flow table might already be minimal or might require a more formal implication table method to prove equivalence.

    **Let's re-examine the example from a textbook like Givone or Kohavi for a simpler case.**

    **Simpler Example:**
    Consider a primitive flow table:

    | Present State | Input 0 | Input 1 | Output (y) |
    | :------------ | :------ | :------ | :--------- |
    | **a**         | a, 0    | b, 0    | 0          |
    | **b**         | a, 0    | b, 1    | 0          |
    | **c**         | c, 0    | b, 0    | 0          |

    *   **Output Check:** All states have output 0.
    *   **Equivalence Check:**
        *   **Compare `a` and `b`:**
            *   Input 0: `a`->`a`, `b`->`a`. Next states `a` and `a` are equivalent.
            *   Input 1: `a`->`b`, `b`->`b`. Next states `b` and `b` are equivalent.
            *   Since next states are equivalent for all inputs, `a` and `b` *could* be equivalent.
        *   **Compare `a` and `c`:**
            *   Input 0: `a`->`a`, `c`->`c`. Requires `a` ~ `c`.
            *   Input 1: `a`->`b`, `c`->`b`. Next states `b` and `b` are equivalent.
            *   If `a` ~ `c`, then `a` and `c` can be equivalent.
        *   **Compare `b` and `c`:**
            *   Input 0: `b`->`a`, `c`->`c`. Requires `a` ~ `c`.
            *   Input 1: `b`->`b`, `c`->`b`. Next states `b` and `b` are equivalent.
            *   If `a` ~ `c`, then `b` and `c` can be equivalent.

    *   **Implication Chart:**
        Let's assume `a` and `b` are equivalent. Group {a, b} as **X**.
        Now check if `c` is equivalent to `X` (i.e., `a` or `b`).
        *   Check `c` vs `a` (part of X):
            *   Input 0: `c`->`c`, `a`->`a`. Requires `c` ~ `a`.
            *   Input 1: `c`->`b`, `a`->`b`. Next states `b` and `b` are equivalent.
            *   If `c` ~ `a`, then `c` can be equivalent to `a`.

        *   Check `c` vs `b` (part of X):
            *   Input 0: `c`->`c`, `b`->`a`. Requires `c` ~ `a`.
            *   Input 1: `c`->`b`, `b`->`b`. Next states `b` and `b` are equivalent.
            *   If `c` ~ `a`, then `c` can be equivalent to `b`.

        So, for `c` to be equivalent to `X` ({a,b}), we need `c` ~ `a`.
        Let's test if `a` and `c` are equivalent.
        *   Input 0: `a`->`a`, `c`->`c`. Requires `a` ~ `c`.
        *   Input 1: `a`->`b`, `c`->`b`. Next states `b`~`b`.
        This means that if `a` and `c` are equivalent, then `a` must be equivalent to `c` itself. This is a self-consistency check.

        **Let's formalize the merging for {a, b, c}:**
        If we merge `a` and `c`, we need `a` ~ `c`.
        If we merge `a` and `b`, we need `a` ~ `a` and `b` ~ `b` for inputs.
        If we merge `b` and `c`, we need `a` ~ `c` for input 0.

        **Consider the pairs:**
        *   (a,b) are equivalent: If a ~ a and b ~ b for all inputs.
            *   Input 0: a -> a, b -> a (a~a)
            *   Input 1: a -> b, b -> b (b~b)
            *   This implies that `a` and `b` are equivalent. Merge {a, b} into state **X**.

        *   Now check `c` against `X`.
            *   `c` vs `X` ({a, b}):
                *   Input 0: `c`->`c`, `X`->`a` (from `a`) and `X`->`a` (from `b`).
                    *   For `c` to be equivalent to `X`, `c` must be equivalent to `a`.
                *   Input 1: `c`->`b`, `X`->`b` (from `a`) and `X`->`b` (from `b`).
                    *   `b` is equivalent to `b`.

            *   So, for `c` to be equivalent to `X`, we require `c` ~ `a`.
            *   Let's check if `c` and `a` are equivalent.
                *   Input 0: `c`->`c`, `a`->`a`. Requires `c` ~ `a`.
                *   Input 1: `c`->`b`, `a`->`b`. `b` ~ `b`.
            *   This means `c` and `a` can be equivalent *if* `c` is equivalent to `a`. This is a self-referential condition. If they are equivalent, their next states for input 0 must be equivalent, i.e., `c` must be equivalent to `a`. This is possible.

        Therefore, we can merge all three states {a, b, c} into a single state **A**.

    **Reduced Flow Table:**

    | Present State | Input 0 | Input 1 | Output (y) |
    | :------------ | :------ | :------ | :--------- |
    | **A**         | A, 0    | A, 0/1  | 0          |

    *   **Next State Entry:** For the merged state `A`, the next state entry is determined by the original next states.
        *   From `a`, input 0 -> `a` (maps to A), input 1 -> `b` (maps to A).
        *   From `b`, input 0 -> `a` (maps to A), input 1 -> `b` (maps to A).
        *   From `c`, input 0 -> `c` (maps to A), input 1 -> `b` (maps to A).
        *   So, for input 0, `A` -> `A`. For input 1, `A` -> `A`.
    *   **Output:** The output in the merged state is consistent across the original states and their transitions. For input 0, the output is always 0. For input 1, the output is 0 (from `a`, `c`) or 1 (from `b`). If they are truly equivalent, this implies a problem.

    **Revisiting the Equivalence Rule:** If two states are equivalent, they must produce the same output for all inputs, AND their next states must be equivalent.

    In the simpler example:
    *   `a` vs `b`: Outputs are the same. Next states for input 0 are `a` and `a` (equivalent). Next states for input 1 are `b` and `b` (equivalent). Thus, `a` and `b` are equivalent. Merge {a, b} into **X**.

    *   Now, compare `c` with `X` ({a, b}).
        *   `c` vs `a`:
            *   Input 0: `c`->`c`, `a`->`a`. For `c` and `a` to be equivalent, `c` must be equivalent to `a`.
            *   Input 1: `c`->`b`, `a`->`b`. `b` ~ `b`.
        *   `c` vs `b`:
            *   Input 0: `c`->`c`, `b`->`a`. For `c` and `b` to be equivalent, `c` must be equivalent to `a`.
            *   Input 1: `c`->`b`, `b`->`b`. `b` ~ `b`.

    The condition for merging `c` with `X` ({a, b}) is that `c` must be equivalent to `a` (or `b`, which implies the same).
    Let's check if `a` and `c` are equivalent:
    *   Input 0: `a`->`a`, `c`->`c`. This implies `a` must be equivalent to `c`.
    *   Input 1: `a`->`b`, `c`->`b`. This is consistent.

    So, if `a` and `c` are equivalent, then `a` and `c` can be merged. This implies `c` can be merged with `X`.
    This means {a, b, c} can all be merged into a single state **A**.

    **Reduced Flow Table (Corrected):**

    | Present State | Input 0 | Input 1 | Output (y) |
    | :------------ | :------ | :------ | :--------- |
    | **A**         | A, 0    | A, 0    | 0          |

    *   **Next State for Input 1:**
        *   From original `a`, input 1 -> `b` (maps to A). Output is 0.
        *   From original `b`, input 1 -> `b` (maps to A). Output is 1.
        *   From original `c`, input 1 -> `b` (maps to A). Output is 0.

        If we merge {a,b,c} into A, and for input 1, we have transitions to the *same* next state A, but with *different* outputs (0 and 1), this indicates that the states are NOT equivalent, or there's an issue with the original flow table for consistent merging.

    **Let's re-examine the basic premise of state equivalence for asynchronous circuits.**
    For asynchronous circuits, we often have "don't care" conditions. However, the core idea of state equivalence remains: for any input sequence, the output sequence and final state must be the same.

    **Crucial Point:** The reduction process aims to find maximal compatible sets of states.

    **Let's go back to the first example and assume the implication table approach is necessary.**

    **Primitive Flow Table:**

    | Present State | Input 00 | Input 01 | Input 10 | Input 11 | Output (y1, y2) |
    | :------------ | :------- | :------- | :------- | :------- | :-------------- |
    | **a**         | a, 00    | b, 00    | a, 00    | a, 00    | 00              |
    | **b**         | a, 00    | b, 10    | c, 00    | b, 00    | 00              |
    | **c**         | c, 00    | b, 10    | d, 00    | c, 00    | 00              |
    | **d**         | a, 00    | b, 00    | d, 10    | d, 00    | 00              |

    **Implication Table for (Si, Sj):**

    |       | a     | b     | c     | d     |
    | :---- | :---- | :---- | :---- | :---- |
    | **a** |       |       | X     | X     |  (a vs c: input 10 implies a vs d. a vs d: input 10 implies a vs d)
    | **b** |       |       | X     | X     |  (b vs c: input 00 implies a vs c. b vs d: input 10 implies c vs d)
    | **c** |       |       |       | X     |  (c vs d: input 00 implies c vs a. c vs d: input 10 implies d vs d)
    | **d** |       |       |       |       |

    Let's systematically fill it:

    *   **Pair (a,b):**
        *   Inp 00: a->a, b->a. Ok.
        *   Inp 01: a->b, b->b. Ok.
        *   Inp 10: a->a, b->c. If (a,c) not equivalent, then (a,b) not equivalent.
        *   Inp 11: a->a, b->b. Ok.
    *   **Pair (a,c):**

        *   Input 11: a->a(A), c->c(A), d->d(A). All to A.
    *   **Outputs for A:**
        *   Input 00: 00 (from a,c,d). OK.
        *   Input 01: 00 (from a), 10 (from c), 00 (from d). Inconsistent. This makes A={a,c,d} invalid if the output for `b` is different.

    **If the outputs listed in the original table *are* the outputs generated by that state for that input:**
    *   `a` (00) -> `b` (00) for input 01.
    *   `c` (00) -> `b` (10) for input 01.
    *   `d` (00) -> `b` (00) for input 01.
    *   This means `c` is NOT equivalent to `a` or `d` because they produce different outputs for the same transition.

    **Therefore, in the first example, the maximal compatible sets are:**
    *   {a}
    *   {c}
    *   {d}
    *   {b}
    All states are distinct. The flow table is already minimal.

    This highlights the importance of checking output consistency throughout the merging process.

### 4. Key Concepts and Summary

*   **State Equivalence:** Two states are equivalent if they produce identical output sequences for all input sequences and transition to equivalent next states.
*   **Maximal Compatible Sets:** The largest possible sets of states that are mutually equivalent.
*   **Reduction Goal:** To reduce the number of states by merging equivalent states into a single state in the reduced flow table.
*   **Process:**
    1.  Identify equivalent states by comparing outputs and next states for all input combinations.
    2.  Use the implication table method for systematic equivalence checking.
    3.  Group equivalent states into maximal compatible sets.
    4.  Construct the reduced flow table where each row represents a maximal compatible set.
    5.  Map next state entries to the new merged states.
    6.  Ensure output consistency within merged states. If states within a potential merged set produce different outputs for any input, they cannot be merged.

### 6. Important Points to Remember

*   **Output Consistency is Paramount:** Two states can only be merged if they produce identical outputs for all input conditions. If a potential merged state would have different outputs for the same input, then the original states are not equivalent.
*   **Next State Compatibility:** If state $S_i$ and $S_j$ are being considered for merging, and for an input $k$, $S_i \to S_{i'}$ and $S_j \to S_{j'}$, then $S_{i'}$ and $S_{j'}$ must also be equivalent.
*   **Implication Table:** A systematic tool to identify non-equivalent states. Start by marking incompatible pairs, then propagate incompatibilities.
*   **Maximal Compatible Sets:** The goal is to find the largest possible sets of equivalent states.
*   **Reduced Table Entries:** When merging states, the next state entries in the reduced table are determined by mapping the original next states to their corresponding merged states. If a merged state has transitions to different merged states for the same input, this indicates an error in the reduction or the original flow table.

### 7. Practice Questions

**Question 1:**
Consider the following primitive flow table for an asynchronous sequential circuit. Reduce the flow table to its minimal form.

| Present State | Input 00 | Input 01 | Input 10 | Input 11 | Output (y1, y2) |
| :------------ | :------- | :------- | :------- | :------- | :-------------- |
| **a**         | a, 0     | b, 0     | a, 0     | a, 0     | 0               |
| **b**         | c, 0     | b, 1     | c, 0     | b, 0     | 0               |
| **c**         | c, 0     | b, 1     | d, 0     | c, 0     | 0               |
| **d**         | a, 0     | b, 0     | d, 1     | d, 0     | 0               |

**Answer:**
Let's analyze for state equivalence. All states have output 0.

*   **Check {a, b}:**
    *   Input 00: a->a, b->c. Need a~c.
    *   Input 01: a->b, b->b. Need b~b.
    *   Input 10: a->a, b->c. Need a~c.
    *   Input 11: a->a, b->b. Need a~b.
*   **Check {a, c}:**
    *   Input 00: a->a, c->c. Need a~c.
    *   Input 01: a->b, c->b. Need b~b.
    *   Input 10: a->a, c->d. Need a~d.
    *   Input 11: a->a, c->c. Need a~c.
*   **Check {a, d}:**
    *   Input 00: a->a, d->a. Need a~a.
    *   Input 01: a->b, d->b. Need b~b.
    *   Input 10: a->a, d->d. Need a~d.
    *   Input 11: a->a, d->d. Need a~d.
    *   This suggests {a, d} are equivalent. Let's call this set **X**.

*   **Check {b, c}:**
    *   Input 00: b->c, c->c. Need c~c.
    *   Input 01: b->b, c->b. Need b~b.
    *   Input 10: b->c, c->d. Need c~d.
    *   Input 11: b->b, c->c. Need b~c.
    *   This suggests {b, c} are equivalent. Let's call this set **Y**.

*   **Check {b, d}:**
    *   Input 00: b->c, d->a. Need c~a.
    *   Input 01: b->b, d->b. Need b~b.
    *   Input 10: b->c, d->d. Need c~d.
    *   Input 11: b->b, d->d. Need b~d.

*   **Check {c, d}:**
    *   Input 00: c->c, d->a. Need c~a.
    *   Input 01: c->b, d->b. Need b~b.
    *   Input 10: c->d, d->d. Need d~d.
    *   Input 11: c->c, d->d. Need c~d.

From the above, we need:
1.  `a` ~ `d` (for {a,d})
2.  `c` ~ `d` (for {c,d})
3.  `c` ~ `a` (for {b,d} and {c,d})
4.  `b` ~ `c` (for {b,c})

These conditions imply that `a`, `c`, and `d` must be equivalent. Let's group them as **A = {a, c, d}**.
Now check `b` against **A**.
*   `b` vs `a`: input 10: b->c (in A), a->a (in A). Next states are compatible.
*   `b` vs `c`: input 00: b->c (in A), c->c (in A). Next states are compatible. Input 10: b->c (in A), c->d (in A). Next states are compatible.
*   `b` vs `d`: input 10: b->c (in A), d->d (in A). Next states are compatible.

All states `a`, `c`, `d` transition to states within **A** or `b` itself. And `b` transitions to states within `A` or `b` itself.
The crucial check is output consistency for the *merged* state.
*   For input 10: states `b` and `d` have output 1. states `a` and `c` have output 0.
*   This means `b` and `d` cannot be merged with `a` and `c` because of output inconsistency.

The maximal compatible sets are:
*   **A = {a}**
*   **B = {b}**
*   **C = {c}**
*   **D = {d}**

Let's re-examine the conditions for {a,d} and {b,c}:
*   {a,d} requires `a`~`d`.
*   {b,c} requires `a`~`c`, `c`~`d`, `b`~`c`.

This implies `a`, `c`, `d` must be equivalent. Let **A = {a, c, d}**.
Now check `b` against **A**.
*   Input 10: `b`->`c` (in A), `d`->`d` (in A). Next states are ok.
*   Input 00: `b`->`c` (in A), `c`->`c` (in A). Next states are ok.
*   Input 01: `b`->`b`. `a`->`b`. `c`->`b`. `d`->`b`.
    *   The output from `b` for input 01 is 1.
    *   The output from `a` for input 01 is 0.
    *   The output from `c` for input 01 is 1.
    *   The output from `d` for input 01 is 0.

    Since `a` and `c` have different outputs for input 01, they are not equivalent.
    Since `a` and `d` have the same output for input 01, they might be.
    Since `b` and `c` have the same output for input 01, they might be.

    This suggests the maximal compatible sets are:
    *   **A = {a, d}** (outputs 0 for all inputs).
    *   **B = {b, c}** (outputs 0 for input 00, 1 for input 01, 0 for input 10, 0 for input 11). This is consistent for {b,c}.

    Let's check compatibility between **A** and **B**.
    *   `a` vs `b`: Input 00: a->a (in A), b->c (in B). Requires a~c.
    *   `a` vs `c`: Input 00: a->a (in A), c->c (in B). Requires a~c.
    *   `a` vs `b`: Input 01: a->b (in B), b->b (in B). Next states are compatible.
    *   `a` vs `c`: Input 01: a->b (in B), c->b (in B). Next states are compatible.
    *   `a` vs `b`: Input 10: a->a (in A), b->c (in B). Requires a~c.
    *   `a` vs `c`: Input 10: a->a (in A), c->d (in A). Requires a~d.

    This implies that for `a` to be compatible with `c`, we need `a`~`c`. And for `a` to be compatible with `b`, we need `a`~`c`.
    So, the requirements are `a`~`d` and `a`~`c`. This means {a, c, d} are equivalent.
    And for {b, c}, we need `a`~`c`, `c`~`d`, `b`~`c`.

    The only way these conditions can hold is if `a`, `c`, `d` are equivalent.
    Let's assume **A = {a, c, d}** and **B = {b}**.
    *   **A vs B:**
        *   Input 00: a->a(A), b->c(A). OK.
        *   Input 01: a->b(B), b->b(B). OK.
        *   Input 10: a->a(A), b->c(A). OK.
        *   Input 11: a->a(A), b->b(B). Requires a~b.

    This shows that states {a,c,d} cannot be merged, and `b` is separate.
    The maximal compatible sets are:
    1.  **{a, d}** (let's call this **X**)
    2.  **{b, c}** (let's call this **Y**)

    **Reduced Flow Table:**

    | Present State | Input 00 | Input 01 | Input 10 | Input 11 | Output (y) |
    | :------------ | :------- | :------- | :------- | :------- | :--------- |
    | **X**         | X, 0     | Y, 0     | X, 0     | X, 0     | 0          |
    | **Y**         | X, 0     | Y, 1     | X, 0     | Y, 0     | 0/1        |

    *   **Entries for X (from {a,d}):**
        *   Input 00: a->a(X), d->a(X). All to X.
        *   Input 01: a->b(Y), d->b(Y). All to Y.
        *   Input 10: a->a(X), d->d(X). All to X.
        *   Input 11: a->a(X), d->d(X). All to X.
    *   **Outputs for X:**
        *   Input 00: 0 (from a,d). OK.
        *   Input 01: 0 (from a), 0 (from d). OK.
        *   Input 10: 0 (from a,d). OK.
        *   Input 11: 0 (from a,d). OK.

    *   **Entries for Y (from {b,c}):**
        *   Input 00: b->c(Y), c->c(Y). All to Y.
        *   Input 01: b->b(Y), c->b(Y). All to Y.
        *   Input 10: b->c(Y), c->d(X). Need Y~X for next state from `c`.
        *   Input 11: b->b(Y), c->c(Y). All to Y.
    *   **Outputs for Y:**
        *   Input 00: 0 (from b,c). OK.
        *   Input 01: 1 (from b), 1 (from c). OK.
        *   Input 10: 0 (from b), 0 (from c). OK.
        *   Input 11: 0 (from b), 0 (from c). OK.

    The problem is the transition for Y in input 10. `c` (in Y) goes to `d` (in X). So, the entry should be X,0.
    The entry for Y in input 10 should be `X,0`.

    **Corrected Reduced Flow Table:**

    | Present State | Input 00 | Input 01 | Input 10 | Input 11 | Output (y) |
    | :------------ | :------- | :------- | :------- | :------- | :--------- |
    | **X**         | X, 0     | Y, 0     | X, 0     | X, 0     | 0          |
    | **Y**         | Y, 0     | Y, 1     | X, 0     | Y, 0     | 0/1        |

    This seems to be the minimal form.

**Question 2:**
Explain the criteria for merging two states in a flow table.

**Answer:**
Two states, $S_i$ and $S_j$, can be merged into a single state if they satisfy the following conditions:

1.  **Output Consistency:** For every input combination, the output produced by $S_i$ must be identical to the output produced by $S_j$. If there is any input for which the outputs differ, the states are not equivalent and cannot be merged.
2.  **Next State Compatibility:** For every input combination, if $S_i$ transitions to $S_{i'}$ and $S_j$ transitions to $S_{j'}$, then the states $S_{i'}$ and $S_{j'}$ must also be equivalent. This means that if $S_i$ and $S_j$ are merged, their next states must transition to the same merged state or equivalent merged states for all inputs.
