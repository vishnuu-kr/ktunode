# ARM Architecture and Programming: Module 4 - IO Programming in Assembly: Interrupts and Exceptions

## Introduction to Interrupts and Exceptions

This module delves into how the ARM processor handles asynchronous events (interrupts) and synchronous error conditions (exceptions) during program execution. Understanding these mechanisms is crucial for efficient Input/Output (IO) programming in assembly language, allowing the processor to respond to external stimuli and internal errors without constantly polling.

### Key Concepts and Definitions

#### 1. Interrupts

*   **Definition:** An interrupt is an asynchronous event that causes the processor to temporarily suspend its current execution and transfer control to a specific routine (Interrupt Service Routine - ISR) to handle the event. Once the ISR is complete, the processor resumes its original execution.
*   **Purpose:** Interrupts are essential for IO operations. They allow the processor to react to external events (e.g., data arriving from a peripheral, a button press) without continuously polling the device. This significantly improves efficiency and responsiveness.
*   **Sources:**
    *   **External Interrupts:** Generated by external hardware devices (e.g., timers, UARTs, ADCs, GPIO pins).
    *   **Internal Interrupts:** Generated by the processor itself (e.g., software interrupts, exceptions).

#### 2. Exceptions

*   **Definition:** An exception is a synchronous event that occurs during the execution of an instruction, indicating an error condition or a special condition that requires processor intervention. Unlike interrupts, exceptions are predictable and directly related to the instruction being executed.
*   **Purpose:** Exceptions handle errors such as division by zero, illegal instructions, memory access violations, and breakpoints. They also provide a mechanism for system calls.
*   **Types (ARM Cortex-M specific, often shared concepts):**
    *   **Reset:** Occurs when the processor is reset.
    *   **NMI (Non-Maskable Interrupt):** A high-priority interrupt that cannot be disabled by software. Often used for critical events like watchdog timer expirations or system errors.
    *   **HardFault:** A bus fault, instruction access violation, or other severe error that prevents the fault handler from executing.
    *   **MemManage (Memory Management Fault):** Occurs when an access to memory violates the memory protection unit (MPU) rules.
    *   **BusFault:** Occurs on a bus access error (e.g., external device not acknowledging a read/write).
    *   **UsageFault:** Occurs due to specific instruction execution issues like division by zero, unaligned access, or invalid state transitions.
    *   **SVC (Supervisor Call):** A software-generated exception used for making calls to privileged operating system routines.
    *   **DebugMon:** Used for debugging support.
    *   **PendSV (Pendable Service Call):** A low-priority, software-generated interrupt that can be used for context switching in an RTOS.
    *   **SysTick:** A timer interrupt used for periodic system operations, commonly for scheduling in RTOS.
    *   **External Interrupts (IRQ):** Generated by peripherals via an interrupt controller.

#### 3. Interrupt Vector Table (IVT)

*   **Definition:** A table stored in memory (usually at the beginning of the program's execution space) that contains the starting addresses of the ISRs for each interrupt and exception source.
*   **Format:** Each entry in the IVT is typically a 32-bit address (or a branch instruction to that address).
*   **Purpose:** When an interrupt or exception occurs, the processor uses the interrupt number to index into the IVT and fetch the address of the corresponding handler.

#### 4. Interrupt Service Routine (ISR) / Exception Handler

*   **Definition:** A block of assembly code designed to respond to a specific interrupt or exception.
*   **Function:** An ISR typically performs the necessary actions to service the interrupting device (e.g., read data from a UART, update a timer value) and then returns control to the interrupted program.
*   **Key Requirements for ISRs:**
    *   **Saving and Restoring Context:** The ISR must save the processor's state (registers) before execution and restore them before returning to ensure the interrupted program can resume correctly.
    *   **Atomic Operations:** Critical sections within ISRs might need to be protected from re-entrancy or interference from other interrupts.
    *   **Fast Execution:** ISRs should be as short and efficient as possible to minimize disruption to the main program.

#### 5. Interrupt Controller

*   **Definition:** A hardware block within the microcontroller that manages multiple interrupt sources, prioritizes them, and signals the processor when an interrupt needs to be serviced.
*   **Key Functions:**
    *   **Interrupt Masking:** Enabling or disabling individual interrupt sources.
    *   **Prioritization:** Assigning priority levels to different interrupts to determine which one is serviced first if multiple interrupts occur simultaneously.
    *   **Interrupt Vectoring:** Generating the interrupt number that the processor uses to fetch the ISR address from the IVT.
*   **Example (ARM Cortex-M):** The Nested Vectored Interrupt Controller (NVIC) is a prime example. It manages up to 240 interrupts and provides fine-grained control over priorities.

#### 6. Processor Mode and State Changes

*   **Processor Modes:** ARM processors have different operating modes (e.g., User, FIQ, IRQ, Supervisor, Abort, Undefined, System). When an interrupt or exception occurs, the processor typically transitions to a privileged mode (e.g., IRQ mode) to execute the handler.
*   **Processor State:** The processor's current state (e.g., execution mode, interrupt mask, condition flags) is automatically saved by hardware into specific registers (like the Stack Pointer and the Program Status Register - PSR) when an exception occurs. This allows for a seamless return to the interrupted task.

### Interrupt Handling Mechanism

1.  **Interrupt Request (IRQ):** An external peripheral or an internal event triggers an interrupt.
2.  **Interrupt Controller (NVIC):** The interrupt controller receives the IRQ, checks its priority against other pending interrupts, and if it's the highest priority unmasked interrupt, it signals the processor.
3.  **Processor Intervention:** The processor, upon receiving the interrupt signal:
    *   **Suspends Current Execution:** Stops executing the current instruction stream.
    *   **Saves Context:** Automatically pushes the current Program Counter (PC) and Program Status Register (PSR) onto the stack of the mode it's switching to (e.g., the IRQ stack).
    *   **Determines Interrupt Type:** Identifies the source of the interrupt.
    *   **Updates PC:** Loads the PC with the address of the appropriate ISR from the Interrupt Vector Table (IVT).
    *   **Enters Privileged Mode:** Switches to a privileged mode (e.g., IRQ mode) to execute the ISR.
4.  **ISR Execution:** The ISR runs, performs its tasks, and may update internal flags or status registers.
5.  **Return from Interrupt:** The ISR typically ends with a special return instruction (e.g., `BX LR` on ARM Cortex-M, where `LR` holds the saved PC). This instruction retrieves the saved PC and PSR from the stack, restoring the processor to its state before the interrupt, and resumes the interrupted program.

### IO Programming with Interrupts

Instead of continuously checking a device's status (polling), interrupts allow the processor to be notified only when an action is required. This is fundamental for efficient IO.

**Example Scenario: Receiving Data from a UART**

*   **Polling Approach:**
    ```assembly
    LOOP:
        LDR R0, =UART_STATUS_REG
        LDR R1, [R0]
        ANDS R1, R1, #RX_DATA_READY_MASK  // Check if RX data ready bit is set
        BEQ LOOP                        // If not ready, loop back
        // Data is ready, proceed to read
    ```
    This wastes CPU cycles if data is infrequent.

*   **Interrupt-Driven Approach:**
    1.  **Configure UART:** Set up the UART to generate an interrupt when RX data is ready.
    2.  **Enable UART Interrupt in NVIC:** Configure the NVIC to allow the UART interrupt.
    3.  **Write UART RX ISR:**
        ```assembly
        UART_RX_ISR:
            PUSH {R0-R3, LR}          // Save registers and LR
            LDR R0, =UART_DATA_REG    // Address of UART Data Register
            LDR R1, [R0]              // Read received data
            // Process the received data (e.g., store in a buffer)
            // Clear the interrupt flag (if required by hardware)
            POP {R0-R3, LR}           // Restore registers
            BX LR                     // Return from interrupt
        ```
    4.  **Enable Interrupts Globally:** Ensure interrupts are enabled in the processor (e.g., using `CPSIE I` on ARM Cortex-M).

Now, the processor can execute other tasks. When data arrives at the UART, it generates an interrupt, the processor switches to the `UART_RX_ISR`, reads the data, and then returns to where it left off.

### ARM Exception Model (Focus on Cortex-M)

The ARM Cortex-M architecture has a well-defined exception model for efficient handling of interrupts and exceptions.

*   **Vector Table:** Located at a configurable address (often 0x00000000 or specified in the system control block). The first entry (index 0) is typically the Reset handler. Subsequent entries correspond to NMI, HardFault, and then a series of peripheral interrupts (IRQ0, IRQ1, etc.).
*   **NVIC (Nested Vectored Interrupt Controller):**
    *   **Vectored:** Each interrupt has its own dedicated entry in the vector table, eliminating the need for polling within the interrupt dispatcher.
    *   **Nested:** Supports programmable priorities, allowing higher-priority interrupts to preempt lower-priority ones.
    *   **Masking:** Allows individual interrupts to be enabled or disabled.
    *   **Pending States:** Interrupts can be set to a "pending" state, allowing them to be serviced when their priority allows.
    *   **Processor State:** The processor automatically saves key state information (PC, PSR) when an exception occurs, making it easier to return.
    *   **Tail-Chaining:** A mechanism to efficiently chain ISRs, reducing the overhead of returning and re-entering another ISR.
    *   **Late Arriving:** The ability for a higher-priority interrupt to preempt a lower-priority ISR even if the lower-priority ISR has already started.

### Writing Assembly Code for Interrupts

#### 1. Enabling Interrupts Globally

To allow the processor to respond to interrupts, the Interrupt Disable bit (I bit) in the Application Program Status Register (APSR) needs to be cleared.

*   **Instruction:** `CPSIE I` (Set `I` bit in APSR - effectively enabling interrupts)
*   **Instruction:** `CPSID I` (Clear `I` bit in APSR - effectively disabling interrupts)

These instructions typically operate on the current processor mode's PSR.

#### 2. Configuring NVIC (Example: Enabling a specific peripheral interrupt)

This involves writing to specific registers within the NVIC.

*   **NVIC Interrupt Enable Register (NVIC_ISERx):** Writing a '1' to a specific bit enables the corresponding interrupt.
*   **NVIC Interrupt Set-Priority Register (NVIC_IPRx):** Writing a value to a specific bit field configures the priority of an interrupt. Lower numerical values usually indicate higher priority.
*   **NVIC Interrupt Clear-Enable Register (NVIC_ICERx):** Writing a '1' to a specific bit disables the corresponding interrupt.

**Example (Conceptual ARM Cortex-M Assembly - enabling IRQ0):**

```assembly
    // Assuming IRQ0 corresponds to bit 0 of ISER0
    LDR R0, =0xE000E100         // Address of NVIC_ISER0
    MOV R1, #0x01               // Enable bit 0
    STR R1, [R0]                // Write to ISER0 to enable IRQ0

    // Assuming IRQ0 priority is configured in IPR0 (bits 7:4 for IRQ0)
    // Let's set it to priority 5 (lower number = higher priority)
    LDR R0, =0xE000E400         // Address of NVIC_IPR0
    LDR R1, [R0]                // Read current IPR0 value
    MOV R2, #5                  // Priority value
    LSL R2, R2, #4              // Shift priority to bits 7:4 for IRQ0
    ORR R1, R1, R2              // OR with existing value to set priority
    STR R1, [R0]                // Write back to IPR0
```

#### 3. Writing an ISR

```assembly
    // Placeholder for the actual vector table entry for a specific IRQ
    // ... some instructions that might be part of the vector table setup ...
    B IRQ0_Handler              // Branch to the actual handler code

IRQ0_Handler:
    PUSH {R0-R7, LR}            // Save general-purpose registers and Link Register

    // --- ISR Core Logic ---
    // Check if the interrupt source flag needs clearing (e.g., UART RX status)
    LDR R0, =UART_STATUS_REG
    LDR R1, [R0]
    ANDS R1, R1, #RX_DATA_READY_MASK
    BEQ NO_DATA_READY           // If flag is not set, skip reading data

    LDR R0, =UART_DATA_REG
    LDR R1, [R0]
    // Store R1 in a global buffer or process it
    // Clear the interrupt flag if necessary (e.g., by writing to a specific register)

NO_DATA_READY:
    // --- End ISR Core Logic ---

    POP {R0-R7, LR}            // Restore registers
    SUBS LR, LR, #4            // Adjust LR for Thumb-2 instruction returning
    BX LR                      // Branch and exchange to return from interrupt
```

**Important Notes on ISRs:**

*   **Context Saving:** Crucial. Save all registers that the ISR might modify. The `PUSH {reglist, LR}` instruction is common.
*   **Return Instruction:** `BX LR` is used for returning from exceptions in ARM Cortex-M. The `LR` (Link Register) contains the return address. For interrupts, the hardware automatically loads `LR` with the return address + 4 (or 2 for Thumb). The `SUBS LR, LR, #4` (or `SUBS LR, LR, #2`) instruction before `BX LR` is sometimes needed to adjust `LR` correctly if the ISR is in Thumb mode and the interrupted code was also in Thumb mode. In practice, on Cortex-M, the `BX LR` alone is often sufficient as the hardware correctly sets up LR.
*   **Clearing Interrupt Flags:** Many peripherals require software to clear the interrupt pending flag within the peripheral's status register. Failure to do so will cause the interrupt to trigger again immediately upon return.
*   **Re-entrancy:** If an ISR can be interrupted by a higher-priority interrupt of the same type, care must be taken to ensure re-entrancy (e.g., using mutexes or careful buffer management).
*   **Stack Usage:** ISRs use the stack. Deeply nested ISRs or ISRs that call functions can consume significant stack space.

## Practice Questions and Exercises

**Multiple Choice Questions:**

1.  Which of the following is typically NOT considered an exception?
    a) Reset
    b) Division by zero
    c) Data reception from a UART
    d) Illegal instruction execution

    **Answer: c)** Data reception from a UART is a classic example of an *interrupt*, not an exception. Exceptions are synchronous and caused by the currently executing instruction.

2.  The Interrupt Vector Table (IVT) primarily contains:
    a) The addresses of ISRs
    b) The status flags of peripherals
    c) The priority levels of interrupts
    d) The interrupt enable/disable masks

    **Answer: a)** The IVT holds the starting addresses (or branch instructions) for the handlers of different exceptions and interrupts.

3.  Which ARM Cortex-M peripheral is responsible for managing interrupt priorities and enabling/disabling interrupts?
    a) SysTick Timer
    b) NVIC
    c) Program Status Register (PSR)
    d) Floating-Point Unit (FPU)

    **Answer: b)** The Nested Vectored Interrupt Controller (NVIC) handles interrupt prioritization, masking, and vectoring.

4.  When an interrupt occurs on an ARM Cortex-M processor, which of the following is automatically saved by hardware?
    a) All general-purpose registers (R0-R15)
    b) The Program Counter (PC) and Program Status Register (PSR)
    c) The stack pointer (SP) and the status register
    d) Only the Program Counter (PC)

    **Answer: b)** Hardware automatically pushes the PC and PSR onto the stack of the new processor mode. ISRs are responsible for saving other general-purpose registers if they are used.

**Short Answer Questions:**

5.  Explain the difference between an interrupt and an exception in the context of ARM processors. Provide one example of each.
    **Answer:** An **interrupt** is an asynchronous event that diverts the processor from its current execution to handle an external event or a scheduled internal event. Example: A timer expiring, data arriving at a UART. An **exception** is a synchronous event that occurs during instruction execution, usually due to an error or a deliberate system call. Example: Division by zero, executing an `SVC` instruction.

6.  Why is context saving important within an Interrupt Service Routine (ISR)?
    **Answer:** Context saving is crucial to preserve the state of the processor (the values of its registers) before the ISR modifies them. This allows the interrupted program to resume execution correctly from where it left off, without its state being corrupted by the ISR.

7.  Describe the role of the Link Register (LR) in returning from an interrupt or exception handler in ARM.
    **Answer:** When an interrupt or exception occurs, the hardware automatically loads the Link Register (LR) with the return address. The ISR uses this LR value to branch back to the instruction that would have executed next in the interrupted program, typically using an instruction like `BX LR`.

**Assembly Coding Exercise:**

8.  Write a short ARM assembly code snippet that:
    a) Disables interrupts globally.
    b) Configures a hypothetical peripheral interrupt (e.g., IRQ number 5) to have the highest priority (assuming a priority system where lower numbers are higher priority, and priority bits are contiguous).
    c) Enables the hypothetical peripheral interrupt.
    d) Enables interrupts globally.

    **Answer:** (This is a conceptual answer, register addresses and bit fields are typical for Cortex-M)

    ```assembly
    // Assume Peripheral IRQ number 5
    // Assume Priority bits are bits [7:4] for IRQ0-IRQ3, [11:8] for IRQ4-IRQ7, etc.
    // For IRQ5, assume priority is set in bits [11:8] of NVIC_IPR2 (0xE000E408)
    // Assume IRQ5 enable is bit 5 of NVIC_ISER0 (0xE000E100)

    .global enable_and_set_high_priority_irq5
    .thumb

    enable_and_set_high_priority_irq5:
        // a) Disable interrupts globally
        CPSID I

        // b) Configure IRQ5 with highest priority (e.g., priority level 0)
        //    Target: Set bits [11:8] in 0xE000E408 to 0x00
        LDR R0, =0xE000E408         // Address of NVIC_IPR2
        MOV R1, #0x00               // Highest priority value (0)
        LSL R1, R1, #8              // Shift to bits [11:8] for IRQ5
        STR R1, [R0]                // Write priority to IPR2

        // c) Enable the hypothetical peripheral interrupt (IRQ5)
        //    Target: Set bit 5 in 0xE000E100 to 0x01
        LDR R0, =0xE000E100         // Address of NVIC_ISER0
        MOV R1, #0x20               // Bit 5 set (1 << 5)
        STR R1, [R0]                // Write to ISER0 to enable IRQ5

        // d) Enable interrupts globally
        CPSIE I

        BX LR                       // Return from function
    ```

## Important Points to Remember

*   **Interrupts vs. Exceptions:** Understand the asynchronous (interrupts) vs. synchronous (exceptions) nature.
*   **Vector Table:** The mapping from interrupt/exception number to handler address is critical.
*   **NVIC:** The workhorse for interrupt management on Cortex-M, handling prioritization and masking.
*   **Context Saving:** Always save registers used by an ISR before modifying them. The PC and PSR are saved automatically by hardware.
*   **Return from Interrupt:** Use `BX LR` (potentially with `SUBS LR, LR, #offset`) correctly.
*   **Interrupt Flags:** Remember to clear peripheral interrupt flags within your ISRs if required by the hardware.
*   **Efficiency:** Interrupts are key to efficient IO, avoiding constant polling.
*   **Global Interrupt Enable:** The `CPSIE I` instruction is necessary to allow interrupts to be serviced.
