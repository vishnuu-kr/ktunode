# ARM Architecture and Programming: Module 4 - I/O Programming in Assembly: Interrupts and Exceptions

## Topic: Interrupt-Driven I/O

---

### **Introduction**

Traditional I/O programming often relies on **polling**, where the CPU repeatedly checks the status of an I/O device. This is inefficient as the CPU spends a significant amount of time waiting for the device to be ready, wasting valuable processing cycles. **Interrupt-driven I/O** offers a more efficient alternative by allowing I/O devices to signal the CPU when they require attention. This frees up the CPU to perform other tasks while waiting for I/O events.

This topic focuses on how interrupt-driven I/O works in the context of ARM architecture, particularly with Cortex-M microcontrollers, and how to implement it in assembly.

---

### **1. Understanding Interrupts**

**Definition:** An **interrupt** is a signal from a hardware device or software to the processor, indicating an event that requires immediate attention. When an interrupt occurs, the processor suspends its current execution, saves its state, and transfers control to a special routine called an **Interrupt Service Routine (ISR)** or **interrupt handler**.

#### **1.1 Types of Interrupts**

*   **Hardware Interrupts:** Generated by external hardware devices (e.g., timers, UARTs, keyboards, network interfaces). These are asynchronous with the CPU's instruction execution.
*   **Software Interrupts (Exceptions/Traps):** Generated by executing specific instructions within the program (e.g., division by zero, illegal instruction, system call). These are synchronous with the CPU's instruction execution.

#### **1.2 Interrupt Latency**

**Definition:** **Interrupt latency** is the time delay between the occurrence of an interrupt request and the start of the execution of the first instruction in the ISR. This is a critical parameter in real-time systems.

**Components of Interrupt Latency:**

*   **Hardware Interrupt Detection Time:** The time it takes for the interrupt controller to detect the interrupt signal.
*   **Interrupt Masking Time:** If interrupts are masked (disabled), the processor waits for them to be unmasked.
*   **CPU State Saving Time:** The time taken to push the current program state (registers, program counter, status register) onto the stack.
*   **Vector Fetch Time:** The time taken to fetch the address of the appropriate ISR from the interrupt vector table.
*   **ISR Entry Overhead:** Initial instructions within the ISR to set up its environment.

#### **1.3 Interrupt Service Routines (ISRs)**

**Definition:** An **Interrupt Service Routine (ISR)** is a dedicated piece of code that is executed when a specific interrupt occurs. Its primary purpose is to handle the event that triggered the interrupt.

**Key Characteristics of ISRs:**

*   **Fast Execution:** ISRs should be as short and efficient as possible to minimize interrupt latency and avoid delaying other critical tasks.
*   **Minimal Stack Usage:** Avoid complex function calls or large data structures within ISRs to prevent excessive stack usage.
*   **Atomic Operations:** When accessing shared resources (data that can be accessed by both the main program and ISRs), ensure that these accesses are atomic to prevent race conditions.
*   **No Blocking Operations:** ISRs should not perform operations that might block indefinitely, such as waiting for user input without a timeout.
*   **Return to Main Program:** After completing its task, the ISR must restore the CPU's state and return control to the interrupted program.

### **2. Interrupt Handling Mechanism in ARM Cortex-M**

ARM Cortex-M processors use a sophisticated interrupt handling mechanism based on the **Nested Vectored Interrupt Controller (NVIC)**.

#### **2.1 Nested Vectored Interrupt Controller (NVIC)**

**Definition:** The NVIC is a dedicated hardware block that manages all interrupts in a Cortex-M system. It is responsible for prioritizing interrupts, enabling/disabling them, and routing them to the appropriate ISRs.

**Key Features of NVIC:**

*   **Vectored Interrupts:** Each interrupt source has a unique vector address. This eliminates the need for software to poll interrupt sources to identify the interrupt source.
*   **Prioritization:** The NVIC allows assigning different priority levels to various interrupts. Higher priority interrupts can preempt lower priority interrupts.
*   **Nesting:** An ISR can be interrupted by a higher-priority interrupt. This enables real-time systems to respond to critical events promptly.
*   **Configurability:** The number of interrupts, their priorities, and enable/disable states are configurable.

#### **2.2 Interrupt Vector Table**

**Definition:** The **interrupt vector table** is a table in memory that stores the starting addresses of all ISRs. The first entry in the vector table typically points to the Reset Handler.

**How it Works:** When an interrupt occurs, the NVIC uses the interrupt's identifier to look up its corresponding vector address in the interrupt vector table. This address is then loaded into the Program Counter (PC), transferring control to the ISR.

#### **2.3 Processor Mode and Stack Management**

When an interrupt occurs, the ARM Cortex-M processor automatically:

1.  **Saves Context:** The processor automatically pushes key registers (PC, PSR - Program Status Register) onto the **process stack** (MSP) or the **main stack** (PSP) depending on the current stack pointer in use.
2.  **Changes Processor Mode:** The processor switches to **Handler Mode**.
3.  **Sets Interrupt Mask:** The interrupt mask bits in the PSR are set to disable further interrupts of equal or lower priority.

**Retrieving Context:** At the end of an ISR, the processor automatically pops the saved context from the stack to resume the interrupted program.

#### **2.4 Exception Entry and Return**

*   **Exception Entry:** When an interrupt occurs, the processor automatically performs the context saving steps described above.
*   **Exception Return:** The `BX LR` (Branch and Exchange to Link Register) instruction is typically used at the end of an ISR. The Link Register (LR) at this point holds the return address saved by the processor. The `BX` instruction not only branches to the return address but also switches the processor back to its previous mode and restores the saved context from the stack.

### **3. Implementing Interrupt-Driven I/O in Assembly**

Implementing interrupt-driven I/O in assembly involves several steps:

#### **3.1 Setting up the Interrupt Vector Table**

You need to define the interrupt vector table in your assembly code. Each entry will be a `.word` directive containing the address of the corresponding ISR.

**Example (Conceptual):**

```assembly
.section .vectors
  .long  Reset_Handler       // Reset Vector
  .long  Undef_Handler       // Undefined Instruction Handler
  .long  SVC_Handler         // Supervisor Call Handler
  .long  Prefetch_Abort_Handler
  .long  Data_Abort_Handler
  .long  Unused_Handler
  .long  IRQ_Handler         // IRQ Handler (for external interrupts)
  .long  FIQ_Handler         // FIQ Handler (Fast Interrupt Request)

  // ... other exception vectors ...

  // Peripheral Interrupt Vectors (example for Timer 0)
  .long  TIM0_IRQHandler     // Timer 0 Interrupt Handler
```

#### **3.2 Writing an Interrupt Service Routine (ISR)**

An ISR in assembly should:

1.  **Save General-Purpose Registers:** Since the processor only automatically saves PC and PSR, you must manually save any general-purpose registers (R0-R3, R4-R12) that your ISR will use.
2.  **Handle the Interrupt:** Perform the necessary I/O operations or data processing.
3.  **Acknowledge the Interrupt:** Some peripherals require the interrupt to be explicitly cleared in their status registers to prevent re-triggering.
4.  **Restore General-Purpose Registers:** Restore the saved registers in the reverse order they were saved.
5.  **Return:** Use `BX LR` to return from the ISR.

**Example ISR (Conceptual for a Timer Interrupt):**

```assembly
.section .text
.global TIM0_IRQHandler

TIM0_IRQHandler:
  // Save registers used by the ISR
  push {r0-r3, lr}      // Save R0-R3 and the return address (LR)

  // --- ISR Logic ---
  // Example: Toggle an LED or read data from a peripheral
  ldr r0, =LED_PORT       // Load address of LED port
  ldr r1, [r0]            // Read current LED state
  eor r1, r1, #0x01       // Toggle the least significant bit (assuming LED is bit 0)
  str r1, [r0]            // Write back to LED port

  // Acknowledge the interrupt (example: clear a status flag in the timer)
  ldr r0, =TIMER_STATUS_REG
  ldr r1, [r0]
  bic r1, r1, #0x01       // Clear the interrupt pending bit
  str r1, [r0]

  // --- End of ISR Logic ---

  // Restore registers
  pop {r0-r3, pc}        // Restore R0-R3 and load LR into PC for return
                         // (pc is automatically updated by pop)
```

**Important Note:** In the example above, `pop {r0-r3, pc}` is a common shortcut. When `PC` is the destination of a `POP` operation in ARM, it signifies an exception return. The processor automatically restores the `LR` into the `PC` and handles the mode switch and stack pointer adjustment.

#### **3.3 Configuring the NVIC**

You need to configure the NVIC to enable and set the priority of the desired interrupts. This involves writing to specific control registers within the NVIC.

**Key NVIC Registers (Cortex-M):**

*   **NVIC_ISERx (Interrupt Set-Enable Registers):** Used to enable individual interrupts. Writing a '1' to a specific bit enables the corresponding interrupt.
*   **NVIC_ICERx (Interrupt Clear-Enable Registers):** Used to disable individual interrupts. Writing a '1' to a specific bit disables the corresponding interrupt.
*   **NVIC_IPRx (Interrupt Priority Registers):** Used to set the priority level for each interrupt. Lower numerical values typically indicate higher priority (this depends on the implementation, but is standard for Cortex-M).
*   **NVIC_ISPRx (Interrupt Set-Pending Registers):** Used to manually set an interrupt as pending (useful for testing).
*   **NVIC_ICPRx (Interrupt Clear-Pending Registers):** Used to clear a pending interrupt.

**Example Configuration (Conceptual Assembly):**

```assembly
.section .text
.global setup_interrupts

setup_interrupts:
  // Enable Timer 0 interrupt (assuming it's interrupt number 16)
  // NVIC_ISER0 register controls interrupts 0-31
  mov r0, #0x00010000     // Set the 16th bit (for interrupt 16)
  ldr r1, =NVIC_ISER0_ADDRESS
  str r0, [r1]            // Write to NVIC_ISER0 to enable IRQ16

  // Set priority for Timer 0 interrupt (e.g., priority level 5)
  // NVIC_IPR0 register controls priorities for interrupts 0-3
  // NVIC_IPR1 register controls priorities for interrupts 4-7, etc.
  // For interrupt 16, we'd need to find the correct IPR register and bit field.
  // Let's assume interrupt 16 uses a specific bit field in IPR4.
  // This part is highly dependent on the specific microcontroller's memory map.

  // A simplified conceptual example for setting priority:
  // ldr r0, =NVIC_IPR_REGISTER_FOR_IRQ16
  // ldr r1, [r0]
  // bic r1, r1, #0xFF000000 // Clear existing priority bits for IRQ16
  // mov r2, #5              // Desired priority level
  // shl r2, r2, #24         // Shift priority to correct position
  // orr r1, r1, r2          // Set the new priority
  // str r1, [r0]

  // Enable global interrupts (if not already enabled by default after reset)
  // This is often done by clearing the PRIMASK or FAULTMASK registers.
  // For Cortex-M, setting the PRIMASK to 0 (unmasked) is common.
  // The processor automatically masks interrupts upon entry to handler mode.
  // The exception return will unmask them according to their priority.

  bx lr                   // Return from setup function

```

### **4. Advantages of Interrupt-Driven I/O**

*   **Increased CPU Efficiency:** The CPU is not tied up polling devices and can perform other tasks, leading to better overall system throughput.
*   **Faster Response Times:** Critical events can be handled immediately when they occur, improving the responsiveness of the system.
*   **Simpler Main Loop:** The main program loop can focus on its primary tasks, with I/O handled asynchronously by ISRs.
*   **Reduced Power Consumption:** The CPU can spend more time in low-power sleep modes when not actively processing interrupts.

---

### **5. Disadvantages and Considerations**

*   **Complexity:** Implementing interrupt-driven I/O requires careful management of shared resources and potential race conditions.
*   **Interrupt Latency:** Understanding and minimizing interrupt latency is crucial for real-time applications.
*   **Reentrancy:** If an ISR itself can be interrupted by another interrupt, the ISR must be designed to be reentrant (i.e., it can be safely called multiple times concurrently).
*   **Stack Overflow:** Excessive stack usage within ISRs can lead to stack overflow, causing program crashes.

### **6. Practice Questions and Exercises**

**Question 1:** Define interrupt-driven I/O and contrast it with polling. What are the primary benefits of using interrupt-driven I/O?

**Answer:** Interrupt-driven I/O is an I/O handling technique where I/O devices signal the CPU when they require attention, rather than the CPU repeatedly checking their status (polling). The primary benefits include increased CPU efficiency, faster response times, simpler main program loops, and potentially reduced power consumption.

**Question 2:** What is the role of the NVIC in an ARM Cortex-M microcontroller?

**Answer:** The NVIC (Nested Vectored Interrupt Controller) is a hardware block responsible for managing all interrupts. It handles interrupt prioritization, enabling/disabling interrupts, routing them to the correct ISRs via the vector table, and managing interrupt nesting.

**Question 3:** What is interrupt latency, and what factors contribute to it?

**Answer:** Interrupt latency is the time between an interrupt request occurring and the execution of the first instruction of its ISR. Factors include hardware detection time, interrupt masking, CPU context saving, vector fetch time, and ISR entry overhead.

**Question 4:** You are writing an assembly program for a microcontroller and need to create an ISR for a button press.
    *   What general-purpose registers would you typically save before handling the button press?
    *   What instruction would you use to return from the ISR?
    *   What is a crucial step you must perform within the ISR to prevent the same button press from being processed multiple times if the interrupt is still pending?

**Answer:**
    *   You would typically save registers like R0-R3 and potentially R4-R12 if your ISR uses them. The Link Register (LR) is also implicitly saved by the processor's exception entry mechanism but is often explicitly pushed and popped along with other registers in assembly ISRs for clarity and proper return.
    *   You would use `BX LR` to return from the ISR.
    *   You must acknowledge the interrupt by clearing the interrupt pending flag in the relevant peripheral's status register.

**Question 5 (Hands-on - Conceptual):** Write a conceptual assembly snippet for an ISR that toggles an LED connected to GPIO port A, bit 5, when a timer interrupt occurs. Assume the timer interrupt is number 20.

**Conceptual Assembly Snippet:**

```assembly
.section .text
.global TIMER_IRQHandler

TIMER_IRQHandler:
  push {r0, r1, lr}     // Save used registers and LR

  // Toggle LED on GPIO Port A, Bit 5
  ldr r0, =GPIO_PORTA_ADDRESS  // Address of GPIO Port A data register
  ldr r1, [r0]                 // Read current state
  eor r1, r1, #(1 << 5)        // Toggle bit 5
  str r1, [r0]                 // Write back new state

  // Acknowledge Timer Interrupt (assuming a specific status register bit)
  ldr r0, =TIMER_STATUS_REG
  ldr r1, [r0]
  bic r1, r1, #(1 << 0)       // Clear interrupt flag (assuming bit 0)
  str r1, [r0]

  pop {r0, r1, pc}      // Restore registers and return

// --- Initialization Snippet (Conceptual) ---
.section .text
.global init_timer_interrupt

init_timer_interrupt:
  // Enable Timer Interrupt (assuming IRQ number 20)
  // IRQ 20 would likely be in NVIC_ISER1 register
  mov r0, #(1 << (20 - 32))  // Bit 20-32 = bit 0 in ISER1
  ldr r1, =NVIC_ISER1_ADDRESS
  orr r0, r0, [r1]           // Set the bit to enable
  str r0, [r1]

  // Set Timer Interrupt Priority (Conceptual - depends on exact register mapping)
  // Assume it's priority 3 and uses bits 24-31 of some IPR register

  bx lr
```

### **7. Important Points to Remember**

*   **Atomic Operations:** When shared data is accessed by both the main program and ISRs, use atomic operations or disable interrupts briefly to ensure data integrity.
*   **Minimal ISR Code:** Keep ISRs as short and fast as possible. Offload complex processing to the main loop or separate tasks.
*   **Register Saving:** Always save and restore registers used by your ISR to avoid corrupting the state of the interrupted program.
*   **Interrupt Prioritization:** Carefully assign priorities to interrupts based on their criticality to ensure timely handling of essential events.
*   **Context Switching:** Understand that the processor automatically handles saving and restoring essential context (PC, PSR) on interrupt entry/exit.
*   **Exception Return:** `BX LR` is the standard instruction for returning from an ISR.
