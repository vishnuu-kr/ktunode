## 1. Interrupts and Exceptions

Interrupts and exceptions are fundamental mechanisms that allow a processor to respond to asynchronous events from external devices or internal conditions. They enable the processor to deviate from its normal program flow to service a specific event.

**Key Concepts:**

*   **Interrupt:** An external event, typically from a peripheral device, that signals the processor to stop its current task and attend to the event. Examples include a timer overflowing, data arriving at a UART, or a button press.
*   **Exception:** An internal event that disrupts the normal program flow. These can be caused by errors (e.g., division by zero, invalid memory access) or specific instructions (e.g., `SWI` - Software Interrupt).
*   **Interrupt Service Routine (ISR) / Exception Handler:** A dedicated block of code that is executed when a specific interrupt or exception occurs.

**Types of Exceptions in ARM Cortex-M:**

*   **Reset:** Occurs when the processor is powered on or reset.
*   **Non-Maskable Interrupt (NMI):** Highest priority interrupt, cannot be disabled by software. Used for critical events like watchdog timer expiry.
*   **HardFault:** A bus fault or memory management fault that cannot be handled by other fault handlers.
*   **Memory Management Fault (MMF):** Fault during memory access.
*   **Bus Fault (BF):** Fault during bus access (e.g., access to a reserved address).
*   **Usage Fault (UF):** Fault during instruction execution (e.g., division by zero, unaligned access).
*   **SVCall (Supervisor Call):** Software-initiated exception, typically used for system services.
*   **Debug Monitor:** Exception triggered by the debugger.
*   **PendSV (Pendable Service Call):** Lowest priority interrupt, used for context switching in operating systems.
*   **SysTick:** Timer interrupt used for timekeeping and task scheduling.
*   **External Interrupts:** Generated by peripherals via the Nested Vectored Interrupt Controller (NVIC).

**How Interrupts Work (Conceptual):**

1.  A peripheral asserts an interrupt request line.
2.  The interrupt controller (NVIC in ARM Cortex-M) detects the request.
3.  The NVIC prioritizes the interrupt and, if enabled and not masked, signals the processor core.
4.  The processor core completes its current instruction.
5.  The processor automatically saves its current state (program counter, status register) onto the stack.
6.  The processor jumps to the address of the corresponding ISR (determined by a vector table).
7.  The ISR executes, handling the event (e.g., reading data from a buffer).
8.  The ISR returns, restoring the processor's saved state.
9.  The processor resumes its interrupted task.

## 2. Thread and Handler Modes

ARM Cortex-M processors operate in different privilege levels and modes to manage execution and access to system resources. Understanding these modes is crucial for robust embedded programming.

**Key Concepts:**

*   **Processor Modes:** Distinct operational states of the processor, each with specific access rights and capabilities.
*   **Thread Mode:** The primary execution mode for user applications. Can be privileged or unprivileged.
    *   **Privileged Thread Mode:** Has full access to all system resources, including memory and special registers. Typically used by operating system kernels or low-level drivers.
    *   **Unprivileged Thread Mode:** Has restricted access to certain memory regions and special registers to prevent unintended system interference.
*   **Handler Mode:** A privileged mode used exclusively for executing exception handlers (ISRs, fault handlers, etc.). It always has full access to system resources.

**Mode Switching:**

*   The processor automatically enters **Handler Mode** when an exception occurs.
*   The processor automatically returns to **Thread Mode** when an exception handler finishes.
*   Software can explicitly switch between Thread Mode and Handler Mode using specific instructions or system calls (e.g., `SVC` instruction).

**Current Program Status Register (CPSR) / Program Status Register (PSR):**

The PSR contains bits that indicate the current processor mode, interrupt masks, and condition flags. In ARM Cortex-M, the relevant registers are `PRIMASK`, `FAULTMASK`, `BASEPRI`, and the `CONTROL` register.

*   **`CONTROL` Register:** This register explicitly defines the processor mode (Handler or Thread) and the privilege level within Thread Mode.
    *   `nLA` (n privilege level for thread mode): 0 = privileged, 1 = unprivileged.
    *   `SPSEL` (Stack Select): 0 = Main Stack Pointer (MSP), 1 = Process Stack Pointer (PSP).

**Importance:**

*   **Security:** Unprivileged Thread Mode prevents user applications from corrupting critical system data or misbehaving.
*   **Resource Management:** Privileged modes are essential for managing hardware and system resources.
*   **OS Support:** Different modes are fundamental for operating system kernels to manage tasks and exceptions.

## 3. Entering the Exception Handler

When an interrupt or exception occurs, the ARM Cortex-M processor undergoes a well-defined sequence to transfer control to the appropriate handler.

**Key Steps:**

1.  **Exception Detected:** The processor detects an exception condition (either internal or from the NVIC).
2.  **Current Instruction Completion:** The processor finishes the currently executing instruction (unless the exception prevents it, like a bus fault during instruction fetch).
3.  **State Saving:** The processor automatically pushes the following onto the stack (typically the MSP):
    *   **Return Address (PC):** The address of the next instruction to be executed in the interrupted program.
    *   **Status Register (PSR):** Contains flags and the current mode information.
    *   **Exception Link Register (LR):** The value of the LR register, which often holds `EXC_RETURN`.
4.  **Mode Change:** The processor automatically switches to **Handler Mode**.
5.  **Vector Fetch:** The processor uses the exception type (a number from 0 to 15 for Cortex-M exceptions) as an index into the **Vector Table**.
6.  **Vector Table Lookup:** The vector table, located at a specific memory address (usually 0x00000000 or configurable), contains the starting addresses of each exception handler.
7.  **Handler Entry:** The processor loads the PC with the address fetched from the vector table, effectively jumping to the start of the designated exception handler.

**Important Registers Involved:**

*   **Vector Table:** An array of 32-bit addresses. The first entry (index 0) is the initial stack pointer value, and subsequent entries are ISR addresses.
*   **`EXC_RETURN`:** A special value loaded into the LR register when an exception occurs. It contains bits that inform the processor how to return from the exception, including which stack pointer to use and whether to return to Handler or Thread mode.

**Example (Conceptual Assembly):**

Imagine an interrupt occurs. The processor might automatically perform operations akin to this:

```assembly
    ; Processor automatically does this upon exception:
    ; Save PC to stack
    ; Save PSR to stack
    ; Load LR with EXC_RETURN
    ; Switch to Handler Mode
    ; Fetch handler address from vector table based on exception type
    ; Set PC to handler address
```

## 4. Returning from the Exception Handler

Properly returning from an exception handler is as critical as entering it. It ensures that the interrupted program can resume execution without corruption.

**Key Steps:**

1.  **Handler Execution:** The ISR completes its task.
2.  **State Restoration:** The ISR must explicitly restore the processor's context that was saved upon entry. This typically involves:
    *   Popping the saved `PSR` from the stack back into the `PSR`.
    *   Popping the saved `PC` from the stack back into the `PC`.
3.  **Return Mechanism:** The return is often facilitated by a special instruction that uses the `EXC_RETURN` value in the LR register.
    *   In ARM Cortex-M, the `BX LR` (Branch and Exchange to Link Register) instruction is commonly used. When `LR` contains an `EXC_RETURN` value, `BX LR` triggers a special return sequence.
    *   The `EXC_RETURN` value tells the processor:
        *   Which stack pointer (MSP or PSP) to use for restoring the saved state.
        *   Whether to return to **Thread Mode** or **Handler Mode**.
        *   The privilege level for the return (usually to the mode it was in before the exception).

**Important Considerations:**

*   **Context Saving/Restoring:** If the ISR uses any registers that are not automatically saved by the hardware upon exception entry, the ISR *must* save and restore them manually before returning. This is particularly important for general-purpose registers (R0-R3, R4-R11).
*   **Stack Frame:** The automatically pushed registers form an "exception stack frame." The ISR needs to ensure it restores these correctly.
*   **`BX LR` Instruction:** This is the standard way to return from most exception handlers.

**Example (Conceptual Assembly for ISR End):**

```assembly
; Inside the ISR:
; ... ISR code ...

; Manually save/restore any additional registers used by ISR (e.g., R4-R11)
    PUSH {R4-R7} ; Example of saving additional registers

; ...
; Restore additional registers
    POP {R4-R7} ; Example of restoring

; Return from exception handler
    POP {R0-R3, R12, PC} ; Restores PC, LR, PSR (and R0-R3, R12 if they were pushed)
                        ; The POP instruction directly loads the PC from the stack.
                        ; The specific registers depend on the stack frame generated by hardware.
                        ; For Cortex-M, a POP {..., PC} is typical after using BX LR.
                        ; However, often the hardware automatically pushes enough,
                        ; so a simple BX LR is sufficient if no extra registers were pushed.

; A more common and simplified return in Cortex-M:
; The LR register automatically holds EXC_RETURN.
; The POP {..., PC} instruction implicitly uses the saved PC and PSR from the stack.
; The EXC_RETURN value in LR guides the mode and stack pointer for the return.
    BX LR
```

**Note:** The exact sequence of `POP` instructions to restore the context depends on the specific Cortex-M processor and the type of exception stack frame. For many ISRs, the processor automatically pushes enough context that a simple `BX LR` suffices for the return. However, if the ISR modifies registers not automatically saved, it must explicitly push and pop those.

## 5. Latency Reduction Techniques

Minimizing the time it takes from an interrupt request to the start of ISR execution (interrupt latency) is crucial for real-time systems.

**Key Concepts:**

*   **Interrupt Latency:** The delay between an interrupt request being asserted and the first instruction of the ISR being executed.
*   **Interrupt Response Time:** The time from interrupt assertion to the completion of the ISR's task.

**Techniques for Latency Reduction:**

1.  **Minimize ISR Execution Time:**
    *   **Keep ISRs Short and Fast:** Perform only essential work in the ISR. Defer longer tasks to the main loop or a separate thread.
    *   **Avoid Blocking Operations:** Do not perform operations like polling loops or long delays within an ISR.
    *   **Use Assembly for Critical Sections:** For very time-sensitive operations, writing small parts of the ISR in assembly can be more efficient than C.
    *   **Register Usage:** Minimize register saving and restoring by carefully choosing which registers your ISR uses. Prefer registers that are automatically saved by the hardware.

2.  **Optimize the Processor's Response:**
    *   **Disable Interrupts Sparingly:** While interrupts are disabled during critical sections, keep these sections as short as possible.
    *   **Prioritize Interrupts:** Configure the NVIC to assign higher priorities to time-critical interrupts. This ensures they preempt lower-priority interrupts.
    *   **Enable Interrupts at the Earliest Opportunity:** Once the processor is in Handler Mode and the critical section is finished, enable interrupts to allow preemption by higher-priority events.

3.  **Efficient Context Switching:**
    *   **Minimal Stack Operations:** The automatic stack operations for context saving/restoring are usually efficient. Avoid unnecessary pushing/popping of registers within the ISR.
    *   **Floating-Point Unit (FPU):** If an FPU is used, its context saving/restoring can add significant latency. Ensure it's managed efficiently or disabled if not strictly needed by the ISR.

4.  **Hardware Features:**
    *   **Vector Table Offset Register (VTOR):** If the vector table is not at address 0, ensure VTOR is configured correctly. Delays in finding the vector table increase latency.
    *   **NVIC Configuration:** Efficiently configure interrupt enables, priorities, and grouping.

## 6. Priorities and Nested Exceptions

The Nested Vectored Interrupt Controller (NVIC) is central to managing interrupts in ARM Cortex-M processors. It allows for prioritization and the handling of nested interrupts.

**Key Concepts:**

*   **Interrupt Priority:** A numerical value assigned to each interrupt that determines its order of execution when multiple interrupts occur simultaneously or when a higher-priority interrupt arrives while a lower-priority one is being serviced. Lower numbers typically represent higher priorities.
*   **Priority Grouping:** The NVIC allows for grouping interrupts. A priority group divides the priority bits into sub-priority bits and preemption bits.
    *   **Preemption Bits:** Determine if an interrupt can preempt a lower-priority interrupt currently being serviced.
    *   **Sub-priority Bits:** Determine the order of execution among interrupts with the same preemption priority.
*   **Nested Exceptions:** When a higher-priority interrupt occurs while a lower-priority interrupt is being serviced, the processor can suspend the lower-priority ISR and start executing the higher-priority ISR. This is called nesting.
*   **`BASEPRI` Register:** A special register that allows software to mask all interrupts below a certain priority level. This is crucial for implementing critical sections and preventing certain interrupts from preempting essential code.

**How Priorities and Nesting Work:**

1.  Multiple interrupts are requested.
2.  The NVIC evaluates the priority of each pending interrupt based on its configuration.
3.  The highest-priority enabled interrupt is selected for service.
4.  If the selected interrupt is of higher priority than the currently executing ISR, the processor suspends the current ISR (saving its context) and starts the new, higher-priority ISR.
5.  When the higher-priority ISR completes, the processor returns to the lower-priority ISR where it left off.
6.  The `BASEPRI` register can be used to mask interrupts: if an ISR sets `BASEPRI` to a specific priority level, any interrupts with a priority *lower* than `BASEPRI` will be ignored until `BASEPRI` is cleared or set to a lower priority.

**Configuration in ARM Cortex-M:**

*   **NVIC Interrupt Priority Register (IPR):** Used to set the priority of each interrupt source.
*   **NVIC Priority Group Register (AIRCR - Application Interrupt and Reset Control Register):** Used to configure the priority grouping scheme.

**Example Scenario:**

*   Timer Interrupt (Priority 3) is active.
*   UART Interrupt (Priority 2) arrives.
*   Since UART has higher priority (lower number), the Timer ISR is suspended, and the UART ISR executes.
*   Once the UART ISR finishes, execution resumes in the Timer ISR.

**Using `BASEPRI` for Critical Sections:**

```assembly
; Critical section start
    MOV R0, #0x30  ; Set BASEPRI to a priority level (e.g., 0x30)
    MSR BASEPRI, R0

; --- Critical Section Code ---
; No interrupts with priority < 0x30 can preempt here

; Critical section end
    MOV R0, #0     ; Clear BASEPRI to allow all interrupts
    MSR BASEPRI, R0
```

## 7. Synchronization

In a multi-tasking or interrupt-driven environment, ensuring that shared data is accessed and modified atomically (without interference from other tasks or ISRs) is crucial. This is achieved through synchronization mechanisms.

**Key Concepts:**

*   **Shared Resources:** Data, memory locations, or peripherals that can be accessed by multiple execution contexts (e.g., main loop and an ISR, or two different ISRs).
*   **Race Condition:** A situation where the outcome of a program depends on the unpredictable timing of multiple threads or ISRs accessing a shared resource.
*   **Atomicity:** An operation that is guaranteed to complete without interruption.
*   **Critical Section:** A block of code that accesses a shared resource and must be executed atomically.

**Synchronization Techniques in Assembly:**

1.  **Disabling/Enabling Interrupts:**
    *   The most common method for synchronization between ISRs and the main loop.
    *   **Method:** Disable all interrupts before entering a critical section and re-enable them afterward.
    *   **How:**
        *   Use `CPSID I` (Clear Interrupt Enable bit in the Application Program Status Register - PRIMASK) to disable interrupts.
        *   Use `CPSIE I` (Set Interrupt Enable bit) to re-enable interrupts.
        *   **Crucially:** Save the state of the interrupt mask (e.g., `PRIMASK` or `FAULTMASK`) before disabling, and restore it before exiting the critical section. This ensures that if interrupts were already disabled, they remain disabled.
    *   **Caveat:** This approach can increase interrupt latency for other events and should be used sparingly.

2.  **Using `BASEPRI` Register:**
    *   A more refined approach than disabling all interrupts.
    *   **Method:** Set the `BASEPRI` register to a priority level that masks all interrupts that could potentially access the shared resource.
    *   **How:** As shown in the "Priorities and Nested Exceptions" section, load a priority level into `BASEPRI` using `MSR BASEPRI`. Clear `BASEPRI` to 0 to re-enable all interrupts.
    *   **Advantage:** Allows higher-priority interrupts to still preempt the current execution context if they are not masked by `BASEPRI`.

3.  **Atomic Instructions (Limited in Assembly):**
    *   Some ARM architectures offer atomic read-modify-write instructions (e.g., `LDREX` and `STREX`). These are useful for synchronizing between multiple processor cores or in more complex scenarios but are less common for basic ISR/main loop synchronization. They are typically used in C for multithreading.

**Example: Synchronizing a Counter Accessed by ISR and Main Loop**

Let's say a global variable `counter` is incremented by an ISR and read by the main loop.

```assembly
; Global variable declaration (conceptual)
.bss
counter: .word 0

; Function to increment counter (e.g., in an ISR)
increment_counter:
    ; --- Critical Section Start ---
    MRS R0, PRIMASK      ; Read current interrupt mask
    PUSH {R0, LR}        ; Save mask and LR onto stack
    CPSID I              ; Disable interrupts

    LDR R1, =counter     ; Load address of counter
    LDR R2, [R1]         ; Load current value
    ADD R2, R2, #1       ; Increment value
    STR R2, [R1]         ; Store incremented value

    ; --- Critical Section End ---
    POP {R0, LR}         ; Restore saved mask and LR
    MSR PRIMASK, R0      ; Restore original interrupt mask
    BX LR                ; Return

; Function to read counter (e.g., in main loop)
read_counter:
    ; --- Critical Section Start ---
    MRS R0, PRIMASK
    PUSH {R0, LR}
    CPSID I

    LDR R1, =counter
    LDR R2, [R1]         ; Read the counter value

    ; --- Critical Section End ---
    POP {R0, LR}
    MSR PRIMASK, R0
    MOV R0, R2           ; Return the read value in R0
    BX LR
```

## 8. Transfer Rate and Latency

These terms are crucial when evaluating the performance of IO operations.

**Key Concepts:**

*   **Transfer Rate (Throughput):** The amount of data that can be moved per unit of time. Measured in bits per second (bps), bytes per second, KB/s, MB/s, etc.
    *   *Influenced by:* Bus width, clock speed, protocol overhead, DMA efficiency, buffer sizes.
*   **Latency:** The time delay for a single data transfer to complete, from request to reception/transmission.
    *   *Influenced by:* Interrupt latency, protocol setup time, processing time, buffer management.

**Relationship:**

*   **High Transfer Rate does not always mean Low Latency:** A system can transfer a lot of data over time (high throughput) but still have significant delays for each individual data packet (high latency).
*   **Low Latency is critical for real-time responsiveness:** For applications like control systems or audio processing, the time it takes for a single piece of data to arrive or be sent is paramount.
*   **High Transfer Rate is important for bulk data movement:** For applications like data logging or file transfers, maximizing throughput is key.

**Factors Affecting Transfer Rate and Latency in Assembly IO:**

*   **Peripheral Speed:** The inherent speed of the device (e.g., UART baud rate, SPI clock speed).
*   **Bus Speed:** The speed of the processor's internal bus connecting to peripherals.
*   **CPU Overhead:** How much CPU time is spent managing the transfer (e.g., in polling loops or ISRs).
*   **Buffer Management:** Efficiency of buffer filling and draining.
*   **DMA Usage:** DMA offloads the CPU, typically increasing transfer rate and reducing latency by allowing the CPU to perform other tasks.
*   **Interrupt Handling:** The latency of entering and exiting ISRs affects the responsiveness of interrupt-driven IO.

**Example:**

*   **UART:** High baud rate (e.g., 115200 bps) means higher potential transfer rate. Low latency for receiving a single byte is achieved with an interrupt-driven approach rather than polling.
*   **DMA:** Can achieve high transfer rates by moving data directly between peripherals and memory without CPU intervention, thus also reducing the *effective* latency for the CPU.

**From Lewis (Throughout):** Lewis discusses IO performance in terms of data rates and response times when describing various peripherals and their interfaces.

**From Zhu (Throughout):** Zhu often uses examples that highlight the trade-offs between polling and interrupt-driven IO, which directly impacts latency and transfer efficiency. DMA is also covered as a method to improve throughput.

## 9. Buffers and Queues

Buffers and queues are essential data structures for managing the flow of data between a fast processor and slower peripherals, or between different parts of a system.

**Key Concepts:**

*   **Buffer:** A temporary storage area in memory used to hold data during transfer.
    *   **Purpose:** To decouple the producer (e.g., peripheral generating data) from the consumer (e.g., CPU processing data) and to handle differences in data arrival/processing rates.
    *   **Types:**
        *   **Circular Buffer (Ring Buffer):** A fixed-size buffer implemented as if it were connected end-to-end. It uses read and write pointers that wrap around the buffer. This is highly efficient for managing streams of data.
*   **Queue:** A data structure that follows the First-In, First-Out (FIFO) principle.
    *   **Purpose:** To manage a sequence of items to be processed in the order they were received. Often implemented using one or more buffers.
    *   **Common Operations:** Enqueue (add an item), Dequeue (remove an item), IsEmpty, IsFull.

**Implementation in Assembly (Circular Buffer Example):**

A circular buffer typically requires:

*   **A memory array:** The storage for the data.
*   **A write pointer:** Index of the next available slot to write data.
*   **A read pointer:** Index of the next item to read.
*   **Buffer size:** The total capacity.
*   **Count (optional but useful):** Number of valid items in the buffer.

```assembly
; Example: Circular buffer for received bytes from UART
.bss
RX_BUFFER: .space 128     ; 128-byte buffer
RX_BUFFER_SIZE: .word 128
RX_WRITE_PTR: .word 0     ; Index for writing
RX_READ_PTR: .word 0      ; Index for reading
RX_COUNT: .word 0         ; Number of bytes in buffer

; Function to add a byte to the RX buffer (enqueue)
add_byte_to_rx_buffer:
    ; Input: R0 = byte to add
    ; Assumes critical section is managed externally or using BASEPRI

    LDR R1, =RX_BUFFER      ; Base address of buffer
    LDR R2, =RX_WRITE_PTR
    LDR R3, =RX_COUNT
    LDR R4, =RX_BUFFER_SIZE
    LDR R5, [R4]            ; Load buffer size

    LDR R4, [R3]            ; Load current count
    CMP R4, R5              ; Check if buffer is full
    BEQ buffer_full         ; Handle full buffer (e.g., discard, error)

    LDR R6, [R2]            ; Load current write pointer
    STRB R0, [R1, R6]       ; Store byte at write pointer location

    ADD R6, R6, #1          ; Increment write pointer
    CMP R6, R5              ; Check if pointer reached end
    MOVNE R6, R6            ; Keep incremented value if not wrapped
    MOV R6, #0              ; Reset pointer to 0 if it reached end (wrap around)
    STR R6, [R2]            ; Store updated write pointer

    ADD R4, R4, #1          ; Increment count
    STR R4, [R3]            ; Store updated count

    BX LR

; Function to get a byte from the RX buffer (dequeue)
get_byte_from_rx_buffer:
    ; Output: R0 = byte read, R1 = status (0=success, 1=empty)
    ; Assumes critical section is managed externally or using BASEPRI

    LDR R2, =RX_COUNT
    LDR R3, =RX_READ_PTR
    LDR R4, =RX_BUFFER

    LDR R5, [R2]            ; Load count
    CMP R5, #0              ; Check if buffer is empty
    MOVEQ R0, #0            ; No data
    MOVEQ R1, #1            ; Status = empty
    BEQ return_from_get

    LDR R6, [R3]            ; Load current read pointer
    LDRB R0, [R4, R6]       ; Load byte from read pointer location

    ADD R6, R6, #1          ; Increment read pointer
    CMP R6, [RX_BUFFER_SIZE] ; Check if pointer reached end
    MOVNE R6, R6
    MOV R6, #0              ; Reset pointer if wrapped
    STR R6, [R3]            ; Store updated read pointer

    SUB R5, R5, #1          ; Decrement count
    STR R5, [R2]            ; Store updated count

    MOV R1, #0              ; Status = success

return_from_get:
    BX LR
```

## 10. Double Buffering

Double buffering is a technique used to improve performance and reduce visual artifacts in graphics or data processing by using two buffers.

**Key Concepts:**

*   **Two Buffers:** Instead of one, two buffers are used.
*   **Producer/Consumer Model:** One buffer is being filled by the producer (e.g., a peripheral receiving data), while the other buffer is being processed by the consumer (e.g., the CPU or a display controller).
*   **Ping-Pong Buffering:** A common implementation where the roles of the buffers are swapped (ping and pong) after each operation.

**Benefits:**

*   **Prevents Data Corruption:** The consumer always has a complete and stable buffer to work with, even while the producer is filling the other.
*   **Reduces Latency:** The consumer can start processing as soon as a buffer is ready, without waiting for the producer to finish filling a single, potentially large, buffer.
*   **Smoother Updates:** In graphics, this prevents "tearing" or partial updates seen on the screen.

**Implementation in Assembly:**

Double buffering involves managing two sets of pointers and state indicators:

*   `BufferA`: For producer to fill.
*   `BufferB`: For consumer to process.
*   A flag or state variable to indicate which buffer is currently active for the producer/consumer.

**Example Scenario (Receive Data):**

1.  **Initial State:** Buffer A is active for receiving, Buffer B is free/ready for processing.
2.  **Interrupt Arrives:** Peripheral fills Buffer A.
3.  **Buffer Full:** Once Buffer A is full, an interrupt signals this.
4.  **Swap Buffers:**
    *   The ISR switches the active buffer for receiving to Buffer B.
    *   It signals the main loop that Buffer A is ready for processing.
5.  **Main Loop Processing:** The main loop processes Buffer A while the ISR continues to fill Buffer B.
6.  **Buffer B Full:** When Buffer B is full, it's swapped with Buffer A (which is now free).

**Assembly Considerations:**

*   Maintaining pointers for both buffers.
*   Using flags to track buffer status (empty, filling, full, processing).
*   Conditional logic to determine which buffer to access or process.

```assembly
; Conceptual double buffering for data reception
.bss
BUFFER_A: .space 256
BUFFER_B: .space 256
BUFFER_SIZE: .word 256

; Pointers and flags
WRITE_PTR_A: .word 0
WRITE_PTR_B: .word 0
READ_PTR_A: .word 0
READ_PTR_B: .word 0

; Status flags: 0 = Empty, 1 = Filling, 2 = Full, 3 = Processing
STATUS_A: .word 0
STATUS_B: .word 1 ; Start with Buffer B ready for processing, A filling

; ISR to receive data
receive_data_isr:
    ; R0 = received byte
    ; Check which buffer is currently filling (e.g., based on STATUS_A/B or a dedicated flag)

    ; Assume Buffer A is filling
    LDR R1, =BUFFER_A
    LDR R2, =WRITE_PTR_A
    LDR R3, =STATUS_A
    LDR R4, [R3]

    CMP R4, #1 ; Check if actually filling
    BNE skip_buffer_a_logic

    LDR R5, [R2] ; Get current write pointer for A
    STRB R0, [R1, R5] ; Store byte in Buffer A

    ADD R5, R5, #1
    CMP R5, [BUFFER_SIZE]
    MOVNE R5, R5
    MOV R5, #0
    STR R5, [R2] ; Update write pointer for A

    ; Check if Buffer A is now full
    CMP R5, #0 ; If write pointer wrapped around, buffer is full
    BNE skip_buffer_a_full_check
    MOV R4, #2 ; Set STATUS_A to Full
    STR R4, [R3]
    ; Signal main loop to process Buffer A

skip_buffer_a_full_check:
    ; ... similar logic for Buffer B if it were active ...

    BX LR

; Main loop to process data
process_data_loop:
    ; Check if Buffer A is full
    LDR R1, =STATUS_A
    LDR R0, [R1]
    CMP R0, #2 ; Is Buffer A full?
    BNE check_buffer_b_full

    ; Process Buffer A
    LDR R1, =BUFFER_A
    LDR R2, =READ_PTR_A
    LDR R3, =STATUS_A
    ; ... read data from Buffer A using READ_PTR_A ...

    ; Mark Buffer A as processed/empty
    MOV R0, #0 ; Set status to empty
    STR R0, [R3]
    MOV R0, #0 ; Reset read pointer
    STR R0, [R2]

    ; Swap buffers: Make Buffer B the next one to process, Buffer A available for filling
    ; (This logic is more complex, involving tracking which buffer is being filled vs processed)
    ; A common approach is to use a flag: active_buffer = A or B

check_buffer_b_full:
    ; ... check STATUS_B ...
    ; Process Buffer B if full
    ; Swap buffers

    ; Loop back
    B process_data_loop
```

**From Zhu (Chapter 5):** Zhu may use double buffering with UART reception to show how to handle continuous data streams without losing bytes.

## 11. Polled Waiting Loops

Polling is a basic method of IO handling where the processor repeatedly checks the status of a peripheral to see if it's ready for the next operation.

**Key Concepts:**

*   **Polling:** The processor actively queries the status register of a peripheral.
*   **Status Register:** A hardware register within a peripheral that indicates its current state (e.g., data available, transmission complete, busy).
*   **Waiting Loop:** A loop that continues to check a specific bit or flag in the status register until it indicates the desired condition is met.

**How it Works (Assembly Example for UART Transmit):**

To transmit a byte via UART using polling:

1.  Check the UART's status register to see if the transmit buffer is empty (ready to accept data).
2.  If the transmit buffer is not empty, loop back and check again.
3.  If the transmit buffer is empty, write the data byte to the UART's data register.
4.  Repeat for the next byte.

```assembly
; Example: Transmit a byte using polling
; R0 = byte to transmit
; R1 = address of UART Data Register (DR)
; R2 = address of UART Status Register (SR)
; R3 = mask for the Transmit Buffer Empty (TXE) flag in SR

transmit_byte_polled:
    PUSH {R0, R1, R2, R3, LR}

wait_for_tx_empty:
    LDR R4, [R2]      ; Load status register
    AND R4, R4, R3    ; Mask for TXE flag
    CMP R4, #0        ; Check if TXE flag is set (0 means empty)
    BNE wait_for_tx_empty ; If not empty, loop

    ; Transmit buffer is empty, write the data
    STRB R0, [R1]     ; Store byte to UART Data Register

    POP {R0, R1, R2, R3, LR}
    BX LR
```

**Advantages:**

*   **Simplicity:** Easy to understand and implement.
*   **No Overhead:** No interrupt vectors, ISRs, or context switching.

**Disadvantages:**

*   **Wastes CPU Cycles:** The processor spends a significant amount of time doing nothing but checking a status flag, making it unavailable for other tasks.
*   **Inefficient for Slow Peripherals:** If the peripheral is slow to become ready, the CPU is tied up for a long time.
*   **Poor Responsiveness:** Not ideal for time-critical applications where other tasks need to run concurrently.

**From Lewis (Chapter 7):** Lewis contrasts polling with interrupt-driven IO, highlighting the CPU overhead of polling.

**From Zhu (Chapter 5):** Zhu often shows polling examples as a baseline and then introduces interrupt-driven IO and DMA as more efficient alternatives.

## 12. Interrupt-Driven IO

Interrupt-driven IO is a method where the processor is signaled by a peripheral when it requires attention, rather than constantly checking its status.

**Key Concepts:**

*   **Event-Driven:** The processor reacts to events (interrupts) generated by peripherals.
*   **Interrupt Service Routine (ISR):** Code executed when an interrupt occurs.
*   **Efficiency:** Frees up the CPU to perform other tasks while waiting for peripheral events.
*   **Responsiveness:** Allows the system to react quickly to external events.

**How it Works (Assembly Example for UART Receive):**

1.  **Initialization:** Configure the UART to generate an interrupt when a byte is received (RXNE flag set). Enable this interrupt in the NVIC.
2.  **Main Loop:** The main program can perform other tasks or enter a low-power state.
3.  **Receive Interrupt:** When a byte arrives at the UART:
    *   The UART asserts an interrupt request.
    *   The NVIC routes it to the CPU.
    *   The CPU automatically saves its state and jumps to the UART receive ISR.
4.  **ISR Execution:** The ISR reads the received byte from the UART data register, typically storing it in a buffer (e.g., a circular buffer).
5.  **Return from ISR:** The ISR restores the CPU state and returns control to the main program.
6.  **Resumption:** The main program continues from where it left off.

```assembly
; Assumes UART receive interrupt is configured and enabled
; Vector table points to uart_rx_isr

uart_rx_isr:
    PUSH {R0-R3, R12, LR} ; Save general purpose registers and LR

    ; Check if it's a UART RX interrupt (if multiple interrupts share handler)
    ; (For Cortex-M, specific interrupt handlers are common)

    LDR R1, =UART_DR_ADDRESS ; Address of UART Data Register
    LDR R2, =UART_SR_ADDRESS ; Address of UART Status Register
    LDR R3, =RX_BUFFER_FULL_MASK ; Mask to check if RX data is available

    LDR R4, [R2]            ; Read status register
    AND R4, R4, R3          ; Check RXNE flag
    CMP R4, #0
    BNE byte_received       ; If RXNE is set, proceed

skip_handler:
    POP {R0-R3, R12, LR}    ; Restore registers
    BX LR                   ; Return from exception

byte_received:
    LDR R0, [R1]            ; Read the received byte from UART DR

    ; Add the byte to a circular buffer (see previous buffer example)
    ; Example: Call an assembly function to add to buffer
    BL add_byte_to_rx_buffer

    ; Clear the interrupt flag (if required by hardware)
    ; LDR R5, =UART_ICR_ADDRESS ; Interrupt Clear Register
    ; LDR R6, =UART_RXNE_INT_MASK
    ; STR R6, [R5]

    POP {R0-R3, R12, LR}    ; Restore registers
    BX LR                   ; Return from exception
```

**Advantages:**

*   **CPU Efficiency:** CPU is free to do other work.
*   **Fast Response:** Reacts quickly to peripheral events.
*   **Scalability:** Works well with multiple peripherals.

**Disadvantages:**

*   **Increased Complexity:** Requires understanding of interrupts, ISRs, vector tables, and context saving.
*   **Potential for Nested Interrupts:** Needs careful management of priorities.

**From Lewis (Chapter 7):** Lewis dedicates significant coverage to interrupt-driven IO, explaining its architecture and benefits over polling.

**From Zhu (Chapter 5):** Zhu provides extensive assembly examples of interrupt-driven IO for various peripherals like UART, Timers, and GPIOs.

## 13. Direct Memory Access (DMA)

DMA is a hardware feature that allows data transfers between peripherals and memory (or between memory locations) to occur without direct involvement of the CPU.

**Key Concepts:**

*   **Hardware Offload:** DMA controller handles the data transfer, freeing the CPU for other tasks.
*   **High Throughput:** DMA can often perform transfers much faster than software-controlled methods, especially for large blocks of data.
*   **Low CPU Overhead:** The CPU only needs to configure the DMA controller and can then move on to other operations.
*   **Transfer Modes:**
    *   **Memory-to-Memory:** Copying data between two locations in RAM.
    *   **Peripheral-to-Memory:** Moving data from a peripheral's buffer to RAM (e.g., ADC data, UART received data).
    *   **Memory-to-Peripheral:** Moving data from RAM to a peripheral's buffer (e.g., SPI transmit data, DAC output).

**How DMA Works:**

1.  **CPU Configuration:** The CPU programs the DMA controller with:
    *   Source address.
    *   Destination address.
    *   Transfer size (number of bytes/words).
    *   Transfer mode (e.g., increment/decrement addresses, auto-reloading).
    *   Peripheral request signal (if linked to a peripheral).
    *   Interrupt settings (e.g., interrupt on completion).
2.  **Transfer Initiation:** The DMA controller starts the transfer based on the configuration. This could be triggered by a peripheral request or a software start command.
3.  **Data Movement:** The DMA controller accesses the bus, reads data from the source, and writes it to the destination, incrementing/decrementing addresses as configured.
4.  **Completion:** Once the specified number of data units have been transferred, the DMA controller can:
    *   Generate an interrupt to notify the CPU.
    *   Stop or automatically reload for subsequent transfers.

**Assembly Considerations for DMA:**

*   **DMA Controller Registers:** Understanding and programming the specific DMA controller's registers (control, status, address pointers, transfer counts). These are highly processor-specific.
*   **Enabling DMA:** Ensuring the DMA controller is powered on and clocked.
*   **Interrupt Handling:** Setting up an ISR to handle DMA completion interrupts for confirmation or to start the next transfer.

**Example Scenario: ADC to Memory Transfer using DMA**

1.  **Configure ADC:** Set up ADC to generate a DMA request when a conversion is complete.
2.  **Configure DMA:**
    *   Set DMA source to ADC data register address.
    *   Set DMA destination to a buffer in RAM.
    *   Set transfer size to the number of samples required.
    *   Enable DMA transfer completion interrupt.
3.  **Start ADC:** Trigger the ADC to begin conversions.
4.  **CPU Continues:** The CPU can now perform other tasks.
5.  **DMA Transfer:** As ADC conversions complete, the DMA controller automatically reads the data and places it in the RAM buffer.
6.  **DMA Interrupt:** When all samples are transferred, the DMA controller triggers an interrupt.
7.  **ISR:** The DMA completion ISR can signal the main program that the data is ready for processing.

**From Lewis (Chapter 7):** Lewis discusses DMA as an advanced IO technique for efficient data transfer, especially for high-bandwidth peripherals.

**From Zhu (Chapter 7: DMA Controller):** Zhu provides dedicated chapters and examples on how to program the DMA controller on specific ARM Cortex-M microcontrollers, including detailed register manipulation in assembly.

## Practice Questions and Answers

**Question 1:** What is the primary difference between a 'Thread Mode' and a 'Handler Mode' in ARM Cortex-M? Explain why this distinction is important.

**Answer 1:**
*   **Thread Mode:** This is the normal execution mode for user applications and the operating system kernel. It can operate in privileged or unprivileged states.
*   **Handler Mode:** This is a special, always-privileged mode used exclusively for executing exception handlers (Interrupt Service Routines, fault handlers).
*   **Importance:** This distinction is crucial for system stability and security. Handler Mode's privileged status ensures that critical exception handling code can access all system resources and cannot be corrupted by user applications. Thread Mode's unprivileged option protects the system from misbehaving applications.

**Question 2:** A real-time system requires a task to respond to an event within 10 microseconds. What assembly programming techniques discussed in this module would be most relevant for minimizing the delay between the event occurring and the task beginning its execution?

**Answer 2:**
The most relevant techniques for minimizing this delay (interrupt latency) are:
*   **Prioritization:** Assigning a high priority to the interrupt associated with the event using the NVIC.
*   **Short ISRs:** Ensuring the ISR that handles the event is as short and fast as possible, potentially using assembly for critical, time-sensitive operations.
*   **Efficient Context Saving/Restoring:** Minimizing the number of registers saved/restored by the ISR.
*   **Using `BASEPRI`:** To prevent lower-priority interrupts from delaying the response to the critical event, and to protect critical sections within the ISR.
*   **Avoiding Polling:** Relying on interrupt-driven IO rather than polling loops, which have higher inherent latency and CPU overhead.

**Question 3:** Explain the purpose of the `EXC_RETURN` value and how it's used by the processor when returning from an exception handler using the `BX LR` instruction.

**Answer 3:**
The `EXC_RETURN` value is automatically placed into the Link Register (LR) by the processor when an exception occurs. It contains special bit patterns that inform the processor how to return. When the `BX LR` instruction is executed, the processor interprets these bits to:
1.  **Determine the Stack Pointer:** Indicate whether the main stack pointer (MSP) or the process stack pointer (PSP) should be used to restore the saved context (PC, PSR, etc.).
2.  **Determine the Return Mode:** Specify whether to return to Handler Mode or Thread Mode.
3.  **Determine the Privilege Level:** Inform the processor about the privilege level of the mode it should return to.
This allows `BX LR` to correctly restore the processor's state and resume execution in the appropriate mode.

**Question 4:** You need to implement a mechanism to prevent a critical section of code from being interrupted by any UART transmit interrupts. You are using a microcontroller where UART transmit interrupts have a priority value of 5 (lower number = higher priority). Describe how you would use assembly to achieve this synchronization.

**Answer 4:**
The most efficient way to achieve this is by using the `BASEPRI` register.
1.  **Read Current `PRIMASK`:** Before modifying interrupts, read the current state of the interrupt mask using `MRS R0, PRIMASK`. This is important for restoring the original interrupt state later.
2.  **Save `PRIMASK` and `LR`:** Push the saved `PRIMASK` state and the Link Register (`LR`) onto the stack: `PUSH {R0, LR}`.
3.  **Disable Lower Priority Interrupts:** Load the `BASEPRI` register with a value that masks interrupts with a priority *lower* than or equal to 5. For example, if priorities are 0-7, you might set `BASEPRI` to `0x05` (or a value that corresponds to priority 5).
    ```assembly
    MOV R0, #0x05       ; Example: Mask interrupts with priority 5 and above
    MSR BASEPRI, R0
    ```
4.  **Execute Critical Section:** Perform the critical operations. During this time, any UART transmit interrupts (priority 5) or lower-priority interrupts will not preempt the current code.
5.  **Restore `PRIMASK`:** Restore the original interrupt mask state by popping the saved value and writing it back: `POP {R0, LR}` and `MSR PRIMASK, R0`. This ensures that if interrupts were already disabled or partially masked, that state is preserved.

**Question 5:** What are the main advantages of using DMA for data transfer compared to interrupt-driven IO?

**Answer 5:**
The main advantages of DMA over interrupt-driven IO are:
*   **CPU Offload:** DMA transfers data directly between peripherals and memory without CPU intervention. In interrupt-driven IO, the CPU must execute an ISR for each transfer or block of transfers.
*   **Higher Throughput:** DMA controllers are hardware-optimized for moving blocks of data, often achieving higher transfer rates than software-managed interrupt transfers.
*   **Lower CPU Overhead:** While interrupt-driven IO requires CPU cycles for ISR execution and context switching for each interrupt, DMA requires only initial configuration. Once configured, the CPU is free to perform other tasks, leading to better overall system utilization.

## Important Points to Remember

*   **Context Saving:** Always save and restore registers used by your ISR that are not automatically saved by the processor's exception entry mechanism.
*   **`BX LR`:** This is the standard instruction for returning from exception handlers in ARM Cortex-M when the LR register contains an `EXC_RETURN` value.
*   **Critical Sections:** Use interrupt disabling (`CPSID I`/`CPSIE I`) or `BASEPRI` judiciously to protect shared resources and critical sections. Remember to restore the previous interrupt state.
*   **Circular Buffers:** Master the implementation of circular buffers for efficient data streaming between peripherals and memory.
*   **Latency vs. Throughput:** Understand the trade-offs. Low latency is for responsiveness, high throughput is for bulk data. DMA and interrupt-driven IO typically improve both compared to polling.
*   **NVIC Configuration:** Proper configuration of interrupt priorities is vital for managing nested exceptions and ensuring timely servicing of critical events.
*   **Vector Table:** The vector table is the gateway to exception handlers. Ensure it's correctly populated and its address is set.
