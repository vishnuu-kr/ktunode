# BLOCKCHAIN: Module 4: Ethereum – The Ethereum Network

## Topic: Structure of a Smart Contract

---

### **1. Introduction to Smart Contracts on Ethereum (CO4)**

Smart contracts are self-executing contracts with the terms of the agreement directly written into code. They run on a blockchain, most notably Ethereum, and automatically execute when predefined conditions are met. This eliminates the need for intermediaries, increasing efficiency and reducing the risk of fraud.

*   **Definition:** A smart contract is a program that runs on a blockchain and automatically executes when certain conditions are met.
*   **Analogy:** Think of a vending machine. You insert money (condition), select a product (condition), and the machine dispenses the product (execution). Smart contracts automate more complex agreements in a similar fashion.
*   **Key Characteristics:**
    *   **Self-executing:** Automatically runs when conditions are met.
    *   **Immutable:** Once deployed, the code cannot be altered.
    *   **Transparent:** The code and transactions are visible on the blockchain.
    *   **Decentralized:** Runs on a network of computers, not a single server.
    *   **Deterministic:** Given the same inputs, always produces the same output.

---

### **2. The Role of Ethereum in Smart Contracts (CO1, CO4)**

Ethereum was the first blockchain to truly popularize smart contracts and provide a platform for their development and execution.

*   **Ethereum Virtual Machine (EVM):** The EVM is the runtime environment for smart contracts on Ethereum. It's a Turing-complete virtual machine, meaning it can compute anything computable.
    *   **Turing Completeness:** Allows for the creation of complex logic and functionalities within smart contracts.
    *   **Sandboxed Environment:** The EVM executes smart contracts in isolation, preventing them from interfering with the network or other contracts.
*   **Gas:** Every operation performed on the Ethereum network, including executing smart contract functions, requires "gas." Gas is a unit that measures the computational effort required.
    *   **Purpose:** Prevents infinite loops and ensures that users pay for the computational resources they consume.
    *   **Gas Price:** Users specify a gas price in Ether (ETH) to incentivize miners to include their transactions.
*   **Solidity:** The primary high-level programming language used to write smart contracts on Ethereum.
    *   **Object-Oriented:** Supports concepts like inheritance and interfaces.
    *   **Statically Typed:** Requires variable types to be declared.
    *   **Key Features:** Variables, functions, modifiers, events, structs, enums, inheritance, libraries. (Refer to *Solidity Programming Essentials* by Ritesh Modi for detailed syntax).

### **3. Structure of a Smart Contract (CO5)**

A typical smart contract written in Solidity has a well-defined structure.

#### **3.1. Pragma Statement**

*   **Purpose:** Declares the Solidity compiler version to be used for compiling the contract. This is crucial because different compiler versions might have different features or behaviors.
*   **Syntax:** `pragma solidity ^0.8.0;`
    *   `^`: Indicates that the contract can be compiled with any version of Solidity from `0.8.0` up to (but not including) `0.9.0`.
*   **Importance:** Ensures backward compatibility and prevents unexpected behavior due to compiler updates. (Refer to *Mastering Blockchain* by Imran Bashir for details on versioning).

#### **3.2. Contract Definition**

*   **Purpose:** Defines the start of a smart contract. It declares the contract name and can include keywords like `abstract` or `interface`.
*   **Syntax:** `contract MyContract { ... }`
    *   `contract`: Keyword to declare a contract.
    *   `MyContract`: The name of the contract.
*   **Visibility Specifiers:**
    *   `public`: Accessible from any other contract or externally.
    *   `internal`: Accessible only within the current contract and derived contracts.
    *   `private`: Accessible only within the current contract.
    *   `external`: Accessible only from other contracts or externally, but not within the current contract's internal functions. (Default for functions).

#### **3.3. State Variables**

*   **Purpose:** Variables that store data on the blockchain. They are persistent and part of the contract's state.
*   **Declaration:** `uint public myNumber;`
    *   `uint`: Unsigned integer (can be `uint8`, `uint16`, etc., up to `uint256`).
    *   `public`: Makes the variable accessible via a getter function generated by Solidity.
    *   `myNumber`: The name of the variable.
*   **Data Types:**
    *   **Value Types:** `bool`, `int` (signed integer), `uint` (unsigned integer), `address`, `enum`, `struct`, `bytes1` to `bytes32`.
    *   **Reference Types:** `arrays`, `mapping`, `string`.
*   **`mapping`:** A key-value store, similar to hash tables or dictionaries. Ideal for storing data associated with an address or identifier.
    *   **Example:** `mapping(address => uint) public balances;` // Maps an address to its balance.
*   **`memory` vs. `storage`:**
    *   **`storage`:** Data stored permanently on the blockchain. State variables are `storage` by default.
    *   **`memory`:** Temporary data storage used within function execution.
*   **Important Point:** State variables are the primary way smart contracts maintain their data. Their values persist between function calls. (Refer to *Mastering Ethereum* by Antonopoulos & Wood for deep dive into EVM memory and storage).

#### **3.4. Constructor**

*   **Purpose:** A special function that is executed only once when the contract is deployed. It's typically used for initialization.
*   **Syntax:**
    ```solidity
    constructor() {
        // Initialization logic
    }
    ```
*   **Restrictions:** Can only be called once during deployment. Cannot be called by other functions or externally.
*   **Example:** Setting an initial owner or deploying an initial set of parameters.

#### **3.5. Functions**

*   **Purpose:** Blocks of code that perform specific actions. They can read state variables, modify them, or interact with other contracts.
*   **Syntax:**
    ```solidity
    function functionName(parameter1Type parameter1Name, ...) [visibility] [stateMutability] [returns (returnType ...)] {
        // Function logic
    }
    ```
*   **Visibility Specifiers:** `public`, `external`, `internal`, `private`.
*   **State Mutability Specifiers:**
    *   `view`: The function only reads from the blockchain's state but does not modify it.
    *   `pure`: The function does not read from or modify the blockchain's state.
    *   (Default - no specifier): The function can read and modify the blockchain's state.
*   **`returns` Clause:** Specifies the types of values the function will return.
*   **Modifiers:** A powerful feature to modify function behavior, often used for access control or condition checking.
    *   **Syntax:**
        ```solidity
        modifier onlyOwner() {
            require(msg.sender == owner, "Not the owner");
            _; // Placeholder for the function body
        }

        function withdraw() public onlyOwner {
            // ...
        }
        ```
    *   **`require()`:** Used to enforce conditions. If the condition is false, the transaction reverts.
*   **`msg` Object:** A global object containing information about the current transaction:
    *   `msg.sender`: The address that called the function.
    *   `msg.value`: The amount of Ether sent with the transaction.
*   **Example:**
    ```solidity
    uint public value = 5;

    function setValue(uint _newValue) public {
        value = _newValue;
    }

    function getValue() public view returns (uint) {
        return value;
    }
    ```

#### **3.6. Events**

*   **Purpose:** A mechanism for smart contracts to communicate with the outside world (e.g., front-end applications). They log data to the blockchain.
*   **Syntax:**
    ```solidity
    event Transfer(address indexed from, address indexed to, uint value);
    ```
    *   `event`: Keyword to declare an event.
    *   `indexed`: Allows for more efficient filtering of events off-chain.
*   **Emitting Events:**
    ```solidity
    emit Transfer(msg.sender, _to, _value);
    ```
*   **Use Case:** Logging token transfers, recording state changes, providing data for dApps. (Refer to *Blockchain Technology: Concepts and Applications* by Saurabh & Saxena for event logging concepts).

#### **3.7. Structs and Enums**

*   **`struct`:** User-defined type that groups together multiple values of different types.
    *   **Example:**
        ```solidity
        struct Person {
            string name;
            uint age;
        }
        Person public person1; // Default values
        ```
*   **`enum`:** User-defined type that consists of a set of named constants.
    *   **Example:**
        ```solidity
        enum State { Pending, Confirmed, Cancelled }
        State public currentState;
        ```

### **4. Example: A Simple Token Contract (CO5)**

Let's look at a basic structure for a token contract.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract SimpleToken {
    // State Variables
    string public name = "MyToken";
    string public symbol = "MTK";
    uint8 public decimals = 18; // Standard for most tokens
    uint256 public totalSupply;
    mapping(address => uint256) public balances;

    // Events
    event Transfer(address indexed from, address indexed to, uint256 value);

    // Constructor
    constructor(uint256 initialSupply) {
        totalSupply = initialSupply * (10**uint256(decimals));
        balances[msg.sender] = totalSupply; // Mint all tokens to the deployer
    }

    // Function to get balance
    function balanceOf(address account) public view returns (uint256) {
        return balances[account];
    }

    // Function to transfer tokens
    function transfer(address to, uint256 amount) public returns (bool) {
        require(balances[msg.sender] >= amount, "Insufficient balance");
        require(to != address(0), "Invalid recipient address");

        balances[msg.sender] -= amount;
        balances[to] += amount;

        emit Transfer(msg.sender, to, amount);
        return true;
    }
}
```

**Explanation of the example:**

1.  **`SPDX-License-Identifier`**: Important for open-source code compliance.
2.  **`pragma solidity ^0.8.0;`**: Specifies the compiler version.
3.  **`contract SimpleToken { ... }`**: Defines the contract.
4.  **State Variables**:
    *   `name`, `symbol`, `decimals`: Standard token metadata.
    *   `totalSupply`: Total number of tokens in circulation.
    *   `balances`: A mapping to store the token balance for each address.
5.  **Events**:
    *   `Transfer`: Logs every token transfer, making it trackable.
6.  **Constructor**:
    *   Takes `initialSupply` as an argument.
    *   Calculates the actual total supply considering decimals.
    *   Mints all tokens to the contract deployer (`msg.sender`).
7.  **Functions**:
    *   `balanceOf(address account)`: A `view` function to return the balance of a given address.
    *   `transfer(address to, uint256 amount)`: Moves tokens from the caller (`msg.sender`) to another address (`to`). It includes:
        *   **`require()` statements**: To check for sufficient balance and valid recipient address.
        *   **State updates**: Decrements sender's balance, increments recipient's balance.
        *   **`emit Transfer(...)`**: Logs the transfer event.

### **5. Important Points to Remember**

*   **Immutability:** Once deployed, the code of a smart contract cannot be changed. Bugs found later require redeploying a new contract. (Refer to *Mastering Blockchain* by Imran Bashir).
*   **Gas Costs:** Complex operations or those that consume more computational resources will cost more gas. Optimize your code to minimize gas usage.
*   **Security:** Smart contracts are prone to vulnerabilities like reentrancy attacks, integer overflow/underflow, and access control issues. Thorough auditing and best practices are crucial. (Refer to *Mastering Ethereum* by Antonopoulos & Wood for security considerations).
*   **Determinism:** Smart contracts must be deterministic to ensure consensus across the network.
*   **`msg.sender` and `msg.value`:** These are fundamental global variables for understanding who is interacting with the contract and if any Ether was sent.
*   **Error Handling:** Use `require()`, `assert()`, and `revert()` for robust error handling.

### **6. Practice Questions & Answers**

**Question 1:** What is the primary purpose of the `pragma` statement in a Solidity smart contract?

**Answer:** The `pragma` statement specifies the Solidity compiler version that should be used to compile the contract. This ensures that the contract is compiled with compatible compiler settings, preventing potential issues or unexpected behavior due to version differences.

**Question 2:** Explain the difference between `view` and `pure` functions in Solidity.

**Answer:**
*   **`view` functions:** Read data from the blockchain's state but do not modify it. They can access state variables and call other `view` or `pure` functions.
*   **`pure` functions:** Do not read from or modify the blockchain's state at all. They can only operate on their input parameters and local variables.

**Question 3:** What is the significance of the `event` keyword in a smart contract?

**Answer:** `event` is used to emit logs from a smart contract. These logs are stored on the blockchain and can be monitored by external applications (like dApps) to react to specific state changes or actions within the contract, without needing to constantly poll the contract's state.

**Question 4:** In the context of a smart contract, what does `msg.sender` represent?

**Answer:** `msg.sender` represents the address of the account that initiated the current transaction or message call to the contract. It's crucial for access control and tracking origins of actions.

**Question 5:** Why is immutability an important characteristic of smart contracts, and what are its implications?

**Answer:** Immutability means that once a smart contract is deployed to the blockchain, its code cannot be altered. This is crucial for trust and security, as it guarantees that the contract will execute exactly as written. However, it also means that any bugs or vulnerabilities discovered after deployment cannot be fixed directly; a new contract must be deployed, and users would need to migrate their assets or interactions to the new contract. This necessitates rigorous testing and auditing before deployment. (Refer to *Mastering Blockchain* by Imran Bashir).
