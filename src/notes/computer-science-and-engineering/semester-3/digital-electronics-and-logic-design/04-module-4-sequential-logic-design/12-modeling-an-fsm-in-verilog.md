# DIGITAL ELECTRONICS AND LOGIC DESIGN - Module 4: Sequential Logic Design - Modeling an FSM in Verilog

## Introduction

This module delves into modeling Finite State Machines (FSMs) in Verilog, a Hardware Description Language (HDL) widely used for designing digital circuits.  FSMs are fundamental building blocks of digital systems, controlling the sequence of operations based on inputs and current state. This section focuses on how to translate the conceptual FSM model into Verilog code.

## Learning Outcomes

Upon completion of this module, you will be able to:

*   Understand the structure of a Finite State Machine (FSM).
*   Describe the different types of FSMs (Mealy and Moore).
*   Model an FSM using Verilog, including state encoding and transition logic.
*   Write Verilog code for both Mealy and Moore FSMs.
*   Simulate and verify FSM designs in Verilog.

## 1. Understanding Finite State Machines (FSMs)

*   **Definition:** A Finite State Machine (FSM) is a mathematical model of computation used to design digital logic circuits. It consists of a finite number of states, transitions between those states, and actions.

*   **Components:**
    *   **States:** Discrete conditions the FSM can be in.  Represented by bubbles in a state diagram.
    *   **Inputs:** External signals that influence the FSM's behavior and state transitions.
    *   **Outputs:** Signals generated by the FSM, controlled by the current state and/or inputs.
    *   **Transitions:** Rules that determine how the FSM moves from one state to another based on inputs.  Represented by arrows in a state diagram.
    *   **Next State Logic:** Combinational logic that determines the next state based on the current state and inputs.
    *   **Output Logic:** Combinational logic that determines the outputs based on the current state (Moore) or current state and inputs (Mealy).

*   **State Diagram:** A graphical representation of the FSM, depicting states as circles and transitions as arrows labeled with input conditions.

## 2. Types of FSMs: Mealy and Moore

*   **Moore FSM:**
    *   **Output depends only on the current state.** The output logic is a function of the state only.
    *   **Advantages:** Simpler output logic, predictable output behavior (synchronized with the clock).
    *   **Disadvantages:** May require more states to achieve the same functionality as a Mealy machine.
    *   **State Diagram Representation:** Outputs are listed inside the state bubble.

*   **Mealy FSM:**
    *   **Output depends on both the current state and the input.** The output logic is a function of both the state and the input.
    *   **Advantages:** Can often be implemented with fewer states compared to Moore machines.
    *   **Disadvantages:** Output can glitch when the input changes asynchronously to the clock, requiring careful consideration of timing.
    *   **State Diagram Representation:**  Inputs and outputs are listed on the transition arrow in the format "input/output".

*   **Key Difference:**  The fundamental difference lies in how the output is generated.  Moore machines' outputs are synchronized with the clock and depend solely on the state, while Mealy machines' outputs can change asynchronously based on the input.

## 3. Modeling an FSM in Verilog

### 3.1. General Structure

A typical Verilog implementation of an FSM involves the following key sections:

1.  **State Definition:** Define the states using `parameter` or `localparam`. This improves readability and maintainability.
2.  **Input and Output Declarations:** Declare the input and output signals, including the clock and reset signals.
3.  **State Register:** A register to store the current state.
4.  **Next State Logic (Combinational):** A `always @(*)` block that determines the next state based on the current state and inputs. This uses `case` or `if-else` statements.
5.  **State Update Logic (Sequential):** A `always @(posedge clk)` block that updates the current state register based on the next state.  This block includes the reset logic.
6.  **Output Logic (Combinational):** A `always @(*)` block that determines the outputs based on the current state (Moore) or current state and inputs (Mealy).

### 3.2. State Encoding

*   **Binary Encoding:** Each state is assigned a unique binary code.  Requires `ceil(log2(N))` bits for N states.  Example: 4 states can be encoded with 2 bits (00, 01, 10, 11).
*   **One-Hot Encoding:** Each state is assigned a unique bit, with only one bit being '1' at a time. Requires N bits for N states.  Example: 4 states: 0001, 0010, 0100, 1000.  Often results in simpler and faster combinational logic.  More flip-flops are used, so power consumption might be increased.
*   **Gray Encoding:**  Adjacent states differ by only one bit change.  Reduces glitches during state transitions.

**Example (Binary Encoding):**

```verilog
parameter S0 = 2'b00;
parameter S1 = 2'b01;
parameter S2 = 2'b10;
parameter S3 = 2'b11;
```

**Example (One-Hot Encoding):**

```verilog
parameter S0 = 4'b0001;
parameter S1 = 4'b0010;
parameter S2 = 4'b0100;
parameter S3 = 4'b1000;
```

Choose the encoding strategy based on design constraints (area, speed, power).  One-hot encoding is often preferred for FPGAs due to the abundance of flip-flops.

### 3.3. Verilog Code Structure (Moore FSM Example)

```verilog
module MooreFSM (
    input  logic clk,
    input  logic rst,
    input  logic in,
    output logic out
);

  // State definition
  parameter IDLE = 2'b00;
  parameter S1   = 2'b01;
  parameter S2   = 2'b10;

  // State register
  reg [1:0] current_state, next_state;

  // Next state logic
  always_comb begin
    case (current_state)
      IDLE: begin
        if (in) next_state = S1;
        else next_state = IDLE;
      end
      S1: begin
        if (in) next_state = S2;
        else next_state = IDLE;
      end
      S2: begin
        if (in) next_state = S2;
        else next_state = IDLE;
      end
      default: next_state = IDLE; // Avoid latch inference
    endcase
  end

  // State update logic (sequential)
  always_ff @(posedge clk) begin
    if (rst) current_state <= IDLE;
    else current_state <= next_state;
  end

  // Output logic (Moore - depends only on current state)
  always_comb begin
    case (current_state)
      S2: out = 1;
      default: out = 0;
    endcase
  end

endmodule
```

### 3.4. Verilog Code Structure (Mealy FSM Example)

```verilog
module MealyFSM (
    input  logic clk,
    input  logic rst,
    input  logic in,
    output logic out
);

  // State definition
  parameter IDLE = 2'b00;
  parameter S1   = 2'b01;
  parameter S2   = 2'b10;

  // State register
  reg [1:0] current_state, next_state;

  // Next state logic
  always_comb begin
    case (current_state)
      IDLE: begin
        if (in) next_state = S1;
        else next_state = IDLE;
      end
      S1: begin
        if (in) next_state = S2;
        else next_state = IDLE;
      end
      S2: begin
        if (in) next_state = S2;
        else next_state = IDLE;
      end
      default: next_state = IDLE; // Avoid latch inference
    endcase
  end

  // State update logic (sequential)
  always_ff @(posedge clk) begin
    if (rst) current_state <= IDLE;
    else current_state <= next_state;
  end

  // Output logic (Mealy - depends on current state AND input)
  always_comb begin
    case (current_state)
      IDLE: out = 0;
      S1: out = in; // Output depends on the input 'in'
      S2: out = 1;
      default: out = 0;
    endcase
  end

endmodule
```

**Key Differences between the Moore and Mealy Examples:**

*   In the Moore example, the output `out` depends only on the `current_state`.
*   In the Mealy example, the output `out` in state `S1` depends on the input `in`.  This is the crucial distinction.

## 4. Simulation and Verification

*   **Testbench:**  Create a Verilog testbench to provide stimuli (clock, reset, inputs) to the FSM and observe the outputs.
*   **Simulation Tools:** Use simulation tools like ModelSim, Vivado Simulator, or QuestaSim to run the testbench and verify the FSM's behavior.
*   **Coverage Analysis:**  Verify that the testbench covers all states and transitions of the FSM.
*   **Assertions:** Use assertions to check for unexpected behavior and violations of design constraints. Example: `assert property (@(posedge clk) disable iff (rst) current_state != IDLE -> next_state != IDLE);` This is a simplified example that checks after reset is de-asserted, current_state should not be IDLE and next_state should not be IDLE if current_state is not IDLE.

## 5. Important Points to Remember

*   **Always use `always_comb` for combinational logic and `always_ff` for sequential logic.** This helps prevent latch inference and timing issues.
*   **Include a `default` case in `case` statements to avoid latch inference.** Assign a default value to `next_state` and `out`.
*   **Use a reset signal to initialize the FSM to a known state.**
*   **Choose an appropriate state encoding strategy based on the design requirements.**
*   **Thoroughly simulate and verify the FSM to ensure correct functionality.**
*   **Document your design clearly, including the state diagram and Verilog code comments.**
*   **Consider timing constraints and potential metastability issues, especially in Mealy machines.**
*   **Use meaningful state names (e.g., IDLE, READ, WRITE) instead of just S0, S1, etc.**

## 6. Practice Questions and Exercises

**Question 1:**

Design a Moore FSM that recognizes the sequence "110" on an input signal `in`. The FSM should have an output `out` that goes high only when the complete sequence is detected. Assume synchronous operation with a clock signal `clk` and a reset signal `rst`. Write the Verilog code for this FSM using binary encoding.

**Answer:**

```verilog
module SequenceDetectorMoore (
    input  logic clk,
    input  logic rst,
    input  logic in,
    output logic out
);

  // State Definition
  parameter IDLE = 2'b00;
  parameter S1   = 2'b01;
  parameter S11  = 2'b10;

  // State Register
  reg [1:0] current_state, next_state;

  // Next State Logic
  always_comb begin
    case (current_state)
      IDLE: begin
        if (in) next_state = S1;
        else next_state = IDLE;
      end
      S1: begin
        if (in) next_state = S11;
        else next_state = IDLE;
      end
      S11: begin
        if (!in) next_state = IDLE;
        else next_state = S11;  //detects 111 etc. , which means the original sequence is complete and more 1's are following
      end
      default: next_state = IDLE;
    endcase
  end

  // State Update Logic
  always_ff @(posedge clk) begin
    if (rst) current_state <= IDLE;
    else current_state <= next_state;
  end

  // Output Logic (Moore)
  always_comb begin
    case (current_state)
      S11: out = 1;
      default: out = 0;
    endcase
  end

endmodule
```

**Question 2:**

Modify the FSM from Question 1 to be a Mealy FSM. The output `out` should go high in the clock cycle when the '0' of the "110" sequence is received.

**Answer:**

```verilog
module SequenceDetectorMealy (
    input  logic clk,
    input  logic rst,
    input  logic in,
    output logic out
);

  // State Definition
  parameter IDLE = 2'b00;
  parameter S1   = 2'b01;
  parameter S11  = 2'b10;

  // State Register
  reg [1:0] current_state, next_state;

  // Next State Logic
  always_comb begin
    case (current_state)
      IDLE: begin
        if (in) next_state = S1;
        else next_state = IDLE;
      end
      S1: begin
        if (in) next_state = S11;
        else next_state = IDLE;
      end
      S11: begin
        if (!in) next_state = IDLE;
        else next_state = S11; //Stays in S11 detecting more 1s while sequence has completed
      end
      default: next_state = IDLE;
    endcase
  end

  // State Update Logic
  always_ff @(posedge clk) begin
    if (rst) current_state <= IDLE;
    else current_state <= next_state;
  end

  // Output Logic (Mealy)
  always_comb begin
    case (current_state)
      IDLE: out = 0;
      S1:   out = 0;
      S11: begin
          if (!in) out = 1;  // Output goes high only when '0' is received after "11"
          else out = 0;
      end
      default: out = 0;
    endcase
  end

endmodule
```

**Question 3:**

Explain the advantages and disadvantages of using one-hot encoding versus binary encoding for state variables in an FSM.

**Answer:**

*   **One-Hot Encoding:**
    *   **Advantages:**  Simpler combinational logic (often faster), easier debugging.
    *   **Disadvantages:** Uses more flip-flops (area overhead), higher power consumption potentially.

*   **Binary Encoding:**
    *   **Advantages:** Uses fewer flip-flops (area efficient), lower power consumption potentially.
    *   **Disadvantages:** More complex combinational logic (potentially slower), harder debugging.

**Question 4:**

What is latch inference and how can you avoid it when modeling an FSM in Verilog?

**Answer:**

Latch inference occurs when combinational logic (like inside an `always_comb` block) doesn't have a value defined for all possible input combinations.  This results in the simulator inferring a latch, which is undesirable because it can lead to unpredictable behavior and timing problems.

To avoid latch inference:

1.  **Always use complete `case` statements:**  Include a `default` case and assign a value to every signal driven within the `case` statement.
2.  **Fully specify `if-else` statements:** Ensure there's an `else` branch for every `if` condition and assign a value to every signal driven within the `if-else` statement.
3.  **Initialize signals:** Initialize all signals driven within combinational blocks to a known value at the beginning of the block.

This ensures that the combinational logic always has a defined output for any input combination, preventing the simulator from inferring latches.  Failure to do this may result in simulation mismatches compared to the implemented hardware.
