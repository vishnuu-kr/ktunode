# Object Oriented Programming: Module 4 - Event Handling in Swings (Based on SOLID Principles Context)

**Subject:** Object Oriented Programming
**Module:** Module 4: SOLID Principles in Java (Contextualized)
**Topic:** Event Handling in Swings
**Description:** Event Handling in Swings, discussed in the context of Object-Oriented Programming principles, particularly how it relates to, or sometimes violates, SOLID principles.

**Learning Outcomes:**

*   Understand the basic principles of event handling in Swing.
*   Identify different types of Swing events and event sources.
*   Implement event listeners to respond to user interactions.
*   Apply the concepts of event delegation.
*   Recognize how event handling patterns can either adhere to or violate SOLID principles, with a focus on Single Responsibility and Open/Closed Principles.

## 1. Introduction to Event Handling in Swing

*   **What is Event Handling?**  Event handling is the mechanism that controls events and decides what should happen if an event occurs. In GUI programming, events are triggered by user actions (e.g., clicking a button, typing in a text field) or system occurrences (e.g., a window being closed).

*   **Swing Event Model:**  Swing uses an event-delegation model. This means that event sources (GUI components like buttons) delegate the responsibility of handling events to event listeners.

*   **Key Components:**
    *   **Event Source:** The component that generates the event (e.g., JButton, JTextField).
    *   **Event Object:** An object that encapsulates information about the event (e.g., ActionEvent, MouseEvent).  It contains data related to the specific event that occurred.
    *   **Event Listener:** An object that "listens" for a specific type of event and responds to it.  It implements an interface specific to the event type.

## 2. Types of Swing Events and Event Sources

*   **Common Event Types:**
    *   `ActionEvent`:  Generated when a component-defined action occurs (e.g., button click, menu item selection).
    *   `MouseEvent`: Generated when the mouse is pressed, released, clicked, moved, or enters/exits a component.
    *   `KeyEvent`: Generated when a key is pressed, released, or typed.
    *   `ItemEvent`: Generated when the state of an item changes (e.g., a checkbox or radio button is selected/deselected).
    *   `WindowEvent`: Generated when a window is opened, closed, activated, deactivated, etc.
    *   `AdjustmentEvent`: Generated by a scrollbar.
    *   `TextEvent`: Generated by a text component when the text changes.
    *   `FocusEvent`:  Generated when a component gains or loses focus.

*   **Event Sources:**
    *   `JButton`: Generates `ActionEvent`.
    *   `JTextField`, `JTextArea`: Generates `ActionEvent` (when Enter is pressed) and `TextEvent`.
    *   `JCheckBox`, `JRadioButton`: Generates `ItemEvent`.
    *   `JFrame`, `JDialog`: Generates `WindowEvent`.
    *   `JList`, `JComboBox`: Generates `ActionEvent` and `ItemEvent`.
    *   `JScrollBar`: Generates `AdjustmentEvent`.
    *   `JPanel`, `JLabel`: Can generate `MouseEvent` if properly configured.

## 3. Implementing Event Listeners

*   **Steps to Handle an Event:**
    1.  **Identify the Event Source:** Determine which component will generate the event you want to handle.
    2.  **Choose the Appropriate Event Listener Interface:** Select the interface that corresponds to the type of event you want to listen for (e.g., `ActionListener` for `ActionEvent`, `MouseListener` for `MouseEvent`).
    3.  **Implement the Listener Interface:** Create a class that implements the selected listener interface.  This class will contain the `actionPerformed()` (for `ActionListener`), `mouseClicked()`, `mousePressed()`, `mouseReleased()`, `mouseEntered()`, `mouseExited()` (for `MouseListener`), etc. methods.
    4.  **Register the Listener with the Event Source:** Use the `addXXXListener()` method of the event source to register your listener object (e.g., `button.addActionListener(myListener);`).

*   **Example (ActionListener):**

    ```java
    import javax.swing.*;
    import java.awt.*;
    import java.awt.event.*;

    public class ButtonExample extends JFrame {

        private JButton button;
        private JLabel label;

        public ButtonExample() {
            super("Button Example");
            setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
            setLayout(new FlowLayout());

            button = new JButton("Click Me!");
            label = new JLabel("No click yet.");

            // 1. Anonymous inner class implementation of ActionListener
            button.addActionListener(new ActionListener() {
                @Override
                public void actionPerformed(ActionEvent e) {
                    label.setText("Button Clicked!");
                }
            });

            add(button);
            add(label);

            setSize(300, 200);
            setVisible(true);
        }

        public static void main(String[] args) {
            new ButtonExample();
        }
    }
    ```

*   **Different Ways to Implement Listeners:**

    *   **Anonymous Inner Class:**  As shown in the example above.  Convenient for simple listeners that are only used once.
    *   **Separate Class:**  Creates a separate class that implements the listener interface.  Useful for complex listeners or when the listener needs to be reused.
    *   **Implementing the Interface in the Event Source Class:** The class containing the event source itself implements the listener interface (e.g., the `ButtonExample` class itself could implement `ActionListener`).  Can lead to code that violates the Single Responsibility Principle.

## 4. Event Delegation

*   **Explanation:**  As mentioned earlier, Swing uses event delegation.  The event source doesn't handle the event directly; it delegates the responsibility to one or more registered listeners.

*   **Benefits:**
    *   **Decoupling:** The event source doesn't need to know anything about the listener, promoting loose coupling between components.
    *   **Flexibility:** Multiple listeners can respond to the same event.
    *   **Maintainability:** Changes to the way an event is handled don't require modifications to the event source.

## 5. SOLID Principles and Event Handling in Swing

*   **Single Responsibility Principle (SRP):** A class should have only one reason to change.
    *   **Violation:** If a Swing component (e.g., a JFrame) also implements the event listener interfaces and handles the event logic directly within the same class, it's violating the SRP. The class now has two responsibilities: managing the GUI and handling events. This makes the code harder to maintain and test.
    *   **Adherence:**  Create separate listener classes or use anonymous inner classes to handle events. This separates the responsibility of event handling from the responsibility of managing the GUI.

*   **Open/Closed Principle (OCP):**  Software entities (classes, modules, functions, etc.) should be open for extension but closed for modification.
    *   **Potential Violation (Less Obvious):** If event handling logic is tightly coupled within a component, it might be difficult to add new event handlers or modify existing ones without modifying the component itself.  This can be a problem if you want to add more complex event handling logic later on.
    *   **Adherence:** Design event listeners to be easily replaceable or extensible. You can achieve this by using interfaces and abstract classes for your listeners, making it easy to add new listeners without modifying the original component. Consider using the Strategy pattern to encapsulate event handling logic.

*   **Liskov Substitution Principle (LSP), Interface Segregation Principle (ISP), Dependency Inversion Principle (DIP):** These principles are less directly related to the basic event handling mechanisms in Swing but are essential for overall good design in your application.

**Example Illustrating SRP Violation and Improvement:**

*   **SRP Violation (Bad):**

    ```java
    import javax.swing.*;
    import java.awt.*;
    import java.awt.event.*;

    public class BadButtonExample extends JFrame implements ActionListener { // JFrame also handles events

        private JButton button;
        private JLabel label;

        public BadButtonExample() {
            super("Bad Button Example");
            setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
            setLayout(new FlowLayout());

            button = new JButton("Click Me!");
            label = new JLabel("No click yet.");

            button.addActionListener(this); // 'this' refers to the JFrame, which is also the listener

            add(button);
            add(label);

            setSize(300, 200);
            setVisible(true);
        }

        @Override
        public void actionPerformed(ActionEvent e) { // JFrame now handles the button click
            label.setText("Button Clicked!");
        }

        public static void main(String[] args) {
            new BadButtonExample();
        }
    }
    ```

    *   **Problem:** The `BadButtonExample` class (which is a `JFrame`) is responsible for both managing the GUI (creating the button and label) *and* handling the button click event. It violates the Single Responsibility Principle.

*   **SRP Adherence (Good - Using a separate class):**

    ```java
    import javax.swing.*;
    import java.awt.*;
    import java.awt.event.*;

    public class GoodButtonExample extends JFrame { // JFrame only manages the GUI

        private JButton button;
        private JLabel label;

        public GoodButtonExample() {
            super("Good Button Example");
            setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
            setLayout(new FlowLayout());

            button = new JButton("Click Me!");
            label = new JLabel("No click yet.");

            // Use a separate listener class
            button.addActionListener(new MyActionListener(label));

            add(button);
            add(label);

            setSize(300, 200);
            setVisible(true);
        }

        public static void main(String[] args) {
            new GoodButtonExample();
        }
    }

    // Separate class for handling the event
    class MyActionListener implements ActionListener {
        private JLabel label;

        public MyActionListener(JLabel label) {
            this.label = label;
        }

        @Override
        public void actionPerformed(ActionEvent e) {
            label.setText("Button Clicked!");
        }
    }
    ```

    *   **Solution:**  The `GoodButtonExample` class is responsible only for creating the GUI. The `MyActionListener` class is responsible only for handling the button click event. This adheres to the Single Responsibility Principle.

## 6. Important Points to Remember

*   **Event Delegation is Key:** Understand how event delegation works in Swing.
*   **Choose the Right Listener Interface:** Select the appropriate listener interface for the type of event you want to handle.
*   **Consider SOLID Principles:** Design your event handling logic with the SOLID principles in mind, especially SRP.  Avoid creating "god classes" that handle too many responsibilities.
*   **Careful of Overuse of Anonymous Inner Classes:** While convenient, overuse of anonymous inner classes can lead to code that is hard to read and maintain, particularly for complex event handling logic.
*   **Understand the Event Object:** The event object (e.g., `ActionEvent`, `MouseEvent`) provides information about the event that occurred.  Use this information to customize your event handling logic.
*   **Unregister Listeners:** In some cases, you might need to unregister listeners when they are no longer needed to prevent memory leaks (though Swing's automatic garbage collection makes this less of a concern now, it's still good practice in complex applications).  Use `removeXXXListener()` methods for this.

## 7. Practice Questions/Exercises

1.  **Question:** Explain the concept of event delegation in Swing.  Why is it important?
    *   **Answer:** Event delegation means the event source doesn't handle the event directly; it delegates the responsibility to registered listeners. This promotes decoupling, flexibility, and maintainability.

2.  **Question:** What are the steps involved in handling a button click event in Swing? Provide sample code.
    *   **Answer:**
        1.  Get the JButton object.
        2.  Create an ActionListener object (e.g., using an anonymous inner class or a separate class).
        3.  Implement the `actionPerformed()` method to define the event handling logic.
        4.  Register the ActionListener with the JButton using `button.addActionListener(myListener)`.

        ```java
        JButton button = new JButton("Click Me");
        button.addActionListener(new ActionListener() {
            @Override
            public void actionPerformed(ActionEvent e) {
                System.out.println("Button Clicked!");
            }
        });
        ```

3.  **Question:**  Why is it generally considered bad practice for a `JFrame` class to also implement `ActionListener` and handle button click events directly within the same class? What SOLID principle does this violate?
    *   **Answer:** It violates the Single Responsibility Principle (SRP). The `JFrame` should be responsible for managing the GUI, not also for handling events.  This leads to a "god class" that is harder to maintain and test.

4.  **Question:**  How can you ensure your event handling code adheres to the Open/Closed Principle?
    *   **Answer:** Design event listeners to be easily replaceable or extensible. You can achieve this by using interfaces and abstract classes for your listeners, making it easy to add new listeners without modifying the original component.  Consider using the Strategy pattern to encapsulate event handling logic.

5.  **Exercise:** Create a simple Swing application with a text field and a button. When the button is clicked, display the text entered in the text field in a label below the button. Implement the event listener in a separate class.

    *   **Answer (Example):**

        ```java
        import javax.swing.*;
        import java.awt.*;
        import java.awt.event.*;

        public class TextFieldButtonExample extends JFrame {

            private JTextField textField;
            private JButton button;
            private JLabel label;

            public TextFieldButtonExample() {
                super("Text Field Button Example");
                setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
                setLayout(new FlowLayout());

                textField = new JTextField(20);
                button = new JButton("Display Text");
                label = new JLabel("");

                button.addActionListener(new DisplayTextListener(textField, label));

                add(textField);
                add(button);
                add(label);

                setSize(400, 200);
                setVisible(true);
            }

            public static void main(String[] args) {
                new TextFieldButtonExample();
            }
        }

        class DisplayTextListener implements ActionListener {
            private JTextField textField;
            private JLabel label;

            public DisplayTextListener(JTextField textField, JLabel label) {
                this.textField = textField;
                this.label = label;
            }

            @Override
            public void actionPerformed(ActionEvent e) {
                String text = textField.getText();
                label.setText("You entered: " + text);
            }
        }
        ```
