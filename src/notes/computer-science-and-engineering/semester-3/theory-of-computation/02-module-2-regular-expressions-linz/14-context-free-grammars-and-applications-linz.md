## THEORY OF COMPUTATION - Module 2: Regular Expressions (Linz) - Context-Free Grammars and Applications

**Introduction:** This module delves into Context-Free Grammars (CFGs), a powerful tool for describing formal languages. CFGs are more expressive than regular expressions and are crucial for understanding the syntax of programming languages and many other formal systems. We will explore their definition, properties, and applications.

**Learning Outcomes:**

*   Understand the formal definition of a Context-Free Grammar.
*   Be able to design CFGs for specific languages.
*   Understand and be able to create parse trees for strings derived from a CFG.
*   Learn about ambiguity in CFGs and methods for dealing with it.
*   Understand the relationship between CFGs and Pushdown Automata (PDAs).
*   Recognize practical applications of CFGs in programming language parsing and other areas.

**1. Formal Definition of a Context-Free Grammar**

*   **Definition:** A Context-Free Grammar (CFG) is a tuple G = (V, T, P, S) where:

    *   **V:** A finite set of variables or non-terminals (representing syntactic categories).
    *   **T:** A finite set of terminals (representing the basic symbols of the language), disjoint from V.
    *   **P:** A finite set of production rules, where each production rule has the form A → α, where A ∈ V and α ∈ (V ∪ T)* (α is a string of variables and/or terminals).
    *   **S:** The start variable or start symbol, S ∈ V.

*   **Example:**  G = ({S}, {a, b}, P, S), where P consists of the following productions:

    *   S → aSb
    *   S → ε (epsilon, representing the empty string)

*   **Terminology:**

    *   A production rule A → α means "A can be replaced by α".
    *   `S` is the root of the grammar.
    *   `(V ∪ T)*` denotes the set of all possible strings formed by elements of V and T, including the empty string.

**2. Designing CFGs for Specific Languages**

*   **Key Idea:** Start with the simplest case of the language and then build up complexity. Consider how to generate strings inductively.

*   **Example 1: The language L = {a<sup>n</sup>b<sup>n</sup> | n ≥ 0 }**

    *   CFG: G = ({S}, {a, b}, P, S)
        *   P:
            *   S → aSb
            *   S → ε

*   **Example 2: The language L = {w | w is a palindrome over {a, b}}**

    *   CFG: G = ({S}, {a, b}, P, S)
        *   P:
            *   S → aSa
            *   S → bSb
            *   S → a
            *   S → b
            *   S → ε

*   **Example 3: The language of arithmetic expressions (simplified):**

    *   CFG: G = ({E, T, F}, {+, *, (, ), id}, P, E)
        *   P:
            *   E → E + T | T
            *   T → T * F | F
            *   F → (E) | id

*   **General Strategy:**

    1.  **Identify the base case(s):** What are the simplest strings in the language?
    2.  **Identify the recursive step(s):** How can you build more complex strings from simpler ones?
    3.  **Create productions for the base cases and recursive steps.**

**3. Derivations and Parse Trees**

*   **Derivation:** A derivation is a sequence of steps used to generate a string from a CFG's start symbol. Each step applies a production rule to replace a variable with its right-hand side.

    *   **⇒ :**  "Derives in one step." A ⇒ B if B can be obtained from A by applying a single production rule.
    *   **⇒<sup>*</sup> :** "Derives in zero or more steps." A ⇒<sup>*</sup> B if B can be obtained from A by applying zero or more production rules.

*   **Leftmost Derivation:**  At each step, the leftmost variable is replaced.
*   **Rightmost Derivation:** At each step, the rightmost variable is replaced.

*   **Example (using the grammar from Example 1 above, L = {a<sup>n</sup>b<sup>n</sup> | n ≥ 0 }):**

    *   Deriving "aabb":
        *   Leftmost Derivation: S ⇒ aSb ⇒ aaSbb ⇒ aabb
        *   Rightmost Derivation: S ⇒ aSb ⇒ aabb ⇒ aabb

*   **Parse Tree (Derivation Tree):** A tree representation of a derivation.

    *   The root of the tree is the start symbol.
    *   Internal nodes are variables.
    *   Leaves are terminals or ε.
    *   The children of each internal node correspond to the symbols on the right-hand side of the production rule applied at that node.
    *   The string generated by the derivation is the concatenation of the leaves, read from left to right (yield of the tree).

*   **Parse Tree Example (for the string "aabb" using the same grammar):**

    ```
          S
         / \
        a   S  b
           / \
          a   S  b
             /
            ε
    ```

**4. Ambiguity in CFGs**

*   **Definition:** A CFG is ambiguous if there exists at least one string in the language generated by the grammar that has two or more distinct parse trees (or, equivalently, two or more distinct leftmost derivations or two or more distinct rightmost derivations).

*   **Example (Ambiguous Grammar for Arithmetic Expressions):**

    *   CFG: G = ({E}, {+, *, id}, P, E)
        *   P:
            *   E → E + E | E * E | id

    *   The string "id + id * id" has two parse trees (and two leftmost derivations):

        *   Tree 1 (associating `+` first):
            ```
                  E
                 /|\
                E + E
               /   /|\
              id  E * E
                 id  id
            ```

        *   Tree 2 (associating `*` first):
            ```
                  E
                 /|\
                E * E
               /   /|\
              E + E  id
             / \
            id  id
            ```

*   **Dealing with Ambiguity:**

    *   **Rewrite the grammar:**  Create an equivalent grammar that is unambiguous. This is often done by enforcing precedence and associativity rules in the grammar.  See the arithmetic expression grammar in Section 2 for an example of an unambiguous grammar.

    *   **Use precedence and associativity rules during parsing:**  Some parsing techniques can handle ambiguous grammars by applying precedence and associativity rules during the parse. Tools like Yacc/Bison fall into this category.

*   **Important Note:** Not all languages have unambiguous grammars.  Some languages are inherently ambiguous.  However, for practical applications (like programming language parsing), we almost always use unambiguous grammars.

**5. CFGs and Pushdown Automata (PDAs)**

*   **Relationship:** CFGs are equivalent in power to Pushdown Automata (PDAs).  That is, for every CFG, there exists a PDA that accepts the same language, and for every PDA, there exists a CFG that generates the same language.

*   **Informal Idea:**  A PDA can simulate a CFG's derivation process by using its stack to keep track of the variables that need to be expanded.

*   **Conversion (CFG to PDA):** This conversion involves creating a PDA that simulates a leftmost derivation of the CFG.  The PDA will push the right-hand side of a production rule onto the stack when it encounters the corresponding variable. If the stack head matches the input string, the symbols are popped.

*   **Conversion (PDA to CFG):**  This conversion is more complex and involves constructing a CFG that generates all strings accepted by the PDA. This is typically done by creating variables that represent the state of the PDA and the symbols on the stack.

*   **Significance:** This equivalence highlights the power of both CFGs and PDAs.  PDAs provide a more operational view of recognizing context-free languages, while CFGs provide a more declarative way of describing them.

**6. Applications of CFGs**

*   **Programming Language Parsing:** The primary application of CFGs is in defining the syntax of programming languages.  Compilers and interpreters use parsers based on CFGs to analyze the structure of code and generate executable code. The grammar specifies valid language constructs.

*   **XML and other markup languages:**  CFGs are used to define the structure of XML documents and other structured data formats. This allows parsers to validate the structure and extract information.

*   **Natural Language Processing (NLP):**  CFGs can be used to model the syntax of natural languages, though more sophisticated models (like probabilistic CFGs) are often needed to handle the complexities of natural language.

*   **Compiler Construction:** Syntax analysis phase, which utilizes parsers (usually generated automatically from a CFG) to ensure that the input program adheres to the grammar rules of the programming language.

*   **Data Validation:** CFGs can be used to specify the valid formats for data files, and can be used to write programs to validate that the structure of data files conforms to the grammar.

**Practice Questions and Exercises**

1.  **Design a CFG for the language L = {a<sup>n</sup>b<sup>m</sup>c<sup>n</sup> | n, m ≥ 0 }**

    *   **Answer:**
        *   G = ({S, A, B}, {a, b, c}, P, S)
        *   P:
            *   S → aSc | B
            *   B → bB | ε

2.  **Given the CFG: S → aSb | bSa | ε. Derive the string "abba" using a leftmost derivation and draw the parse tree.**

    *   **Answer:**
        *   Leftmost Derivation: S ⇒ aSb ⇒ abSaSb ⇒ abbSaSb ⇒ abbaSb ⇒ abbaεb ⇒ abba
        *   Parse Tree:
            ```
                S
               /|\
              a S b
             /   /|\
            b   S a S
               /      \
              ε        ε
            ```

3.  **Is the following CFG ambiguous? If so, show an example string with two different parse trees.**
    *   S → AB
    *   A → aA | ε
    *   B → bB | ε

    *   **Answer:** Yes, the grammar is ambiguous. The string "ab" has the following derivations:

        *   S ⇒ AB ⇒ aAB ⇒ aB ⇒ abB ⇒ ab
        *   S ⇒ AB ⇒ aAB ⇒ aAbB ⇒ aabB (This leads to a different parse tree although it cannot derive the string ab)
        *   S ⇒ AB ⇒ AbB ⇒ aAbB(This also leads to a different parse tree although it cannot derive the string ab)

        *More accurately, although the string `ab` does not have two different parse trees, the string "" (epsilon) has two different parse trees.*
        * S ⇒ AB ⇒ A => epsilon, B => epsilon
        * S => AB => epsilon

4.  **Briefly explain the relationship between CFGs and PDAs.**

    *   **Answer:** CFGs and PDAs are equivalent formalisms.  For any CFG, you can construct a PDA that recognizes the same language, and vice-versa. This equivalence demonstrates that CFGs can be implemented by a computing device with a stack.

**Important Points to Remember**

*   CFGs are more powerful than regular expressions.
*   Ambiguity can be a problem when designing CFGs for programming languages.
*   Parse trees are visual representations of derivations.
*   CFGs and PDAs are fundamentally related.
*   CFGs are used extensively in compiler construction and other areas of computer science.
*   Understanding the design principles for CFGs (identifying base cases and recursive steps) is crucial.
