# THEORY OF COMPUTATION - Module 2: Regular Expressions (Linz) - CFGs and Programming Languages

## 2. Key Concepts and Definitions

### 2.1 Context-Free Grammar (CFG) Definition

A **Context-Free Grammar (CFG)** is a formal grammar defined as a 4-tuple:

G = (V, T, P, S) where:

*   **V** is a finite set of *variables* or *non-terminal symbols*. These are symbols that can be replaced by other symbols or terminal strings.
*   **T** is a finite set of *terminal symbols*. These are the basic symbols of the language that cannot be replaced.  V and T are disjoint (V ∩ T = ∅).
*   **P** is a finite set of *production rules* (or simply, productions).  Each production rule is of the form:  A → α where A ∈ V and α ∈ (V ∪ T)* (i.e., α is a string of zero or more variables and terminals).  A is the *left-hand side* (LHS) and α is the *right-hand side* (RHS).
*   **S** is the *start variable* or *initial symbol*, where S ∈ V.  The derivation process begins with the start variable.

**Important Considerations:**

*   The "context-free" part means that the replacement of a variable doesn't depend on the surrounding symbols.  The production A → α allows us to always replace A with α, regardless of where A appears in a string.

### 2.2 Derivations

A **derivation** is a sequence of replacements according to the production rules of the grammar. We use the following notation:

*   **α ⇒ β**:  String α *derives* string β in one step if α = γAδ, β = γωδ, and A → ω is a production in P.  We are replacing the variable A in α with ω according to a production rule.
*   **α ⇒<sup>*</sup> β**: String α derives string β in zero or more steps (the reflexive transitive closure of ⇒).  This means either α = β, or there exist strings α<sub>1</sub>, α<sub>2</sub>, ..., α<sub>n</sub> such that α ⇒ α<sub>1</sub> ⇒ α<sub>2</sub> ⇒ ... ⇒ α<sub>n</sub> ⇒ β.

### 2.3 Language Generated by a CFG

The **language generated by a CFG G**, denoted L(G), is the set of all terminal strings that can be derived from the start variable S:

L(G) = {w ∈ T<sup>*</sup> | S ⇒<sup>*</sup> w}

### 2.4 Parse Trees

A **parse tree** (or derivation tree) is a tree representation of a derivation.  It illustrates how a string is generated by a CFG.

*   The root of the tree is labeled with the start variable S.
*   Internal nodes are labeled with non-terminal symbols (variables) from V.
*   Leaf nodes are labeled with terminal symbols from T.
*   If an internal node is labeled with variable A and its children are labeled with X<sub>1</sub>, X<sub>2</sub>, ..., X<sub>n</sub>, then A → X<sub>1</sub>X<sub>2</sub>...X<sub>n</sub> is a production rule in P.  (Each X<sub>i</sub> is either a terminal or a variable.)

### 2.5 Ambiguity

A CFG is **ambiguous** if there exists a string w ∈ L(G) that has two or more distinct parse trees (or equivalently, two or more distinct leftmost derivations or rightmost derivations).  Ambiguity can be a problem in programming languages because it can lead to multiple interpretations of the same program.

### 2.6 CFGs and Programming Language Syntax

CFGs are used to formally define the **syntax** of programming languages. The syntax specifies the legal structure of programs in a language, independent of their meaning (semantics).

*   Terminals represent the basic lexical elements (tokens) of the language (e.g., keywords, identifiers, operators, constants).
*   Non-terminals represent syntactic categories (e.g., expression, statement, function definition).
*   Production rules define how these syntactic categories can be combined to form valid program structures.

## 3. Examples

### 3.1 Example 1:  Simple Arithmetic Expressions

Let's define a CFG for simple arithmetic expressions with addition and multiplication:

G = (V, T, P, E) where:

*   V = {E}  (E represents an expression)
*   T = {id, +, *, (, )}  (id represents an identifier)
*   P = {
    *   E → E + E
    *   E → E * E
    *   E → (E)
    *   E → id
    }
*   S = E

**Derivation:**

Let's derive the string "id + id * id":

E ⇒ E + E ⇒ id + E ⇒ id + E * E ⇒ id + id * E ⇒ id + id * id

**Parse Tree:**

```
      E
     /|\
    E + E
   /   /|\
 id  E * E
    /   / \
   id  *  id
```

**Ambiguity:**

This grammar is ambiguous.  Consider the string "id + id * id".  It has another parse tree:

```
         E
        /|\
       E * E
      /|\   \
     E + id  id
    / \
   id  id
```

This ambiguity arises because the grammar doesn't specify operator precedence (which operation should be performed first). In the first parse tree, `*` has precedence.  In the second parse tree, `+` has precedence.

### 3.2 Example 2:  If-Then-Else Statement

Let's define a CFG for a simplified if-then-else statement:

G = (V, T, P, S) where:

*   V = {S, B} (S represents a statement, B represents a Boolean expression)
*   T = {if, then, else, id, =, ;} (id represents an identifier)
*   P = {
    *   S → if B then S else S
    *   S → id = id;
    *   B → id = id
    }
*   S = S

**Derivation:**

Let's derive the string "if id = id then id = id; else id = id;":

S ⇒ if B then S else S ⇒ if id = id then S else S ⇒ if id = id then id = id; else S ⇒ if id = id then id = id; else id = id;

**Parse Tree:**

```
               S
             / | \
            if B then S else S
            /  |    |     |  \
          if id = id then id = id; else id = id;
```

### 3.3 Example 3: A simpler Arithmetic Expression grammar (unambiguous)

To remove ambiguity from the arithmetic expression grammar, we can introduce different non-terminals to enforce precedence:

G = (V, T, P, E) where:

*   V = {E, T, F} (E: Expression, T: Term, F: Factor)
*   T = {id, +, *, (, )}
*   P = {
    *   E → E + T
    *   E → T
    *   T → T * F
    *   T → F
    *   F → (E)
    *   F → id
    }
*   S = E

In this grammar, multiplication has higher precedence than addition due to the way the rules are structured.

Now, the string `id + id * id` only has one parse tree, reflecting the standard precedence.

## 4. Practice Questions/Exercises

1.  **Define a CFG for the language {a<sup>n</sup>b<sup>n</sup> | n ≥ 0}.**

    *Answer:* G = ({S}, {a, b}, P, S) where P = { S → aSb, S → ε }

2.  **Draw a parse tree for the string "aabb" using the CFG from question 1.**

    *Answer:*

    ```
          S
         / \
        a   S   b
           / \
          a   S   b
             / \
            ε
    ```

3.  **Define a CFG for the language of all strings of balanced parentheses.**  For example, "()", "(())", "()()", etc.

    *Answer:* G = ({S}, {(, )}, P, S) where P = {S → (S), S → SS, S → ε }

4.  **Consider the CFG:**

    S → aS | bS | ε

    **What language does this CFG generate?**

    *Answer:*  The language {a, b}<sup>*</sup> (all strings of a's and b's, including the empty string).

5.  **Is the following grammar ambiguous? Why or why not?**

    S → S + S | S * S | id

    *Answer:* Yes, this grammar is ambiguous because a string like "id + id * id" has two distinct parse trees, leading to different interpretations of operator precedence.

6.  **Design a CFG for representing simple variable declarations in a programming language, such as "int x;" or "float y;". Assume the terminals are {int, float, id, ; }.**

    *Answer:* G = ({S, TYPE}, {int, float, id, ; }, P, S) where P = {S → TYPE id ;, TYPE → int, TYPE → float}

## 5. Important Points to Remember

*   CFGs are a powerful tool for defining the syntax of programming languages.
*   The ambiguity of a CFG can lead to parsing problems and multiple interpretations of the same program. Therefore, it's often desirable to design unambiguous grammars, though not all languages have unambiguous CFGs.
*   CFGs are used in the construction of parsers, which are essential components of compilers and interpreters.
*   CFGs describe context-free languages, which are a larger class of languages than regular languages (languages described by regular expressions).
*   Pay close attention to the order of operations and associativity when designing grammars for expressions.  The grammar structure must reflect the desired precedence and associativity.
*   Understanding derivations and parse trees is crucial for understanding how a CFG generates a language and for identifying potential ambiguities.
